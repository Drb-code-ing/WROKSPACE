## 什么是Function Call ?
不就是Tool? 不好意思， 面试就到这。
工具Tool 和 Function Call 不是一回事。
Function Call 字面意思是函数调用。
llm 可以根据文字语义， 转成结构化参数， 然后给到函数， 执行， 并将结果
放入message 列表。
准确的定义是， Function Call 是工具一种调用方式，
Tool 是包含Function Call的。

为什么叫Tools?
真实项目中会有很多的工具。
Tools 的定义里有一个describe 字段 ，它会塞到大模型的上下文中，
**描述**即提示词。

如果项目中有 100个工具， 会出现什么问题， 怎么解决？

会将100段对工具的描述全部塞到llm的上下文， 导致上下文爆炸 开销巨大、产生幻觉，
工具调用不准确。

懒加载 -》 思考

多Agent架构

这个时候就衍生了 意图识别（做路由）， 走到对应的Sub Agents, 就可以将这100个工具
拆分。 一个子Agent  只负责部分工具， 这样就解决了上下文爆炸问题， 从架构上解决了问题。

我为什么要有工具?
赋予大模型访问外部系统、执行动作的能力，弥补模型静态知识与能力边界的不足。
工具多了怎么办？ 通过意图识别 拆分子Agent, 把工具分组隔离， 缩减单次上下文负载。
整个链路方案是？ 意图识别路由到子Agent, 子Agent 加载对应分组工具， 完成工具调用
并汇总结果。 deepagents 做多Agent 快速开发。

## 说下RAG的流程

RAG 分为两个阶段 ：
  - 离线知识库构建阶段
  对各种格式的文档加载解析、清洗、分块
  分块后用嵌入模型生成向量， 存入向量数据库，用于语义检索。
  构建BM25 倒排索引， 存入es 全文检索数据库， 用于关键词检索
  将数据块之间的关系通过 图数据库存储， 用于多跳检索。
  - 在线问答阶段
  会对用户问题做query 改写， 换成更适合检索的表达。
  然后会做混合检索
  向量检索根据语义匹配相识的内容
  关键词检索根据具体术语、专有名词去精确匹配内容
  多跳检索根据数据实体之间的关系， 去构建更复杂的检索路径。
  之后会去做去重， 用RFF算法 对结果合并排序。
  之后用ReRank 重排模型筛选和问题相关的文档片段
  把筛选后的文档片段放入prompt, 交给大模型生成回答。
  这就是混合检索RAG 的流程。
