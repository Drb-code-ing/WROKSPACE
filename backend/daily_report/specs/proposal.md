# 智能日报生成器

## 1. 背景与目标

### 1.1 背景
目前，团队成员每天需要消耗15-30min 手动撰写日报，内容涵盖当日代码提交、任务进展及协作沟通情况。
这一过程不仅重复低效，且常因遗忘导致信息缺失

另外，团队需要Leader需要成员的工作动态，但人撰写的日报往往信息密度低，格式参数不齐，严重影响了阅读体验与管理效率。

### 1.2 目标
构建一个自动化工具，旨在从团队现有的协作平台中抓取当日工作数据，自动生成结构化日报，并精准送给相关干系人。

### 1.3 目标用户
- 主要目标（数据生产者）：5 - 15 人的研发团队核心成员
- 主要读者（数据消费者）：团队Leader、项目负责人、客户代表等

## 2. 功能范围

### 2.1 做什么（本期）

#### 数据采集
- 对接GitHub/GitLab，获取当日代码提交记录（含Commit Message 及变更统计）
- 对接飞书/Jira，抓取当日任务状态流转（如新建、进行中、已完成）
- 从飞书群消息中提取与项目强相关的讨论摘要

#### 日报生成
- 将采集数据按“代码提交 -> 任务进展 -> 协作沟通”的逻辑进行三段式编排
- 为每个成员生成独立的日报
- 输出Markdown 格式（支持无缝转换为HTML 邮件）

#### 推送通知
- 每个工作日 18:00 自动触发日报生成流程
- 通过SMTP 服务向团队Leader 发送HTML 格式邮件
- 通过飞书机器人将Markdown 格式日报推送至团队组群

### 2.2 不做什么
- 不做智能摘要和AI 总结（本期仅做数据清洗与整理，不涉及语义理解）
- 不做移动端
- 不做历史日报的搜索与统计图表分析
- 不做个人日报的手动编辑与补充功能
- 不做支持团队隔离/多租户架构

### 2.3 技术架构
- 开发语言： Python 3.11 及更高版本（复用团队现有技术栈）
- 部署环境：公司内网服务器（Docker 容器化部署）
- 外部依赖：Github API、飞书平台API、SMTP 服务、飞书机器人
- 运行方式：定时任务（如使用 Cron 表达式），不需要常驻后台服务

## 3. 验收标准

### 3.1 功能验收

- [ ] 能够准确获取指定Github 仓库过去24h 内所有成员的Commit 记录
- [ ] 能够准确获取飞书项目中当日发生状态变更的任务列表
- [ ] 能够从飞书消息中筛选并提取包含指定关键词的讨论记录
- [ ] 生成的日报必须包含“代码提交”，“任务进展”和“协作沟通”三部分
- [ ] 日报必须符合Markdown 格式规范，支持无缝转换为HTML 邮件
- [ ] 邮件发送链路畅通，团队Leader 能够正常收到HTML 格式的日报
- [ ] 飞书机器人能够正常将Markdown 格式的日报发送至指定团队组群

### 3.2 性能验收
- [ ] 单词日报生成耗时(5人团队为例) < 60s
- [ ] 单一数据源（如某API）超时或失败，不影响其他数据源的正常采集
- [ ] 采集失败的数据源需要在日报中显示标注“数据源获取失败”，严禁静默跳过

### 3.3 边界场景
- [ ] 若团队成员当日无任何提交、任务或消息，日报对应的板块应显示“今日无记录”
- [ ] 当Github API 触发限流时，系统应具备等待并重试机制（上限三次）
- [ ] 当飞书Token 过期时，系统应自动刷新Token
- [ ] 系统需要识别非工作日（周末或法定节假日），并自动跳过日报生成

### 4. 术语定义

| 术语 | 定义 |
| --- | ----------------------------------------------------- |
| 代码提交 | 从 GitHub/GitLab 获取的当日代码提交记录 |
| 任务    | 从飞书/Jira 获取的当日任务状态流转记录 |
| 协作沟通 | 从飞书群消息中提取的与项目强相关的讨论摘要 |
| 日报    | 系统自动生成的每日工作摘要，涵盖代码、任务、沟通三个维度 |
| 成员    | 已在系统中完成 GitHub 与飞书账号映射绑定的团队成员 |
| 数据源  | 提供原始工作数据的外部协作平台（GitHub、飞书任务、飞书消息） |
| 采集窗口 | 单次采集所覆盖的时间跨度，默认为当日 00:00 至任务执行时刻 |
