## 功能需求
工作中汇报、进度、问题、解决方案 等上传下达，工作中的一环

- proposal.md 的三层结构 模版
  - 第一层：目标层(Why)
    核心问题：为什么做该项目？旨在解决何种痛点
    关键内容、项目背景、核心目标、目标画像及成功标准
    形象类比：我们要建造一座什么样的房子？供谁居住
  - 第二层：范围层(What)
    核心问题：项目范围包括哪些？
    关键内容、项目功能、项目边界、项目依赖和约束等
    形象类比：房子有几层？几个房间？是否包含花园？
  - 第三层：验收层
    核心问题：怎么判断项目完成了？如何验证交付质量？
    关键内容：可量化的验收标准、性能指标及边界场景测试

### 需求文档总结

SDD 工作流的首要步骤，将模糊的需求意图转化为结构化规范

需求分析的核心任务并非“穷举所有功能”，而是促使隐含的决策显性化。每一个“AI 可能产生误解或猜测的环节”，
都需要化为“人类明确做出的选择”，包括数据来源，目标受众，实现程度和排除范围。这些选择被记录在proposal.md 中。
成为后续所有开发工作的基石和验收标准。

proposal 遵循“目标层(Why)、范围层(What)、验收层” 的三层结构，三者之间存在紧密的逻辑约束关系，目标层界定范围层，范围层界定验收层，而验收层方向验证目标层的实现程度

撰写规范时，对精度的把控是一种需要刻意练习的核心功能：其标准在于“恰好够AI 执行”

判断这一界限的标准十分明确：
如果某项决策改变了系统的行为，则需要写入规范；
如果他仅改变代码的编写方式：则由AI 决定；

AI 严格遵循 proposal.md 中的规范，一次到位

## 架构设计
how
proposal.md 定义**做什么**，design.md 定义**如何做**

运筹帷幄之中，决胜千里之外 -- 好的架构设计，往往在落地之前便已奠定胜局

从proposal.md 到 design.md 关键的一步跨越
堪称SDD 全流程中信息密度最高、思想跨越最大的关键一步

先画地图，再行军

本质并非“绘制图表”，而是在编码之前回答一系列**结构性**问题
系统任何划分、模块间任何通信，采用何种技术栈及决策依据，任何保障非功能性要求

如果这些问题没有在design.md 中明确，AI 会猜，生成代码往往并非我们所想

design.md 4个核心组成部分

- 系统架构
  包括模块划分、职责定义、以及数据流向
  设计需要遵循 **单一职责原则** 和 **关注点分离原则**
  （单一职责原则：每个模块只负责一个功能，只有一个引起它变化的原因）
  ```py
  # 没有遵循单一职责原则，User 类负责了获取用户姓名和保存用户信息两个职责

  class User:
    def __init__(self, name, age):
      self.name = name
      self.age = age
    # 职责一：获取用户姓名
    def get_name(self):
      return self.name
    # 职责二：将用户信息保存到数据库
    def save_to_db(self):
      print(f"保存用户信息到数据库：{self.name}")
  ```

  ```py
  class User:
    def __init__(self, name, age):
      self.name = name
      self.age = age
    
  class UserRepository:
    def save(self, user: User):
      print(f"保存用户信息到数据库：{user.name}")
  ```
