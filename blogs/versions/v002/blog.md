# 从 Prompt 到 3D 小世界：一个 AI Native 开发者的实践与思考

## 引言

上篇文章聊了 **OPC（一人公司）** 的概念——一个人借助 AI，身兼 PM、设计师、前端、后端七个角色。有读者问：听起来很美好，但具体怎么落地？

今天我就用一次完整的实践来回答这个问题——**用 AI 搭了一个 3D 小世界编辑器**。

整个过程只用了一个中午，从需求描述到最终产出，AI 写了几乎全部代码。但有意思的是，在这个过程中我学到的最重要的东西不是 Three.js 的 API，而是两件事：**复杂 prompt 的设计方法**，以及 **LLM 到底是怎么工作的**。

这篇文章就把这两个收获串起来讲给你听。

## 一、搭建 3D 小世界：一次完整的 Prompt 驱动开发

事情是这样的：我想做一个 3D 小世界编辑器——类似"摆在桌子上的小模型"那种感觉，不是开放世界游戏。8x8 的网格，鼠标点格子放东西，可以拖拽旋转视角，能存档，首次打开还有个操作提示。

需求很明确，但技术上有严格的约束：单页面、零构建、Three.js 用 CDN 引入、不要 ES module、不要 npm、所有物体用 Three.js 内置几何体拼，不要外部模型。

我把这些需求整理成了一段 prompt，核心结构是这样的：

```
我想做一个网页的"3D 小世界编辑器"，定位是"摆在桌子上的小模型"

## 我想要的体验
- 一打开网页就看到一个 8x8 左右的小世界
- 鼠标点格子放东西（草地、土路、水、石头、树、房子、擦除）
- 拖拽转视角、滚轮缩放
- 鼠标悬停的格子要有视觉反馈
- 关闭网页，下次打开还在
- 能切换 3 个不同的存档世界
- 重置按钮能程序化生成一个随机小村庄
- 首次打开有个操作提示，几秒后自动淡出

## 技术约束
- 单页面，零构建：直接双击 HTML 就能打开
- Three.js 用 CDN 引入（r128），不要 npm
- 所有 3D 物体用内置几何体拼（Box、Cone、Cylinder等）

## 视觉方向
- "积木玩具"风：颜色饱和、对比明确
- 背景奶油色，光照要"日光"感
- 阴影要柔，不要硬切

## UI 风格
- 顶部标题面板 + 存档控制
- 底部工具栏（emoji 图标 + 中文标签）
- 右下小地图（canvas 2D）
- 全部磨砂玻璃风格（半透明 + 模糊）
```

AI 在一轮对话中直接生成了完整的 HTML、CSS、JS 三个文件。打开浏览器，一个奶油色背景、积木风格的 3D 世界就出现在眼前——草地、土路、水塘、小房子、树木，全都可以点击放置，操作流畅。

## 二、PM → 设计师 → 工程师：OPC 工作流复现

如果你还记得上篇文章的 OPC 七个角色，你会发现这次开发完美复现了其中三个核心角色的协作：

**作为 PM**，我定义的是体验目标："摆在桌子上的小模型"。这个定位很关键——它排除了"开放世界游戏"的复杂度，限定了范围：8x8 就够了，不需要无限地图，不需要复杂的物理引擎。需求的边界越清晰，AI 产出的质量就越可控。

**作为设计师**，我定义的是视觉方向："积木玩具"风、奶油色背景、磨砂玻璃 UI、日光感光照。这些描述看起来是"感觉型"的，但对 AI 来说，它们是具体的参数约束——饱和色对应高饱和度颜色值，日光感对应方向光而非环境光，磨砂玻璃对应 CSS 的 backdrop-filter: blur()。

**作为工程师**，我定义的是技术约束：零构建、Three.js r128、IIFE 代码组织、数据走唯一入口 setCell。这些约束让 AI 从一开始就在正确的轨道上编码，不会引入 React、Vue 等不必要的依赖，也不会把代码写成难以维护的一团。

你看，**一个人 + 一段 prompt = 三个角色同时在线**。这就是 OPC 在实践中的样子。

## 三、复杂 Prompt 的分割艺术

这次实践中，我体会最深的一个方法论是——**复杂 prompt 的逻辑分割**。

很多人写 prompt 容易犯一个错：把所有需求混在一起，想到哪写到哪。结果 AI 生成的代码要么遗漏关键功能，要么架构混乱难以修改。

我的做法是把 prompt 切分成五个逻辑块：

1. **体验目标**：用户打开网页后能做什么（操作流程）
2. **技术约束**：不能用什么、必须用什么（技术边界）
3. **视觉方向**：整体风格和观感（美学指南）
4. **UI 风格**：界面组件的具体样式（交互设计）
5. **代码组织**：数据结构和架构约定（工程规范）

每个块只回答一个问题，彼此独立。这样 AI 在处理时，不会把"按钮长什么样"和"数据存在哪"混在一起思考。

这和上篇文章里吴恩达的 **Goal + Input + Output + Layout + Features** 模式本质上是同一个道理：**给 AI 一个结构化的框架，而不是一段模糊的描述。**

结构化 prompt 和模糊 prompt 的区别，就像是建筑设计图和随手涂鸦的区别——前者能盖起大楼，后者只能有个轮廓。

## 四、从 AIGC 到 LLM：理解你正在对话的东西

到这里，我们一直在聊"怎么用 AI"。但我越来越觉得，**理解 AI 本身的工作原理**，才是用好 AI 的关键。

你可能经常看到这些词：LLM、大模型、千亿参数、万亿参数。它们到底是什么意思？

**LLM（Large Language Model，大语言模型）**，本质上是一个在海量数据上训练出来的超大神经网络（DNN, Deep Neural Network）。它通过学习互联网级别的文本数据，获得了语义理解（NLP）、逻辑推理和内容生成的能力。

如果用一句话概括它的工作方式：

> **y = fθ(x)**

- **x** 是你输入的 prompt
- **f** 是一个极其复杂的预训练函数
- **θ**（西塔）是模型全部的参数——也就是"权重"
- **y** 是神经网络运算之后输出的结果

这里的 **θ** 就是衡量模型规模的关键。主流大模型的参数在 **Billion（十亿）** 级别，也就是百亿到千亿。而 DeepSeek-v4-Pro 达到了 **1.6T（万亿）** 级别，DeepSeek-v4-Flash 也有 **158B（千亿）**。

1.6T 是什么概念？如果每个参数用一个字节存储，1.6T 个参数就是 1.6TB——这还只是参数本身，不算运行所需的计算资源。

理解这个公式的意义在于：**当你写 prompt 的时候，你是在引导一个万亿参数的超级函数。** prompt 的每一个词，都在影响这个函数的计算路径。这就是为什么 prompt 工程如此重要——你是在"编程"一个万亿参数的系统，只是用的编程语言是自然语言。

## 五、代码向后，业务向前

最后一个让我感触很深的认知是这四个字：**代码向后，业务向前**。

什么意思呢？

在过去，程序员的日常是写代码——从零开始实现功能、逐行调试、手动优化。代码是我们工作的核心。

但在 AI 时代，**代码的主力变成了 LLM**。从 3D 世界编辑器的经历可以看到：AI 写了全部的前端代码——Three.js 场景搭建、物体工厂、交互系统、数据持久化、小地图渲染、程序化生成算法，全部由 AI 完成。

那程序员做什么？

做**代码之外的事**：定义体验目标、设计视觉风格、设定技术约束、理解业务场景、验证输出质量。

换句话说，**写代码的门槛在降低，但理解业务和定义问题的门槛在升高**。

这也是为什么我需要理解 LLM 的原理——不是因为我要训练模型，而是因为只有理解了 y = fθ(x) 这个框架，我才能更精准地设计我的 x（prompt），从而得到更好的 y（输出）。

还有一个更深层的点：**领域知识仍然是护城河。**

在这个 3D 项目中，如果我不懂 Three.js 的基本概念（场景、相机、渲染器、几何体、材质、光照、阴影、射线检测），我连 prompt 都不知道该怎么写——我无法描述技术约束，无法判断 AI 生成的代码是否合理，无法在 AI 跑偏时引导它回到正轨。

所以 AI 并没有让领域知识变得无用，反而让它变得更珍贵——**AI 是你的代码主力，但你是 AI 的架构师。**

## 结语：Be AI Native

写这篇文章的时候，我正在整理我的学习笔记。我注意到笔记的开头写着四个字：**Be AI Native**。

什么叫 AI Native？不是会用几个 AI 工具就完了。而是：

- 以 **AI 为核心思想**——在做任何技术决策时，优先考虑 AI 能做什么
- 以 **AI 为核心工具**——把 AI 嵌入到开发流程的每一个环节
- 以 **AI 为生产力**——用 AI 将个人产出放大一个数量级

从 OPC 的概念框架，到 3D 小世界的实践落地，再到 LLM 的原理理解，最后到"代码向后，业务向前"的方法论觉悟——这就是我理解的 AI Native 之路。

这条路还很长，但方向很清晰。**从"写代码的人"到"用 AI 创造产品的人"，这中间只差一个思维转变。**

希望你也能早点上车。
