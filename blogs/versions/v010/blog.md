# 从 API 到 Agent 实战：一个 AI Native 开发者的 Hermes Agent 初体验

## 引言

v009，我从代码层面理解了 Agent 的"发动机"——`client.chat.completions.create()` 一行代码，调通了 Python 和 LLM API 的最后一公里。那天的认知是：Agent 的本质就是多轮 API 调用 + 工具编排。

今天，v010，我第一次真正和一个完整的 AI Agent 系统**深度对话**。

不是用 Claude Code 写代码，不是在 NoteBook 里调 API，而是**和 Agent 本身聊天**——问它是什么、看它能做什么、试它的边界、理解它的架构。主角是 **Hermes Agent**，一个由 Nous Research 出品的开源 AI Agent 框架。

这篇文章聊三个东西：① Agent 的多平台架构——一个"大脑"如何连接多个"触手" ② Agent 的资源管理——Token 消耗、记忆、技能 ③ Agent 的局限性——它做不到什么，以及为什么了解边界比了解能力更重要。

比前九篇更"实战"，因为我不是在学概念，而是在用一个真实系统。

## 一、Hermes Agent：一个开源 AI Agent 的全貌

Hermes Agent 是什么？

一句话：**一个能跑在你电脑上、能连接多个聊天平台、能记住你、能学习的 AI 助手。**

和 Claude Code（v003）相比，Hermes 的定位更广。Claude Code 是一个编码 Agent——你给它代码任务，它帮你执行。Hermes 是一个**通用 Agent**——你可以和它聊天、让它写代码、管理文件、搜索信息、截图、操作浏览器，甚至定时执行任务。

核心特性：

- **20+ LLM 提供商支持**：OpenRouter、Anthropic、OpenAI、DeepSeek、小米 MiMo……换模型只需要改一行配置
- **多平台网关**：同一个 Agent 可以跑在微信、Telegram、Discord、Slack、WhatsApp、邮件……你在哪个平台和它聊天都行
- **持久记忆**：跨会话记住你是谁、你的偏好、你的工作环境
- **技能系统**：从经验中学习，把解决方案保存为可复用的"技能文档"

这四点，每一点都对应了前九篇文章的一个主题：

- 多提供商 → v009 的"Python 调 API"，但更灵活——不是绑定一个模型，而是随时切换
- 多平台 → v004 的"CLI 工作流"，但更广——不只是终端，还有微信、浏览器
- 持久记忆 → v002 的"Prompt 设计"，但更持久——不是一次性的指令，而是跨会话的知识积累
- 技能系统 → v006 的"模块化"，但更智能——不是手动拆分模块，而是 Agent 自己学会并保存

v003 说 Agent 是"AI 帮你干活的工具"。今天的认知升级了：**Hermes 不只是工具，它是一个能学习、能记忆、能跨平台存在的"数字伙伴"。**

## 二、多平台网关：Agent 的"触手"

Hermes 最让我惊讶的设计是**多平台网关**。

什么意思？同一个 Agent "大脑"，可以通过不同的"触手"和你交互：

- **终端 CLI**：在命令行里直接对话，最轻量
- **WebUI**：浏览器里打开图形界面，支持 Markdown 渲染、图片预览
- **微信**：直接在微信里聊天，Agent 在后台回复
- **Telegram / Discord / Slack**：团队协作平台也能用

这些入口共享同一个 Agent 实例、同一套记忆、同一套技能。你在微信上告诉它"我喜欢简洁的回复"，下次在 Telegram 上它也会记住。

但这个架构有一个关键依赖：**你的电脑必须开着。**

网关运行在你的电脑上，它就像一个"服务器"——微信消息进来，网关转发给 Agent，Agent 处理后回复，网关再转发回微信。电脑关机 = 网关停了 = 所有平台都联系不上 Agent。

这让我想到 v001 OPC 的"一人公司"概念。一人公司的 AI 助手需要 24 小时在线——客户在微信上问问题，Agent 不能说"我电脑关了，明天再回你"。所以真正的部署方案是：

- **云服务器**：租一台便宜的 Linux VPS，把 Hermes 装上去
- **树莓派**：家里放一个小主机，24 小时运行
- **系统服务**：`hermes gateway install` 把网关安装为系统服务，开机自启

v004 聊 CLI 工作流时，我说"CLI 缩短了想法到执行的路径"。今天加一句：**多平台网关缩短了你到 Agent 的距离**——不管你在哪，不管用什么设备，都能找到你的 Agent。

## 三、Token 消耗：Agent 的"燃料表"

和 Agent 聊天不是免费的。

每一次对话，Agent 都要把你的消息、系统提示、技能内容、对话历史一起发给 LLM。LLM 处理这些文本需要计算资源，计算资源按 **Token** 计费。

今天的会话数据：

| 类型 | Token 数 | 说明 |
|------|---------|------|
| 输入 Token | 55,555 | 你发的消息 + 系统提示 + 技能 + 历史 |
| 输出 Token | 5,781 | Agent 的回复 |
| 缓存读取 | 1,021,440 | 重复内容的缓存（通常有折扣） |

为什么输入比输出多 **10 倍**？

因为系统提示（System Prompt）很长。它包含了 Agent 的人格定义、所有可用技能的描述、环境信息（你的操作系统、工作目录、可用工具）、记忆内容……每次对话都要发送一遍。

这让我想起 v005 Git 的版本管理。Git 管理的是代码的变化历史，Token 管理的是"认知成本"——每次对话，Agent 都要"回忆"一遍所有上下文，这个"回忆"是有成本的。

缓存机制是优化手段。系统提示、技能列表这些不变的内容会被缓存，下次对话时直接读取缓存，不需要重新计算。1,021,440 的缓存读取 Token，如果按正常价格算会很贵，但缓存价格通常是原价的 1/10 甚至更低。

**成本意识**是 AI Native 开发者的必修课。用 Agent 做事很方便，但每次调用都有成本。优化 Prompt 长度、合理使用缓存、选择合适的模型——这些都是实际工程中需要考虑的问题。

v008 说"能跑"和"好用"之间隔着整个工程化思维。Token 管理就是其中一面：**能让 Agent 跑起来是第一步，让 Agent 跑得经济是第二步。**

## 四、记忆与技能：Agent 的"长期记忆"

Hermes 有两种"记忆"机制。

### 持久记忆（Memory）

Agent 会记住跨会话的信息。比如：

- "用户偏好中文交流"
- "Hermes WebUI 安装在 C:\Users\Lenovo\hermes-webui"
- "E 盘的 WROKSPACE 文件夹拼写是 WROKSPACE 不是 WORKSPACE"

这些信息存储在 `~/.hermes/memory.json`，每次对话自动注入到系统提示里。你不需要每次都告诉 Agent "我是谁"、"我在哪"——它已经记住了。

对比 v002 的 Prompt 设计。Prompt 是**一次性指令**——你写一次，用一次，下次还得重新写。Memory 是**持久知识**——写一次，永远记住，自动加载。

### 技能系统（Skills）

技能是 Agent 从经验中学习的产物。

当 Agent 解决了一个复杂问题、发现了一个工作流程、或者被用户纠正了，它可以把这些知识保存为"技能文档"。下次遇到类似问题，直接加载技能，不需要重新探索。

比如今天的会话中，Agent 发现了：
- Windows 环境下浏览器自动化有兼容性问题
- 网关需要安装为系统服务才能开机自启
- PowerShell 可以用来截图

这些发现可以保存为技能，下次遇到同样问题时直接调用。

v006 聊模块化时说"每一个模块都是可复用的代码单元"。技能就是 Agent 的"模块化知识"——每一个技能都是可复用的解决方案。

**记忆是 Agent 的"事实记忆"**（你是谁、你在哪），**技能是 Agent 的"程序记忆"**（怎么做某件事）。两者结合，让 Agent 越用越聪明。

## 五、浏览器自动化：Agent 的"眼睛"与局限

今天的会话中，我尝试让 Agent 用 Edge 浏览器打开稀土掘金（juejin.cn），查看我的作品数据。

结果：**失败了。**

Agent 尝试了多种方法：
1. 直接调用 `browser_navigate` → Chrome 启动失败
2. 设置环境变量 `CHROME_PATH` → 仍然失败
3. 添加 `--no-sandbox` 参数 → 工具不支持

失败原因：**Windows 环境的浏览器自动化兼容性问题**。Hermes 的浏览器工具底层依赖 Chrome DevTools Protocol，在 Linux 和 macOS 上工作良好，但在 Windows 上遇到了路径检测、权限、启动参数等问题。

这次失败教会了我三件事：

**第一，Agent 不是万能的。** 它受限于操作系统、权限、工具链。在 Linux 上一行命令搞定的事，在 Windows 上可能需要折腾半天。这不是 Agent 的错，是环境的差异。

**第二，了解边界比了解能力更重要。** 知道 Agent 能做什么（写代码、管理文件、搜索信息）是基本功，知道 Agent **不能**做什么（在某些 Windows 环境下自动化浏览器）才是实战经验。

**第三，人机协作是必然的。** Agent 做不到的事，人来补充。浏览器打不开？我自己打开，截图发给 Agent 分析。Agent 分析截图的能力很强——它能识别界面元素、读取文字、理解布局。

成功的部分也值得一提：
- 文件系统访问 ✅：Agent 能读取 E 盘的 WROKSPACE 文件夹
- 终端命令执行 ✅：Agent 能运行 PowerShell、bash 命令
- 截图功能 ✅：通过 PowerShell 调用 .NET 实现全屏截图

v007 聊 FDE 时说"FDE 需要根据业务场景选择技术栈"。浏览器自动化失败就是活生生的例子——不是所有技术在所有环境下都能用，**选择可行的技术方案比选择最先进的技术方案更重要。**

## 六、从使用者到理解者：认知跃迁

回顾十篇文章，我的 Agent 认知经历了三个阶段：

**阶段一：用 Agent（v003-v004）**
"Claude Code 帮我搭落地页，CLI 帮我执行命令。" 这个阶段，Agent 是一个黑箱——你给指令，它给结果，中间发生了什么，你不清楚。

**阶段二：理解 Agent 的底层（v009）**
"Agent 的本质是 LLM API 调用。" 这个阶段，你打开了黑箱，看到了发动机——`client.chat.completions.create()` 是核心，Prompt 质量决定输出质量。

**阶段三：和 Agent 系统交互（v010）**
"Agent 是一个可配置的系统，有架构、有成本、有边界。" 这个阶段，你不只是用 Agent，而是理解它怎么运行、消耗多少资源、在什么场景下会失败。

这三个阶段的递进，对应了三种不同的工程能力：

| 阶段 | 认知 | 工程能力 |
|------|------|---------|
| 用 Agent | "AI 帮我做事" | 会用工具 |
| 理解底层 | "AI 的发动机是 API" | 会调工具 |
| 系统交互 | "AI 是可配置的系统" | 会管工具 |

FDE（v007）需要的正是第三种能力——不只是用 Agent，而是**管理 Agent**：评估能力边界、计算使用成本、设计人机协作的工作流、处理失败情况。

v001 说一人公司的第一步是找到正确的工具和工具。今天补上后半句：**找到工具之后，要理解工具的边界。** 一个不知道 Agent 局限性的人，会在关键时刻失望；一个了解局限性的人，会提前准备 Plan B。

## 结语

今天学到的不只是 Hermes Agent 怎么用。是三件事：

**第一，Agent 是可配置的系统，不是黑箱。** 它有架构（网关、CLI、WebUI）、有资源管理（Token、记忆、技能）、有边界（操作系统兼容性、权限限制）。

**第二，多平台网关让 Agent 无处不在。** 微信、终端、浏览器——你在哪，Agent 就在哪。但前提是 Agent 所在的机器要一直运行。

**第三，了解边界才能用好工具。** 浏览器自动化失败了，但文件操作、截图、命令执行都成功了。知道什么能做、什么不能做，才能做出正确的技术决策。

回顾十篇文章的完整路径：

- v001-v004：AI 工具链（OPC → Prompt → Agent → CLI）
- v005-v006：工程基本功（Git → 模块化）
- v007：业务视角（FDE）
- v008-v009：编程基本功 + 语言扩展（数组去重 → Python + API）
- **v010：Agent 实战（架构、成本、边界）**

两条线在这里交汇了：一条是理论（v009 的 API 调用），一条是实战（v010 的 Agent 系统交互）。理论让你知道 Agent 是什么，实战让你知道 Agent 能做什么、不能做什么。

AI Native 开发者的下一步，不是学更多 API，而是**在真实环境中和 Agent 协作**——用它、踩坑、总结、再用。
