## 一、Benchmark 是什么

### 1.1 一句话定义

笔记原话：

> benchmark 是用标准题目给大模型打分的体系  
> benchmark 是 llm 在一系列测试中的得分集合（多维，可测）

拆开看：

```text
标准题目  →  大家考同一张卷，结果可横向对比
打分体系  →  不是主观「感觉好用」，而是可复现指标
得分集合  →  不是一个总分，而是多维成绩单
```

### 1.2 为什么需要它

大模型太大、太多，能力又多维。没有公共尺子，就只剩：

```text
官网文案
KOL 体感
自家 Demo 截图
```

笔记的类比很贴切：

> 给一堆测试标准题目，让 AI 模型去打分，模型的高考，考完了会出一个分数。

高考比喻的价值在于三点：

```text
1. 可比：同一套规则
2. 可测：不是玄学
3. 有限：高考高分 ≠ 人生全面最强
```

第三点最重要——**benchmark 测的是「在这些题上的表现」，不是「在你业务上的表现」。**

### 1.3 最小心智模型

```text
Benchmark
  = 多张标准试卷
  + 统一评分方式
  + 可公开对比的分数集合

它回答：
  这个模型在知识 / 推理 / 代码 / 数学 / 中文等维度大概站在哪

它不回答：
  你的客服场景会不会翻车
  你的成本是否划算
  你的延迟能不能接受
```

## 二、常见测试集：多维能力的几张卷

LLM 能力是多维的，所以没有「一张卷定终身」。笔记列出的几套核心试卷，建议按「考什么」来记，而不是只背缩写。

### 2.1 MMLU：综合知识广度

```text
MMLU
  Massive Multitask Language Understanding
  大规模多任务语言理解
```

特征：

```text
- 约 57 个学科领域选择题
- 考知识广度
- 相当于「文理综合卷」
```

适合回答：

```text
模型是不是「书读得够多」
常识、学科知识覆盖是否扎实
```

不适合单独回答：

```text
会不会真正推理
会不会修真实代码仓库
```

### 2.2 GPQA Diamond：顶级推理，而且 Google-Proof

```text
GPQA Diamond
  Graduate-Level Google-Proof Q & A
  研究生级、搜不到答案的问答
```

考什么：

```text
物理 / 化学 / 生物等研究生级别难题
重点不是背，而是推
```

为什么叫 **Google-Proof**：

> 这些题目就算你上网搜也很难找到答案。  
> 考的是模型是不是真正能推理，而不是去背答案。

这是读分时很关键的过滤器：

```text
能搜到的题 → 容易混进「记忆 / 污染」成分
搜不到的题 → 更接近真实推理能力
```

### 2.3 HumanEval 与 SWE-bench：代码能力的两套卷

笔记把它们写成「两套试卷」：

```text
HumanEval
  164 道编程题
  让模型写出能跑通的代码
  更像算法/函数级编程考试

SWE-bench
  让模型去修真实 GitHub 项目里的 bug
  更像工程现场
```

对照：

| 测试 | 场景像什么 | 更偏什么能力 |
|------|------------|--------------|
| HumanEval | 独立小函数写对 | 代码生成正确性 |
| SWE-bench | 真实仓库修 bug | 定位、改动、工程上下文 |

所以看到「代码 SOTA」时，要追问：

```text
是 HumanEval 高，还是 SWE-bench 高？
会写小函数 ≠ 会在大仓库里稳妥改代码
```

### 2.4 MATH / AIME：数学推理

```text
MATH / AIME
  竞赛级数学题
  AIME 是美国数学竞赛的高级别
  需要多步数学推理
```

它测的不是「会不会算个税」，而是：

```text
符号操作
多步推导
中间别跑偏
```

### 2.5 C-Eval：中文能力

笔记写作 `C-Eavl`，行业通行名一般为 **C-Eval**：

```text
C-Eval
  专门针对中文语境
  覆盖约 52 个学科、多种难度
  和训练语料中的中文质量强相关
```

对国内业务尤其关键：

```text
英文榜第一，不代表中文业务体验第一
中文指令遵循、术语、阅读理解要单独看
```

### 2.6 一张多维成绩单

把上面收成「体检分项」：

```text
MMLU          → 知识广度
GPQA          → 硬推理（抗检索捷径）
HumanEval     → 函数级代码
SWE-bench     → 仓库级工程代码
MATH / AIME   → 数学推理
C-Eval        → 中文能力
```

**没有单项能代表全部。**  
读模型卡时，至少扫三列：知识、推理、和你业务最相关的那一列（代码 / 数学 / 中文）。

## 三、厂商怎么用 benchmark

### 3.1 发布会话术的标准动作

笔记写得很直白：

> 每次模型发布，会拿出一堆的 benchmark 来说自己特别强。  
> 厂商会挑表现好的几项去重点放大。

典型路径：

```text
1. 跑一圈公开榜
2. 挑自己领先的 2–4 项做成大图
3. 标题写成「全面领先 / 最强 / SOTA」
4. 弱项放在附录、脚注或干脆不提
```

这不一定是造假，但一定是**叙事选择**。

### 3.2 「第一」到底第一在哪

笔记结论：

> 模型在 xx 上说第一，不代表整体最强。  
> 可能只是在某一项考试里面拿了最高分。

翻译成工程师语言：

```text
「编码第一」可能是 HumanEval
「推理第一」可能是 GPQA
「综合第一」可能是某家自定义加权总分
```

你要问的不是：

```text
谁第一？
```

而是：

```text
第一的那张卷，和我的任务同构吗？
```

### 3.3 读榜时的三个防坑问题

```text
1. 测的是哪张卷？版本是否一致？
2. 是否允许工具 / 联网 / 多数投票等额外加成？
3. 和我的场景是否同分布？（客服、代码、检索、中文……）
```

同一名字的 benchmark，评测协议稍微一变，分数就能差一截。  
**没有协议细节的分数，参考价值要打折。**

## 四、正确用法：门槛，不是排名

### 4.1 笔记的核心判断

> Benchmark 是一个门槛，不是排名。  
> 一个模型连 benchmark 都差，大概率能力也差（门槛）。  
> 要看多个维度，不是单一分数。  
> 要看具体业务，以及实际效果。

这句话可以拆成四层决策：

```text
1. 门槛过滤
   关键项太差 → 直接淘汰
   （连标准题都差，业务上大概率更差）

2. 多维对照
   至少看知识 + 推理 + 你的关键能力维

3. 业务对齐
   代码团队看 HumanEval / SWE-bench
   中文产品看 C-Eval 与中文真实对话
   研究分析看 GPQA / 长链路推理体感

4. 真实验收
   用你的数据、你的工具、你的延迟与成本预算复测
```

### 4.2 一个可执行的选型漏斗

```text
公开 benchmark（粗筛）
  → 多维都不至于「明显拉胯」
  → 进入候选池

场景小样本评测（细筛）
  → 20–100 条真实任务
  → 人工或规则打分

在线 / 灰度（终筛）
  → 延迟、成本、稳定性、安全
  → 业务指标说话
```

benchmark 负责**把明显不行的挡在门外**；  
真正拍板的，永远是**你的任务分布上的表现**。

### 4.3 和「体感」如何共存

体感有用，但不该单独上场：

```text
只有体感 → 容易被一两个漂亮回答骗到
只有榜单 → 容易选到「考试强、干活一般」的模型
榜单 + 场景评测 + 成本延迟 → 可工程化决策
```

## 五、可直接复用的实践清单

### 5.1 读模型发布稿时

```text
[ ] 先列出它强调的 3 个 benchmark 名称
[ ] 分别翻译成：知识 / 推理 / 代码 / 数学 / 中文？
[ ] 追问评测是否含工具、联网、多次采样
[ ] 找到它没强调的弱项维度
[ ] 问一句：这些卷和我的业务同构吗？
```

### 5.2 团队内建立「最小成绩单」

```text
候选模型 A / B / C
  MMLU：
  GPQA：
  代码相关（HumanEval 或 SWE-bench）：
  中文相关（C-Eval 或内部中文集）：
  内部 30 题业务集：
  单价 / 延迟：
```

### 5.3 给业务同学的一句话解释

```text
Benchmark 像体检报告：
单项高不代表全面健康，
单项太低通常说明真有问题，
最后能不能上岗，还得看实际工作表现。
```

## 六、面试高频问题与答题框架

### 6.1 什么是 LLM Benchmark？

**回答框架：**

> LLM Benchmark 是用一套标准题目和统一评分方式，衡量大模型在特定能力维度上表现的评测体系。它输出的是可横向比较的多维分数集合，而不是单一的「好/不好」。常见维度包括综合知识、硬推理、代码、数学、中文等。

### 6.2 为什么需要多个 benchmark，而不是一个总分？

**回答框架：**

> 大模型能力是多维的。MMLU 更偏知识广度，GPQA 更偏抗捷径的推理，HumanEval 与 SWE-bench 分别偏函数级与仓库级代码，MATH/AIME 偏数学，C-Eval 偏中文。一个总分会掩盖短板，也便于厂商只放大优势项。工程选型应看与任务相关的分项。

### 6.3 GPQA 为什么强调 Google-Proof？

**回答框架：**

> Google-Proof 指题目很难靠搜索直接找到答案，从而降低「靠记忆网页或训练集捷径得分」的可能，更接近考察真实推理。若题目可轻易检索到，高分可能混有记忆成分，推理结论要谨慎。

### 6.4 HumanEval 高是否等于编码最强？

**回答框架：**

> 不一定。HumanEval 主要测独立编程题/函数级正确性；SWE-bench 更接近真实仓库修 bug。会写小函数不等于能在复杂项目上下文中定位与修改。要看业务是算法题生成，还是工程改仓。

### 6.5 厂商宣传「多项第一」时如何理性看？

**回答框架：**

> 先确认具体榜单、版本与评测协议，再判断这些项是否覆盖自己的关键能力。厂商会优先展示优势分项，「某项第一」不等于整体最强。Benchmark 应用作门槛过滤和多维对照，最终仍要用业务数据与成本延迟做验收。

### 6.6 如果只能记一句选型原则，是什么？

**回答框架：**

> Benchmark 是门槛，不是排名：连标准题都差的模型大概率不可用；但标准题高，只代表「具备基础资格」，不代表在你的业务、中文场景、成本约束下最优。

## 结语

第四十四天的 benchmark 笔记不长，但补上了 AI 工程里极容易被营销带偏的一层公共语言：

```text
1. Benchmark = 标准题打分体系（多维、可测）
2. 不同试卷考不同能力
   知识 / 推理 / 代码 / 数学 / 中文
3. 厂商会放大优势分项
   「第一」要还原成「哪一张卷第一」
4. 正确用法
   门槛过滤 + 多维对照 + 业务实测
```

把它和相邻文章排成一条线：

```text
v045：模型怎么生成（采样参数）
v047：系统怎么编排（Workflow / Agent）
v051（本篇）：模型怎么被衡量（Benchmark）
v052：新模型发布后怎么分层使用（GPT-5.6）
```

如果只带走一个检查清单：

```text
看见「第一」 → 问是哪张卷
看见高分   → 问和我的任务同构吗
看见弱项   → 当门槛，慎重入选
最终拍板 → 业务集 + 成本 + 延迟
```
