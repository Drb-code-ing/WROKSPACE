# 大模型怎么随机说话：Temperature、Top-K 与 LangChain 工作流初探

## 引言

之前的文章一直在讨论"如何调用大模型"：v039 拆解流式输出协议，v043 补齐 BFF 层架构，v044 把整个模型塞进浏览器。但有一个更底层的参数问题，我们始终没有正面回答：

> **大模型每次回答同一个问题，结果为什么不一样？这个"不一样"到底有多不一样？作为开发者，我能不能精确控制它？**

第四十一天的学习从一个非常朴素的起点出发——大模型本质是什么？它是怎么"说话"的？然后引出两个控制随机性的核心参数：**Temperature** 和 **Top-K**。最后用 LangChain 的 Chain 概念，把"调参"变成"设计 AI 工作流"。

本文基于 `ai/temperature/readme.md` 和 `ai/temperature/t-demo/main.mjs` 的实践，从"下一个词预测"的概率本质讲起，到 LangChain 工作流编排，把这两个参数的设计哲学和工程权衡彻底拆开。

---

## 一、LLM 说什么话，不是"选择"而是"抽样"

很多人对大模型有一个直觉误解：模型"想好了"要说什么，然后一个字一个字往外说。

实际情况更接近：

```text
给定前文（prompt + 已生成内容）
        ↓
模型输出一个概率分布（词表里每个词都有一个概率）
        ↓
从这个概率分布中抽样一个词
        ↓
把这个词拼到末尾，重复以上过程
```

举个例子。输入"你好"，模型输出的概率分布可能是：

```text
吗  0.60    ← 概率最高，"你好吗"是最自然的接续
啊  0.15
呀  0.10
美  0.05
坏  0.01
... （词表里还有几万个候选，概率接近 0）
```

关键认知在于：

> **LLM 不"决定"下一个词，它输出一个候选池和每个候选的权重。最终选出哪个词，是由采样策略决定的。**

这个采样策略就是 Temperature 和 Top-K 的主场。

### 1.1 这跟传统编程的差别在哪

传统编程：

```text
输入 → 确定性的计算逻辑 → 确定的输出

function greet(name) {
  return `你好，${name}`
}
greet('小明')  // 永远是"你好，小明"
```

LLM 编程：

```text
输入 → 概率分布 → 采样 → 输出

同样的 prompt，两次调用可能返回不同的内容
```

这不是 bug，是 feature。但"多不一样"应该由开发者说了算，而不是由运气说了算。

## 二、Temperature：控制概率分布的"陡峭程度"

Temperature 不是某种玄学参数，它有一个严谨的数学直觉：

```text
模型输出一组 logits（原始分数）
         ↓
除以 Temperature
         ↓
过 softmax 转成概率
         ↓
按概率抽样
```

### 2.1 直觉比公式重要

把词表想象成一个"受欢迎程度排行榜"：

```text
原始票数：
  吗 60票  ████████████████████████████████
  啊 15票  ████████
  呀 10票  █████
  美  5票  ██
  坏  1票  █
```

**Temperature = 0.2（低）：**

对所有候选做了一次"票数放大"——高票的变得更高，低票的变得更低：

```text
  吗 → 几乎确定被选中
  啊 → 几乎不可能
  坏 → 绝对不可能
```

结果：模型非常"听话"，几乎总是选概率最高的词。适合写代码、法律条款、合同、数学推理。

**Temperature = 0.8（高）：**

对所有候选做了一次"票数拉平"——高票的和低票的差距缩小：

```text
  吗 → 大概率，但不一定
  啊 → 有不小的概率
  坏 → 虽然概率低，但偶尔会被选中
```

结果：模型更有"创造力"，偶尔冒出不那么常规的词。适合写散文、诗歌、创意文案、AI 漫剧。

### 2.2 极端不是目的，找到业务的合适区间才是

| Temperature | 行为 | 风险 | 适合场景 |
|---|---|---|---|
| 0.0 ~ 0.3 | 高度确定，接近贪心 | 可能过于刻板、重复 | 代码生成、法律文书、数学 |
| 0.3 ~ 0.7 | 平衡 | — | 通用对话、客服、问答 |
| 0.7 ~ 1.0 | 创造性增强 | 幻觉增多、逻辑松散 | 创意写作、头脑风暴、多模态生成 |

> 把 Temperature 拉高会增加随机性，让生成看起来"不太靠谱"；但有些创作类场景需要这种随机性来激发创意。问题不是"选哪个"，而是**如何保证创意质量**。

## 三、Top-K：先画圈，再跳舞

Temperature 解决的是"候选之间差距多大"，但它不限制候选范围。即使 Temperature = 0.2，"坏"虽然概率被压得很低，理论上仍有一丝可能被选中——这在严谨场景下就是风险。

Top-K 的思路完全不同：**先划定一个范围，只允许在这个范围内抽样**。

### 3.1 工作原理

```text
全词表（几万个候选）
        ↓
按概率从高到低排序
        ↓
只保留前 K 个
  例：K=4  →  吗 0.60, 啊 0.15, 呀 0.10, 美 0.05
             →  坏 0.01 及以下被直接丢弃
        ↓
在 K 个候选中，按原概率比例 + Temperature 调整后抽样
```

**Top-K = K 越大，模型"眼界"越宽，但也越容易跑偏。**

### 3.2 两个参数的正确组合方式

实践中不会只用 Temperature 或只用 Top-K，而是配合使用。配合的核心原则：

```text
先 Top-K：圈定候选范围（排除明显不靠谱的选项）
再 Temperature：在圈内调整随机性（控制创意 vs 严谨的偏向）
```

几种典型组合：

| Temperature | Top-K | 效果 | 典型应用 |
|---|---|---|---|
| 低 (0.2) | 大 (8) | 准确但信息完整 | 技术文档、代码、法律 |
| 高 (0.8) | 小 (4) | 靠谱的创意 | 创意文案、故事创作 |
| 低 | 小 | 过于保守、可能呆板 | 基本不用 |
| 高 | 大 | 容易胡说八道 | 基本不用，除非探索性实验 |

关键原则：

> **Temperature 和 Top-K 不能都太大或太小。**
>
> - Temperature 低 + Top-K 大 = 比较准确又有信息量
> - Temperature 高 + Top-K 小 = 靠谱的创意性
>
> AI 应用效果不能靠猜，要观测、对比、迭代。

### 3.3 分两步走的工程意义

很多创意类任务希望"有创意但有底线"，比如 AI 漫剧剧本生成：

```text
第一步：Top-K = 4 → 把候选压缩到概率最高的 4 个词
      保证不会出现模型自己都认为概率极低的荒谬选项

第二步：Temperature = 0.8 → 在 4 个词里增加随机性
      避免总是选第一名，给第二名、第三名更多机会
```

这种"先剪枝、后随机"的策略，让开发者在"可控"和"创意"之间找到了一个操作杠杆。

## 四、Hello LangChain：从"调参"到"设计 AI 工作流"

理解了 Temperature 和 Top-K，下一步自然是：怎么在代码里用？

第四十一天的 Demo 选择了 LangChain。但学习笔记对 LangChain 的定位非常务实：不是"学一个新框架"，而是理解它解决什么问题。

### 4.1 LangChain = lang(uage) + chain

名字本身就是定义：

```text
lang(uage) → 语言模型
chain      → 工作链条 / 工作流编排
```

核心模块来自 `@langchain/core`：

| 模块 | 做什么 | 为什么需要 |
|---|---|---|
| `messages` | 对话列表管理 | LLM 每次调用都需要完整历史，需要统一结构 |
| `output_parsers` | 输出解析器 | 模型返回的原始对象有很多字段，Parser 帮你自动提取需要的格式 |
| `tools` | 工具函数 | Agent 需要调用外部能力（搜索、计算、文件） |
| `prompts` | 提示词模板 | 同一套 AI 业务，不同用户只需换参数，模板复用 |

### 4.2 为什么需要 LangChain？

学习笔记里有一个非常诚实的答案：

> 开发更快，业务类。
>
> AI Agent 应用是生成式的、概率分布的，有点黑盒。要让结果"被觉得靠谱"，不能太智能（不知道结果怎么出来），也不能太不智能（结果差）。
>
> Chain 就是把 AI 工作链条上的每个节点链起来——每个节点可控、可替换、可观测。

这个定位跟很多人对 LangChain 的第一印象不同：它不是魔法，它是一套**把黑盒拆成灰盒**的工具。

### 4.3 AI 工作流的直觉：不是调用一次，而是设计一条线

```text
start → PromptTemplate → LLM → StringOutputParser → end
```

之前我们写代码调用 LLM：

```javascript
// 硬编码方式：prompt 和调用逻辑混在一起
const response = await model.invoke('请写一篇散文，主题：秋日山野晚风')
console.log(response.content)
```

这在 Demo 里没问题，但在真实业务里会遇到：

- 同一个"生成文案"逻辑要给不同用户用，每次只是改一个主题，prompt 散落在各处
- 换模型、换输出格式时，需要改所有调用点
- 想要比较"同一个 prompt 在不同参数下效果"时，没有复用的基础设施

LangChain 的 Chain 把这些节点变成可拼装的积木：

```javascript
// 模板：独立管理，可复用
const storyPrompt = PromptTemplate.fromTemplate(`
请写一篇短篇散文，主题：{theme}
风格温柔治愈，篇幅200字左右，不要分段，文字细腻有画面感
`)

// 模型：可替换，参数可配置
const creativeModel = new ChatOpenAI({
  model: 'deepseek-v4-pro',
  temperature: 0.8,
  topK: 4,
})

// 输出解析器：统一返回格式
const outputParser = new StringOutputParser()

// 链：组装
const creativeChain = storyPrompt.pipe(creativeModel).pipe(outputParser)

// 调用：只关心输入
const result = await creativeChain.invoke({ theme: '秋日山野晚风' })
```

### 4.4 为什么复用 PromptTemplate 而不是复用字符串？

很多初学者会写：

```javascript
const prompt = `请写一篇短篇散文，主题：${theme}`
```

这在单个文件里完全可行。但工程层面的问题在于：

- **版本管理**：prompt 需要 A/B 测试和迭代，散落在代码里无法管理
- **变量校验**：模板引擎能检查 `{theme}` 是否被传入，硬编码时传漏了静默生成奇怪内容
- **可观测性**：模板的 `{theme}` 是结构化的，可以做日志、分析哪类输入触发什么行为
- **团队协作**：prompt 工程师和代码工程师可以独立工作，prompt 本身成为可交付的配置

在 Agent 应用中，很多业务本质上是 prompt 驱动的——不同用户走同一套 AI 业务，只需要换身份、换参数。PromptTemplate 让 prompt 变成了**可配置资产**，而不是埋在代码里的魔法字符串。

## 五、Demo 深度解读：一个创意模型和一个严谨模型

第四十一天的 Demo 代码 `main.mjs` 里设置了两套 LLM 配置：

### 5.1 创意性 LLM

```javascript
const creativeModel = new ChatOpenAI({
  model: 'deepseek-v4-pro',
  temperature: 0.8,  // 增强创意的发散性
  topK: 4,           // 仅从概率分布最高的4个词中采样，限制跑偏
  maxTokens: 1024,
})
```

设计思路：

```text
创作需要"意料之外"
  → Temperature: 0.8，概率分布被拉平，第二名第三名有机会
  → 但有底线：Top-K: 4，前四名之外的词直接丢弃
  → 不会出现"模型自己也觉得很不合理的词"
```

### 5.2 严谨性 LLM

```javascript
const preciseModel = new ChatOpenAI({
  model: 'deepseek-v4-pro',
  temperature: 0.2,  // 高度确定，接近贪心
  topK: 8,           // 保证候选池足够大，不因剪枝丢失信息
  maxTokens: 1024,
})
```

设计思路：

```text
严谨场景需要"准确且完整"
  → Temperature: 0.2，几乎总选最高概率的词，输出稳定可预期
  → 但不过度剪枝：Top-K: 8，保证候选多样性
  → 信息不会因为 K 太小而被截断
```

### 5.3 为什么两个模型用同一个 `storyPrompt`？

```javascript
const creativeChain = storyPrompt.pipe(creativeModel).pipe(outputParser)
const preciseChain = storyPrompt.pipe(preciseModel).pipe(outputParser)
```

这恰好展示了 PromptTemplate 的复用价值。同样一段 prompt 模板，换一个模型参数配置，就变成了一条新工作流。你不需要改 prompt、不需要改输出解析——只需要换中间的 LLM 节点。

这个设计的工程意义是：

```text
Prompt 工程师关心：输入什么、期望输出什么
模型工程师关心：用哪个模型、什么参数
Chain 让两者解耦
```

## 六、幻觉问题：为什么参数调对了，模型还是会"编"

学习笔记里提到了"幻觉问题"，但没有展开。这里补一段——因为它和 Temperature / Top-K 直接相关。

### 6.1 幻觉不是"参数设错了"，而是概率模型的固有特性

即使 Temperature = 0、Top-K = 1（绝对贪心），模型也可能"编造事实"。原因是：

```text
模型的训练目标：预测下一个 token，使概率最大化
不等于：说真话，使事实准确性最大化
```

模型在训练数据里见过"秦始皇统一了中国"和"秦始皇发明了电灯"，前者频率远高于后者。但如果你问的是一个冷门话题，训练数据里的正确信息和错误信息可能频率相近甚至颠倒。

对开发者来说，关键不是"消除幻觉"（这是一个研究问题），而是**用正确的工具把幻觉控制在业务可接受范围内**：

```text
Temperature 低 → 输出更"主流"、更接近训练数据里最常见的模式
                 → 对于常见知识，间接降低了幻觉概率
                 → 但不能保证真实性

Top-K 高 → 保留更多候选
          → 对于需要多样化信息来源的任务更友好
          → 但不会自动区分"来源可信"和"来源不可信"

真正的幻觉防线在参数之外：
  - RAG：让模型基于检索到的真实文档回答
  - 事实性校验：用第二个模型验证第一个模型的输出
  - 结构化约束：用 output_parsers 和 tool calling 限制输出形态
```

## 七、从 Demo 到生产：AI 应用随机性控制的工程清单

把第四十一天的学习笔记推到生产场景，需要把"调两个参数"变成一套可操作的方法论。

### 7.1 不要只调参数，要设计观测

```text
❌ 错误方式：
  "感觉这个回答有点死板，把 temperature 调高一点试试"
  
✅ 正确方式：
  1. 定义评估指标（准确性、多样性、用户满意度）
  2. 准备 20~50 条代表性测试用例
  3. 多组参数并行对比
  4. 选择综合最优的，而非"感觉"最好的
```

### 7.2 不同业务场景，不同参数组合

是一个"分业务配置"的起点：

| 场景 | Temperature | Top-K | 理由 |
|---|---|---|---|
| 代码补全 | 0.0~0.2 | 1~3 | 代码需要确定性，不能随机 |
| 技术问答 | 0.2~0.4 | 6~10 | 准确为主，但表达方式可以略有变化 |
| 客服对话 | 0.4~0.7 | 4~8 | 需要自然感但不能离谱 |
| 故事创作 | 0.7~0.9 | 3~5 | 需要创意但不能跑偏 |
| 头脑风暴 | 0.8~1.0 | 6~10 | 发散第一，质量第二 |

### 7.3 同一产品内可以有多组参数

一个 AI 写作助手的不同功能可能用不同的配置：

```text
"写大纲"功能   → Temperature 0.3, Top-K 6   （结构优先）
"扩写段落"功能 → Temperature 0.7, Top-K 4   （创意优先）
"事实核查"功能 → Temperature 0.1, Top-K 3   （准确性优先）
```

### 7.4 `maxTokens` 也是随机性的间接控制

`maxTokens` 不直接影响概率分布，但它限制了"随机错误的累积范围"。一个生成了 2000 token 的回答比一个只生成 100 token 的回答有更多机会"走偏"。这不是替代 Temperature/Top-K 的手段，而是一个需要配合考虑的约束。

## 八、面试高频问题与答题框架

### 8.1 大模型为什么每次回答可能不一样？

**回答框架：**

> LLM 生成文本的本质是从概率分布中抽样。每个位置的输出不是"选最高分"，而是根据模型输出的概率分布随机抽取。即使概率最高的词被选中的可能性最大，第二名、第三名仍有机会。这就是"非确定性生成"。Temperature 和 Top-K 是开发者控制这个随机程度的两个核心参数。

### 8.2 Temperature 和 Top-K 有什么区别？

**回答框架：**

> Temperature 控制概率分布的"陡峭程度"——高 temperature 拉平分布，增加随机性；低 temperature 放大差异，趋向确定性。Top-K 控制候选范围——只保留概率最高的 K 个词，K 以外的直接丢弃。两者配合使用：Top-K 先划定安全边界，Temperature 再在边界内调整随机性。不能两个都设太大或太小。

### 8.3 写代码和写散文，Temperature 应该怎么设？

**回答框架：**

> 写代码追求确定性——逻辑必须正确，不能随机。Temperature 应设低（0.0~0.2），Top-K 可以设中（3~5），保证候选里有足够选项但几乎总选最高分。写散文追求创造力和表达多样性——Temperature 可以设高（0.7~0.9），但 Top-K 应该设小（3~4），防止模型跑偏到离谱的词。核心原则是"低 T 高 K 保准确，高 T 低 K 保创意底线"。

### 8.4 LangChain 的 Chain 概念解决了什么问题？

**回答框架：**

> Chain 把 AI 应用从"一次函数调用"变成"一条可编排的工作流"。Prompt 模板、模型选择、输出解析各自独立，通过 `.pipe()` 连接。好处是：每个节点可替换、可测试、可观测；同一套 prompt 可以换不同模型和参数做 A/B 测试；业务变更时只需替换链上的某个节点，不需要重写整个调用逻辑。本质上是把"调 API"升级成了"设计 AI 流水线"。

## 结语

第四十一天的学习从一个大模型最基础的问题出发——它到底怎么"选词"的——然后一步步走到工程层面。

```text
概率分布   →   理解大模型不是"决定"而是"抽样"
Temperature →   控制随机程度
Top-K       →   控制候选范围
配合使用     →   "先剪枝，后随机"的组合策略
```
