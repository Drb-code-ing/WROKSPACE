# 从模块化到全栈项目：一个 AI Native 开发者的工程化启蒙

## 引言

上篇学完 Git，版本管理有了保障。但很快新问题来了：代码不会丢了，但还是一团乱麻。

AI 帮我生成各种功能，但最终的文件结构越来越乱。一个文件写了一千行，一个函数做了五件事。改了一个地方，另一个地方就崩了。

我开始意识到：**有版本管理只是第一步，怎么组织代码才是更深的学问。**

所以 v006 的主题很自然——**模块化**。

## 一、模块化：写代码的第一条规则

先看笔记里的一句话：

> **一个函数只写一个功能**
> **一个文件只写一个模块/类**
> **一个文件夹只负责一个模块/架构**

这三句话看起来简单，但它是我学编程以来第一次系统性地理解"怎么组织代码"。

在学模块化之前，我的代码风格是"能跑就行"——AI 帮我生成一段代码，我把它扔进一个文件里。如果再加功能，就在同一个文件里继续加。我从来没想过"合不合理"、"好不好改"。

但模块化要求你反过来想：

- **这个函数到底负责什么？** 如果它既做数据计算又做页面渲染，那就拆开。
- **这个文件里放的函数是不是同一类事？** 如果是，放一起；如果不是，拆开。
- **这个文件夹管理的是不是同一个功能？** 整个 users 项目就应该放在一个文件夹里，而不是散落在各个角落。

有一个类比帮我很好理解了这件事：

> 宜家家具的安装手册，每一个螺丝钉都有自己的小袋子。你不会把十个螺丝和一把扳手混在一起装，因为安装的时候你会疯掉。
>
> 代码也是一样。每一个模块就是一个小袋子，里面的东西只服务于一个目的。你找 bug、加功能的时候，只需要打开对应的袋子，而不是翻开整个工具箱。

更妙的是，这个思路和 v001 的 OPC 理念遥相呼应。

OPC 说**一个人可以分饰七个角色**——Boss、PM、设计师、前端、后端、测试、运维。七个角色各司其职，互不干扰。模块化做的就是同一件事：**把不同职责的代码拆分到不同的容器里，让它们各管各的。**

团队分工的思想，最终映射到了代码分工上。

## 二、从"能跑"到"好维护"

AI 编程最大的优势是快。但快有一个副作用：**你很少去审视 AI 生成的代码结构是否合理。**

过去我的工作流是这样的：

1. 向 AI 描述需求
2. AI 生成一段代码，塞进一个文件
3. 复制、粘贴、刷新浏览器——能跑，行！
4. 下一个需求来了，用同样的方式再加一段

这种模式的问题是：代码累积多了，各个功能之间的边界开始模糊。函数 A 里调了函数 B 的数据，函数 B 又依赖了函数 C 的状态。改了一处，另外两处莫名奇妙报错。

**"能跑"和"好维护"之间，隔着一个模块化的距离。**

好维护的代码有两个特征：

1. **可读性**——看代码就能理解逻辑，不需要翻来覆去梳理调用链。
2. **简单可靠**——改一个地方，不需要担心破坏另一个地方。

模块化同时满足这两点：每个模块像一个小黑盒，只要接口不变，内部怎么改都不影响外部。

这和 v002 里的 Prompt 设计逻辑一脉相承。当时我说，写 Prompt 要结构化——分 Goal、Input、Output、Layout、Features。每一块负责一件事，拼接成完整的 Prompt。现在我发现，**写代码也是同样的道理**——分模块、定接口、各自独立，拼接成完整的项目。

从"能跑"到"好维护"，其实就是从"一次性生成"到"可长期演进的工程思维"的转变。

## 三、全栈项目初体验：前后端分离

有了模块化的理论基础，我迎来了第一个真正意义上的"全栈项目"——**users-chat**。

```
users-chat/
├── backend/         # 后端：数据接口
│   ├── db.json      # 数据存储
│   ├── package.json # 项目配置
│   └── node_modules/
└── frontend/        # 前端：用户界面（待建）
```

这个项目结构本身就是一个模块化的实践：**后端管数据，前端管展示。**

当时笔记里写了一个有趣的词：**"古法编程"**。这个词的意思是：前后端分离是传统开发的标准做法，但对于一直靠 AI 生成代码的我来说，第一次在项目里明确分出 backend 和 frontend 两个目录，居然有一种"仪式感"。

### json-server：一行命令开 API

后端用了 json-server——一个能把 JSON 文件变成 REST API 的工具。安装和使用非常简单：

```bash
npm init -y          # 初始化 Node 项目
npm i json-server    # 安装 json-server
```

然后在 `package.json` 的 scripts 里配置：

```json
"dev": "json-server --watch db.json"
```

运行之后，一个 `db.json` 文件就自动变成了 API 接口：

```json
{
  "users": [
    { "id": 1, "name": "廖昊", "hometown": "赣州" },
    { "id": 2, "name": "肖伟彬", "hometown": "赣州" },
    { "id": 3, "name": "戴睿彬", "hometown": "吉安" }
  ]
}
```

访问 `http://localhost:3000/users` 就能拿到完整的用户数据。

这行命令对我的意义很大，因为它让我第一次理解了 **API（Application Interface）** 的概念。笔记里着重标了"接口"两个字——**接口就是两个系统之间的约定**。

之前我听别人说 "调一下接口" 完全没概念。但自己写完 backend，看到 `db.json` 里的用户数据通过 API 暴露出来，理解了：后端写了一个接口，前端通过访问这个地址就能拿到数据——这就是前后端分离的本质。

npm 的初始化也值得一提。`npm init -y` 生成 `package.json`，`npm i json-server` 安装依赖。虽然之前也在用 npm，但系统地理解它作为"Node 包管理器"的角色——管理项目的所有外部依赖——是这次项目才真正建立的认知。

## 四、数据存储：变量会消失，文件不会

在做 users-chat 项目之前，我对"数据"的理解停留在**内存层面**——变量、数组、对象，程序运行完了，数据就没了。

但一个正经的项目需要**长期存储**。笔记里列出了几种层次：

1. **内存存储**（数组/对象）：快，但程序重启就丢。
2. **文件存储**（JSON 文件/CSV/文本）：关机了还在。
3. **数据库**（MySQL 等）：更强大的文件存储系统。

db.json 就是第二层——最轻量的持久化方案。把数据写进 JSON 文件里，服务器重启了，数据还在。这虽然不能替代真实数据库，但作为学习数据持久化的起点，它让我直观地理解了"存"和"取"的关系。

这也呼应了 v005 的 Git 学习——Git 做的是**代码的持久化**，数据存储做的是**业务数据的持久化**。两个放在一起，才是一个完整的工程化视角：

- **代码要存档**（Git）
- **数据也要存档**（数据库/文件存储）

对于一个人 + AI 的开发者来说，理解"持久化"可能是最基本但也最重要的思维转变——**写的东西不会凭空消失，你才能放心地构建复杂系统。**

## 五、Prompt 再进化：加上模块化约束

模块化不只改变了写代码的方式，也改变了写 Prompt 的方式。

之前我写 Prompt 是这样的：

> "帮我做一个用户管理页面，能增删改查用户数据"

AI 生成出来的东西往往是一个大文件，数据获取、页面渲染、事件处理全混在一起。

现在我的 Prompt 会加上一个简单的约束：

> "帮我做一个用户管理页面，按模块化方式组织代码。数据请求放单独的文件，UI 组件拆分，逻辑和数据分离。"

效果立竿见影。AI 生成的代码结构清晰了很多——有专门的 API 层、组件层、工具层。

这不是什么高深的技巧，但它说明了一个趋势：**你对自己的代码有更高的要求，AI 的输出质量也会随之提升。**

回看整个系列的 Prompt 进化史，这条路径非常清晰：

- **v002** 的五块分割法——把 Prompt 拆成 Goal / Input / Output / Layout / Features
- **v003** 的六要素框架——加了 Tech Stack 和 Style，适配更加复杂的项目
- **v006 的模块化约束**——在 Prompt 里加上架构要求，让 AI 生成的代码更有结构

每一次 Prompt 的进化，背后都是工程认知的提升。**你越懂怎么写好的代码，你就越能指挥 AI 写好的代码。**

## 结语：Git + 模块化 = 工程化的第一步

回顾这五天的学习路径，很有意思：

1. **OPC**（认知）——知道一个人 + AI 能干什么
2. **Prompt**（沟通）——知道怎么和 AI 交流
3. **Agent**（工具）——知道怎么用 AI 做项目
4. **CLI**（工作流）——知道怎么让 AI 融入日常
5. **Git**（版本）——知道怎么管代码的历史
6. **模块化**（架构）——知道怎么管代码的结构

六步走完，我从一个"全靠 AI 帮我写"的状态，开始有了自己的工程判断——什么时候该拆模块、数据怎么存、项目结构怎么组织。

这些在传统开发者看来可能是"常识"，但对我来说，是实打实的认知升级。

我越来越相信一件事：**Be AI Native 的路上，基本功不是束缚，而是加速器。**

你懂版本管理，AI 帮你 commit 得更频繁；
你懂模块化，AI 帮你拆得更合理；
你懂架构，AI 帮你搭得更扎实。

AI 让你的能力放大，但放大的是你的决定，不是你的空白。
