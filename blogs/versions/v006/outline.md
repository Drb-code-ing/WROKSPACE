# v006 大纲

## 标题
从模块化到全栈项目：一个 AI Native 开发者的工程化启蒙

## 结构

### 引言
- 接 v005：上篇文章学了 Git 管版本，这回学怎么管代码结构
- 引出新问题：有版本管理了，但代码还是一团乱麻怎么办？
- 故事线：第五天学习从 notes 里的零散代码，到第一个有结构的全栈项目
- 核心观点：工程化的第一步不是学框架，而是理解"怎么组织代码"

### 一、模块化：写代码的第一条规则
- 一个函数只做一件事
- 一个文件只写一个模块/类
- 一个文件夹只负责一个模块/架构
- 类比：宜家家具安装手册——每个零件装进独立袋子，找起来才快
- 呼应 v001 OPC 七个角色——分而治之的思想，从团队分工延伸到代码分工

### 二、从"能跑"到"好维护"
- AI 生成代码很快，但生成的代码往往是一个大文件、一个函数写到底
- 之前笔记里的代码风格 vs 现在有结构的项目
- 好维护 = 可读性 + 简单可靠
- 呼应 v002 Prompt 设计的结构化思维——写 Prompt 要分 Goal/Input/Output，写代码也要分模块

### 三、全栈项目初体验：前后端分离
- users-chat 项目：一个完整的全栈项目长什么样
  - backend/：json-server，提供 users API
  - frontend/：准备写前端页面
- 协作形式：前后端分离（"古法编程"的现代化）
- json-server 是什么：一行命令把 json 文件变成 REST API
- 第一次理解 API（Application Interface）：接口就是"两个系统之间的约定"
- 呼应 v001 中后端角色的第一次落地

### 四、数据存储：变量会消失，文件不会
- 内存存储（数组/对象）：程序重启就丢了
- 文件存储（json 文件）：关机了还在
- 数据库：更强大的文件存储
- db.json 就是我们的"数据库"——users 表
- 呼应 v005 的分布式版本控制——持久化是工程化的基础思维

### 五、Prompt 再进化：加上模块化约束
- 之前写 Prompt 只要求"做出什么功能"
- 现在加一个约束："按模块化方式组织代码"
- 效果：AI 生成的代码结构更清晰
- 呼应 v002 的五块分割法和 v003 的六要素框架——Prompt 设计的每次进化都对应着工程认知的提升

### 结语
- Git 管版本 + 模块化管结构 = 工程化第一步
- 五天的成长路径：OPC（认知）→ Prompt（沟通）→ Agent（工具）→ CLI（工作流）→ Git（版本）→ 模块化（架构）
- Be AI Native 的路上，基本功不是束缚，而是加速器
