# ES 关键词检索：倒排索引、ik 分词与 BM25——给 RAG 装上精确匹配这条腿

前几天的 RAG 进阶之路已经走完三级台阶：native RAG（固定链路：检索→生成）、路由 RAG（简单问题直答、复杂问题检索）、多跳 RAG（子问题拆解 + 循环检索）。Milvus 向量检索在"语义泛化"上表现出色——问"大辽南院大王"也能召回写"乔峰"的段落。但它有个捂不住的盲区：**专业术语和精确实体，纯语义检索反而容易匹配不准**。这一天的笔记补上第三块拼图——**Elastic Search 关键词检索**，并顺着"两路召回怎么融合"一路推进到混合检索的 RRF 算法。这篇文章把整条线拆开讲清楚：倒排索引为什么快、text 和 keyword 怎么分工、ik 双分词器有什么讲究、BM25 凭什么比 TF-IDF 好，最后回到 Agentic RAG 的闭环设计。

---

## 一、向量检索的盲区：为什么 RAG 需要第三种检索

先把三种存储的分工摆出来，笔记里有一句很精炼的定位：

> **MySQL 管行列，Milvus 管语义，ES 管关键词索引。**

- **MySQL**：关系型数据库的"原始"底座，按行列存结构化数据，擅长事务和精确条件查询，但模糊文本搜索是短板；
- **Milvus**：把文本变成向量，按"语义距离"检索，擅长泛化——但语义空间里"降龙十八掌"和"打狗棒法"可能离得很近，而"AML 反洗钱规则 3.2.1 条"这种精确标识符反而成了模糊点；
- **ES**：全文检索特种兵，专攻"关键词必须精确命中"的场景。

笔记里对 Agentic RAG 的定位也很清醒：检索层现在是 **web search + Milvus + ES** 三路供选；Agentic RAG 要回答的是三个问题——**用什么检索？信息够不够？要不要重新搜？** 具体的图结构要根据业务场景设计，理解这个闭环的思路就可以。而要让闭环里"关键词检索"这一路真正跑起来，得先搞懂 ES 的看家本领——倒排索引。

## 二、倒排索引：查询快是因为提前算完了

### 正向索引的困境

普通 MySQL 用的是**正向索引**：以一行为单位存储完整数据，检索文本内容时只能**逐行遍历、逐字匹配**：

```sql
SELECT * FROM article WHERE content LIKE '%高血糖%';
-- 前后通配符让索引失效，全表扫描
```

数据量越大、文本越长，模糊搜索就越慢——大规模关键词检索场景下性能崩塌。

### 倒排索引：把映射反过来

ES 的解法是把方向倒过来。正向索引是"**文档 → 关键词**"，倒排索引是"**关键词 → 文档**"：

```
doc1: "乔峰在聚贤庄大战群雄"   ─┐
doc2: "乔峰误杀阿朱"           ─┼─→ 入库时全部分词，汇进一张全局大表
doc3: "段誉初遇王语嫣"         ─┘

┌──────────┬─────────────────────────────────────┐
│ 词(term)  │ 倒排列表(posting list)                │
├──────────┼─────────────────────────────────────┤
│ 乔峰      │ doc1(TF=1,pos=1) · doc2(TF=1,pos=1) │
│ 聚贤庄    │ doc1(TF=1,pos=3)                    │
│ 阿朱      │ doc2(TF=1,pos=4)                    │
│ 段誉      │ doc3(TF=1,pos=1)                    │
└──────────┴─────────────────────────────────────┘
```

三个关键认知：

**① 索引是全局一张表，不是每篇文档一份。** 所有文档分词后的词条合并进同一个词典，所以查询"乔峰"时一次就能命中 doc1、doc2——posting list 本身就是"包含这个词的全部文档"的完整名单。

**② posting list 里存的不止文档 ID。** 还有词频 TF（给相关性打分用）和位置 pos（给短语匹配用，"乔峰 误杀"要求两词紧挨着就靠它）。

**③ 用写入时的计算换查询时的速度。** 分词、建表全部在**入库时**完成，查询时只做 O(1) 查表 + 排序，不需要翻任何文档原文——这就是"海量文本下毫秒级全文检索"的底气。

### 写入即索引，但不是马上可搜

补充两个工程细节：文档写入后先进内存 buffer，默认**每 1 秒 refresh** 生成一个可搜索的 segment——所以 ES 号称"近实时"（NRT），刚插的数据最长等 1 秒才能被查到。另外分词规则在入库那一刻就定死了，之后改 analyzer **不会重分老数据**，必须 reindex 重建——这是 ES 运维的经典坑。

## 三、动手：建索引、mapping 与检索 API

ES 的 9200 端口存放的是**索引**（可以粗略对应 MySQL 的"表"）。全套操作走 HTTP API：

```bash
# 查看所有索引（table 形式展示）
GET /_cat/indices
```

创建索引就像建表，`mappings` 就是 schema——`properties` 里声明各个和搜索相关的字段：

```json
PUT /article
{
  "mappings": {
    "properties": {
      "title":   { "type": "text" },
      "content": { "type": "text" },
      "author":  { "type": "keyword" }
    }
  }
}
```

两种字段类型的分工是 ES 设计的精髓：

| 类型 | 入库时 | 检索方式 | 适用场景 |
| --- | --- | --- | --- |
| `text` | **分词**，每个词条进倒排表 | 全文检索（match） | 标题、正文 |
| `keyword` | **不分词**，整值当一个词条 | 精确匹配、过滤、聚合（term） | 作者、状态、标签 |

写入后检索：

```json
GET /article/_search
{
  "query": {
    "match": { "title": "高血糖" }
  }
}
```

match 会把"高血糖"也走一遍分词器再查倒排表；而 `term` 查询不分词、精确匹配——所以 **"全文检索 + 精确过滤"** 是标准组合拳（正文 match 搜内容，author term 过滤作者）。

笔记里还点了一个概念：ES 的查询语言叫 **DSL（Domain-Specific Language，领域特定语言）**。三家数据库三套语言正好对照着记：MySQL 用 SQL，Milvus 用 embedding 向量，Elastic Search 用基于 http 的 DSL。

## 四、ik_max_word + ik_smart：索引细、查询粗的非对称设计

ES 自带的 standard 分词器对中文是单字切分（"乔峰"→乔/峰），检索质量崩坏，所以中文场景必装 **IK 分词器**。而 IK 有两个模式，用法有讲究：

```json
{
  "content": {
    "type": "text",
    "analyzer": "ik_max_word",     // 写入时细粒度切
    "search_analyzer": "ik_smart"  // 查询时粗粒度切
  }
}
```

**为什么两侧不一样？逻辑是"召回靠索引侧的多，精确靠查询侧的少"。**

- **ik_max_word（写入）**：最细粒度切——"中华人民共和国"会切出 `中华人民共和国 / 人民 / 共和 / 共和国 / 国`。每个可能的词都成为倒排表里的一个 term，等于**多留钩子**：不管用户按哪种粒度查询，表里都有对应的词可命中 → **召回高**；
- **ik_smart（查询）**：粗粒度智能切——"乔峰大战聚贤庄"只出 `乔峰 / 大战 / 聚贤庄`。查询词少而准 → 噪声少 → **精确高**。

这背后有一条铁律：**索引粒度 ≥ 查询粒度**。

- 索引切得细、查询切得粗 ✓：索引里有"人民"，查询"人民"能命中；
- 索引切得粗、查询切得细 ✗：索引只有"中华人民共和国"整词，查询切出"共和"——查无此词，直接漏召回。

**那查询侧为什么不也用 max_word？** 查询切成"乔/峰"这种单字后，所有含"峰"的文档（张峰、山峰、峰回路转）全被捞出来——召回爆炸、精确崩塌。BM25 的 IDF 会压低单字分值，但架不住命中量大。所以查询侧宁粗勿细。

打个比方：**图书馆的索引卡做全**（书里任何词都建卡），**检索只用规范词查卡**。卡做全了，怎么查都有；查询词做精了，不捞杂鱼。

对称的另一面是代价：索引侧细切让索引体积膨胀、分词耗时更长；查询侧粗切遇到词典外的新词（"阿朱"若不在词库）可能切不动。

## 五、打分：从 TF-IDF 到 BM25

命中的文档按什么排序？这就是相关性打分算法的战场。

**TF-IDF** 的骨架：`score = TF × IDF`——词在**这篇文档**出现越多越相关（TF），且在**全局**越稀有越值钱（IDF："聚贤庄"比"一个"分高）。直觉很好，但有两个先天缺陷：

**缺陷一：词频线性增长。** 出现 10 次得分是 1 次的 10 倍——长文档靠堆词就能霸榜。

**缺陷二：不管文档长短。** 长文档天然 TF 高（词多机会多），短文命中被不公平地压下去。

**BM25**（best matching 25）继承了这个骨架，补上两个修正项：

```
score = IDF × tf·(k1+1) / ( tf + k1·(1 - b + b·文档长/平均长) )
                              └── 饱和 ──┘   └────── 长度归一 ──────┘
```

- **词频饱和（参数 k1）**：TF 的增益边际递减——k1=1.2 时，出现 10 次的增益只比 5 次多一点，长文堆词刷分失效；
- **文档长度归一化（参数 b）**：分母里加入文档长度与平均长度之比，**短文档命中更可信**。

直观例子，查"乔峰"：文档 A 是 5000 字长文出现 10 次，文档 B 是 200 字短文出现 2 次——**TF-IDF 选 A**（10 > 2），**BM25 大概率选 B**（2/200 的密度远高于 10/5000）。这更符合人的判断。

背景：ES 5.x 之前默认 TF-IDF，之后（Lucene 6+）换成 BM25。调参直觉一句话：k1 越大越接近 TF-IDF 的线性，b 越大对长文档惩罚越重。

## 六、混合检索与 RRF：两路召回怎么合

回到 RAG 主线。现在有两路召回：ES 的 BM25（关键词精确）+ Milvus 的向量检索（语义泛化），两路各返回一批带分数的文档。怎么合成一个列表？

第一反应是"分数加权平均"——但立刻撞墙：**两路分数标准完全不同**。BM25 分数无上界（0.6 和 6.0 谁好没有绝对意义，取决于查询词的稀有度），cosine 相似度却有界（约 0~1），分布形状也不同，任何归一化都要先知道分布再调权重，脆弱且难维护。

解法就是笔记里那句话：**抛弃分数，只看排名**——这就是 **RRF（Reciprocal Rank Fusion，倒数排名融合）**：

```
RRF(doc) = Σᵢ 1 / (k + rankᵢ(doc))
```

- `rankᵢ(doc)`：文档在第 i 路结果里的**名次**（从 1 开始）；没出现在该路 → 该路记 0 分；
- `k`：平滑常数，**ES 默认 60**。

**k=60 平滑的是什么？** 不加 k 时，第 1 名得 1/1=1、第 2 名只有 0.5——头部差距巨大，一路的冠军轻易碾压另一路所有结果。加上 k=60 后变成 1/61≈0.0164 vs 1/62≈0.0161——名次间的落差被压平，两路影响力更均衡。**只有"在两路都靠前"的文档才能突出重围**——RRF 最看重的就是双路共识。

**RRF 的局限与进阶**：它丢弃了分数量级信息（"断层第一"和"险胜第一"被同等对待），改进方向是归一化加权融合；更主流的生产方案是**两阶段**——召回（BM25 + 向量，RRF 融合）之后接 **cross-encoder 重排**（如 bge-reranker），融合解决"两路怎么合"，重排解决"哪个最相关"，是两层问题。

至此 Agentic RAG 的检索层齐装满员：**web search（兜底）+ Milvus（语义）+ ES（关键词）**，融合交给 RRF。而"用什么检索、信息够不够、要不要重新搜"的决策，就是下一步 Agentic 化的工作——用 LangGraph 把这些判断画进图里。

## 面试问答

**问：倒排索引为什么比 MySQL 的 LIKE 快？**

> LIKE '%词%' 前后通配符让 B+ 树索引失效，只能逐行遍历逐字匹配，数据量越大越慢。倒排索引在写入时就完成了分词和"关键词→文档"映射的构建，查询时 O(1) 查表直接拿到包含该词的全部文档列表，再按 BM25 排序——本质是用写入时的计算换查询时的速度。

**问：text 和 keyword 类型有什么区别？**

> text 入库时分词，每个词条进倒排表，走 match 全文检索；keyword 不分词，整值当一个词条，走 term 精确匹配、过滤和聚合。标准组合是"全文检索 + 精确过滤"：正文用 text 搜内容，作者/状态用 keyword 过滤。

**问：ik_max_word 和 ik_smart 为什么一个建索引一个做查询？**

> 非对称设计：索引侧细粒度多留钩子（任何查询粒度都能命中，召回高），查询侧粗粒度少而准（不捞杂鱼，精确高）。铁律是索引粒度 ≥ 查询粒度，反过来查询切出的词在索引里不存在，直接漏召回。查询侧不用 max_word 是因为单字匹配会召回爆炸。注意改分词器不会重分老数据，必须 reindex。

**问：BM25 和 TF-IDF 的区别？**

> BM25 继承 TF-IDF"词频×稀有度"的骨架，补上两个修正：词频饱和（k1 控制增益递减，防长文档堆词刷分）和文档长度归一化（b 控制，短文档命中更可信）。例子：查"乔峰"，5000 字长文出现 10 次和 200 字短文出现 2 次，TF-IDF 选前者，BM25 大概率选后者。ES 5.x 起默认 BM25。

**问：混合检索两路分数不可比，怎么融合？**

> 用 RRF 弃分数只看排名：文档综合分 = 各路 1/(k+名次) 之和，k 默认 60。k 平滑了头部名次的差距，让两路影响力均衡，"双路都靠前"的文档胜出。排名是分布无关的，天生可比，几乎零调参。局限是丢了分数量级信息，生产上更好的方案是召回融合后再用 cross-encoder 精排的两阶段架构。

**问：为什么说关键词检索和向量检索是互补关系？**

> 向量检索语义泛化好——"契丹武士"能召回只写"乔峰"的段落，但专有名词、编号、术语容易模糊匹配错；关键词检索精确、可解释，但换说法就失效。RAG 生产环境的标配是混合检索：BM25 保精确、向量保泛化、RRF 融合、必要时重排，再往上由 Agent 决定用哪路检索和要不要重搜。

## 结语：把检索层的最后一块拼图装上

第七十五天把 Agentic RAG 的检索选项从"一条路"扩充成"三路协同"：

```text
MySQL     行列存储        事务与精确条件
Milvus    语义向量        泛化匹配（换说法也能召回）
ES        关键词索引      精确命中（术语/实体/编号）
─────────────────────────────────────────────
写入时分词 → 全局倒排表 → 查询 O(1) 查表 → BM25 排序
两路融合：弃分数、看排名，RRF = Σ 1/(k+rank)
```
