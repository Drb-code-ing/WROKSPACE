# Workflow 与 Agent：确定性流水线 vs 不确定探索——AI 工程的双层能力

## 引言

v045 把 LangChain 的 `.pipe()` 写成了一条可编排的 AI 工作流：Prompt 模板 → 模型 → 输出解析器。那一篇的重点是"调参 + 链式调用"，回答的是：

```text
怎么把一次 LLM 调用，做成可复用、可替换节点的流水线？
```

但第四十二天的学习笔记提出了一个更尖锐、也更容易被面试官追问的问题：

> **AI 工作流也能干活，它和 Agent 有什么区别？**
>
> 很多人会混淆——反正都是 AI 在执行任务。

v029 讲过 Agent 的能力公式（LLM × Tools × Context），v034 写过 ReAct Loop，v042 拆过 Skills。那些文章各自站在"智能体是什么"的一侧。

**本篇不重复 Agent 六要素，也不重复 Temperature 调参。** 镜头只对准一个对照关系：

```text
Workflow = 确定的执行
Agent    = 不确定的探索
```

本文基于 `ai/agent/concepts/workflow_agent/readme.md`，从 Coze 可视化编排、LangChain 的 pipe 流水线、招聘简历处理链路，一路走到 Agent 的感知 / 决策 / 执行三能力，最后给出产业选型与"骨架 + 大脑"的双层架构。

## 一、从 `.pipe()` 重新认识 Workflow

### 1.1 你其实已经写过 Workflow

v045 的 Demo 里有这样一段：

```js
const creativeChain = storyPrompt
  .pipe(creativeModel)
  .pipe(outputParser)

creativeChain.invoke({ theme: '秋日山野晚风' })
```

第四十二天的笔记把这段代码直接抬到了概念层：

```text
企业的流水线 AI 工作流（workflow）
LangChain 打造 链着工作节点（node）
pipe = 传送带 / 水管子
```

这不是修辞。它精确描述了 Workflow 的技术形态：

```text
原料（输入）
  → 节点 A（固定逻辑）
  → 节点 B（固定逻辑）
  → 节点 C（固定逻辑）
  → 成品（输出）
```

每一步都有明确的输入和输出。条件满足，就进入下一环节。**路线在运行前就已经画好了。**

### 1.2 Workflow 的本质定义

学习笔记给出的定义非常干净：

> Workflow 本质上是一套预定义的流程，可以把它想象成一套生产的流水线。  
> 每一步都有明确的输入和输出。每个节点的逻辑是固定的，当条件满足，就会进入下一环节。  
> 在技术上，它通常变成一个编排好的工作流引擎——一个由 AI 调用、条件判断、循环逻辑组成的图谱。

拆成三个关键词：

```text
预定义（predefined）  → 路径在写代码 / 画图时就定了
节点固定（fixed node） → 每个节点做什么不临时发明
条件驱动（condition）  → 满足条件就前进，不满足就走另一条固定分支
```

所以 Workflow 的核心不是"有没有 AI"，而是**有没有一条被编排好的轨道**。

### 1.3 可视化工作流：Coze 与 AI 照相馆

笔记里提到用 Coze 构建过可视化工作流（AI 照相馆）：

```text
输入
  → 逻辑判断
  → LLM
  → 图片生成
  → ...
  → 输出
```

照相馆愿意付费买工作流，不是因为"更聪明"，而是因为：

```text
需要把智能融入既定流程
需要稳定执行
需要可预期的成本与结果
```

FDE（前沿部署工程师）把 Workflow 当成神器，也是同一逻辑：**流程性工作、自动化、可交付。** 客户买的是"按 SOP 稳定跑完"，不是"AI 自己想怎么干就怎么干"。

### 1.4 LangChain：用代码快速搭建工作流

笔记把 LangChain 定位得很准：

> LangChain 是用于快速搭建工作流的开发框架，灵活构建各类智能任务链路。

对比一下：

| 形态 | 代表 | 编排方式 | 适合谁 |
|---|---|---|---|
| 可视化 Workflow | Coze / Dify / n8n | 拖拽节点 | 业务 / FDE / 快速验证 |
| 代码 Workflow | LangChain / LangGraph（部分） | `.pipe()` / 图编排 | 工程师 / 复杂集成 |

两者都是 Workflow，差别只在"画图"还是"写代码"。**轨道感**是共同特征。

## 二、一个完整例子：招聘简历 Workflow

抽象定义看多了容易飘。笔记给了一个非常落地的招聘场景：

```text
输入：一份简历（PDF）
  ① 解析 PDF
  ② 提取技能描述、工作经历、教育经历
  ③ 匹配岗位需求（RAG）
  ④ 打分、排序
输出：优质简历列表
```

### 2.1 为什么这是 Workflow，不是 Agent

看路径：

```text
PDF → 解析 → 结构化字段 → RAG 匹配 → 打分排序 → 结果
```

- 每一步的职责在编排时就定死了
- 不会因为"这份简历写得特别文艺"就临时决定先去搜公司舆情
- 不会因为"候选人是海归"就突然改成另一套评估流程
- 输入同类、输出同类，可批量、可复盘、可计费

这正是企业流水线要的东西：

```text
稳定
可审计
可替换节点
可横向扩展（每天处理 1 万份简历）
```

### 2.2 节点可以含 AI，但流程仍是确定的

常见误解：

```text
"节点里有 LLM，所以它是 Agent。"
```

错。LLM 只是节点内部的计算单元：

```text
节点 ②：用 LLM 从文本里抽技能标签  ← 仍然是固定步骤
节点 ③：用 RAG 匹配 JD              ← 仍然是固定步骤
节点 ④：用规则或模型打分            ← 仍然是固定步骤
```

**AI 在节点里，不代表路径由 AI 决定。**  
Workflow 允许节点很智能，但**调度权在编排图**。

### 2.3 失败路径也是预定义的

生产级 Workflow 还会把异常写进轨道：

```text
PDF 损坏      → 进入人工复核队列
解析字段缺失  → 标记 low_quality，不进入匹配
RAG 无结果    → 降级为关键词匹配
打分低于阈值  → 直接淘汰，不进排序列表
```

这些分支同样是预定义的。系统"知道"自己在哪条路上，因为它本来就只有这些路。

## 三、那 Agent 到底哪里不一样？

### 3.1 不在轨道上，而在开放空间里

笔记对 Agent 的描述几乎是一句定义：

> 和 Workflow 逻辑完全不一样，它不走在一条预设的轨道上，而是站在一个开放的空间里，自己去探索怎么做（智能）。

对照：

```text
Workflow：路径先画好，运行时按图走
Agent   ：目标先给定，运行时自己找路
```

### 3.2 Agent 的三大核心能力

从技术角度，一个 Agent 往往具备三个大的核心能力：

#### 1）感知能力（Perception）

```text
通过输入文本、图像、数据来理解任务
知道有哪些工具可以调用
判断当前情况如何
决定如何分步、如何规划
```

感知不是"读到字符串"，而是把环境状态转成可决策的信息。

#### 2）决策能力（Decision）

```text
根据感知到的信息
选择最合适的下一步操作
```

决策意味着**分支不是写死在图里，而是运行时生成**。

#### 3）执行能力（Action）

```text
真正调用工具
修改数据库
发请求、写文件、触发下游系统
```

没有执行，Agent 只是会想不会干；没有决策，它只是脚本；没有感知，它只是盲打。

> v029 的公式 `Agent = LLM × Tools × Context`，可以看成这三能力的另一种切分：LLM 负责感知与决策，Tools 负责执行，Context 给感知提供燃料。

### 3.3 旅行规划：动态路径的经典例子

笔记的例子非常直观：

```text
你让 Agent 去规划旅行。
它可能会：
  1. 先搜机票和酒店价格
  2. 再查天气和签证需求
  3. 结合你的偏好和预算，动态权衡方案
```

关键点不在"它会搜机票"，而在：

```text
整个过程，它走的路径可能和你预期的完全不同。
```

- 预算突然变紧 → 改成邻近城市
- 签证查不到 → 换目的地
- 天气极差 → 把行程从海边改成博物馆
- 你中途说"改成亲子" → 重新规划，而不是硬走原流程

这就是自主性（autonomy）和适应性（adaptability）。

### 3.4 高速公路 vs 司机

笔记用了一个非常好记的比喻：

```text
Workflow 像一条高速公路
  路线清晰固定
  训练有素就能到达既定终点

Agent 更像一个司机
  它知道要去哪
  可以随时改道（感知环境）
  尝试新的路线
  甚至在目的地变化时自行调整
```

再压缩成一句：

> **本质区别在于：Workflow 是确定的执行，Agent 是不确定的探索。**

## 四、一张表看清边界

| 维度 | Workflow | Agent |
|---|---|---|
| 路径 | 预定义 | 运行时生成 |
| 控制权 | 编排图 / 规则引擎 | LLM 推理 + 工具选择 |
| 可预期性 | 高 | 中到低 |
| 创造力 | 弱（节点内可有，流程无） | 强 |
| 失败模式 | 分支可预置 | 可能绕路、重试、改目标 |
| 审计难度 | 低（路径固定） | 高（路径发散） |
| 成本波动 | 相对稳定 | 可能因多轮探索暴涨 |
| 技术依赖 | 规则、图形化编排、流程引擎 | 大模型推理、记忆、工具调用 |
| 典型场景 | 审批、数据清洗、客服 SOP、简历筛选 | 复杂搜索、策略规划、开放任务 |

产业角度，笔记的判断也很清楚：

```text
Workflow 更适合流程化、重复性任务
  审批流程、数据清洗、客服 AI

Agent 更适合动态角色场景
  复杂搜索、策略规划
```

技术栈领域：

```text
Workflow → 规则、图形化编排（Coze）、流程引擎
Agent    → 大模型推理能力、记忆能力、工具调用
```

## 五、最容易混淆的四个误区

### 误区 1：节点里有 LLM，就是 Agent

```text
❌ 错
✅ 对：调度权在谁手里，才决定它是 Workflow 还是 Agent
```

LLM 可以是 Workflow 节点里的"工人"，也可以是 Agent 里的"指挥官"。

### 误区 2：有 if/else 就是 Agent

```text
Workflow 也有条件判断和循环
但分支是人预先画好的

Agent 的分支是它自己想出来的
```

`if score < 60 then reject` 是 Workflow。  
`先想想这份简历该不该深挖，要不要先查公司背景` 才是 Agent 味道。

### 误区 3：Agent 一定比 Workflow 高级

```text
不是高级与低级
是不确定探索 vs 确定执行

很多企业场景里，Workflow 才是正确解
因为客户要的是稳定交付，不是惊喜
```

### 误区 4：只能二选一

笔记最后明确说：未来 AI 工程会集合两者的双层能力。

```text
底层 Workflow：提供稳定性和可控性
上层 Agent  ：提供灵活性和智能性

Workflow 是骨架
Agent 是 Workflow 的大脑

Workflow 没什么创造力
Agent 有创造力，但不可控、不可预测
一起结合：既高效又有智慧
```

这是本篇最重要的工程结论。

## 六、双层架构：骨架 + 大脑怎么落地

### 6.1 一个可落地的分层

```text
┌─────────────────────────────────────┐
│  Agent 层（探索 / 决策 / 改道）        │
│  - 理解目标                           │
│  - 选择工具 / 选择子流程               │
│  - 处理异常与目标漂移                 │
└─────────────────┬───────────────────┘
                  │ 调用 / 编排
┌─────────────────▼───────────────────┐
│  Workflow 层（稳定执行 / 可审计）      │
│  - PDF 解析                           │
│  - 字段抽取                           │
│  - RAG 匹配                           │
│  - 打分排序 / 通知 / 入库             │
└─────────────────────────────────────┘
```

### 6.2 招聘场景的双层版

```text
Agent：
  收到"帮我筛本周的后端候选人"
  → 感知：有 120 份新简历，岗位是 Java 后端
  → 决策：先跑标准筛选 Workflow；对 top 10 再做深挖
  → 执行：调用筛选 Workflow；对可疑简历再调搜索工具

Workflow：
  解析 → 抽取 → RAG 匹配 JD → 打分 → 排序
  （路径固定，结果可复盘）
```

Agent 负责"怎么安排今天的筛选策略"，  
Workflow 负责"每一份简历怎么稳定处理"。

### 6.3 什么时候该把哪一层做厚

```text
流程重复、合规要求高、成本要可预期
  → 把 Workflow 做厚，Agent 只做轻量路由

任务开放、目标会变、环境信息不全
  → 把 Agent 做厚，Workflow 沉淀高频子流程

两者都重要
  → 高频子任务 Workflow 化
    低频异常与策略 Agent 化
```

这和软件工程里的"脚本自动化 vs 人做决策"是同一哲学，只是现在"决策者"也可能是模型。

## 八、面试高频问题与答题框架

### 8.1 Workflow 和 Agent 有什么区别？

**回答框架：**

> Workflow 是预定义流程：节点固定、输入输出明确、条件分支事先编排好，适合流程化、重复性任务。Agent 是开放空间里的探索者：具备感知、决策、执行能力，路径在运行时动态生成，适合复杂搜索和策略规划。一句话：Workflow 是确定的执行，Agent 是不确定的探索。

### 8.2 节点里调用了大模型，算不算 Agent？

**回答框架：**

> 不算自动升级为 Agent。关键看调度权在谁手里。如果整体路径仍由编排图固定推进，LLM 只是某个节点的处理函数，它仍是 Workflow。只有当系统能根据环境自主选择下一步、改道甚至调整目标时，才进入 Agent 范畴。

### 8.3 企业该上 Workflow 还是 Agent？

**回答框架：**

> 看任务是否流程化、结果是否要求强可预期。审批、数据清洗、标准客服、简历初筛，优先 Workflow；开放式调研、动态规划、异常处理密集的场景，优先 Agent。生产上更常见的是双层：底层 Workflow 保稳定，上层 Agent 保灵活。

### 8.4 为什么说 Workflow 是骨架、Agent 是大脑？

**回答框架：**

> Workflow 提供可审计、可复用、成本可控的执行骨架，但创造力有限；Agent 提供推理、记忆、工具调用带来的智能与适应力，但路径不可完全预测。两者结合，才能既高效又有智慧——骨架保证不散架，大脑保证会应变。

### 8.5 LangChain 的 pipe 和 Coze 工作流是什么关系？

**回答框架：**

> 都是 Workflow 形态。Coze 是可视化编排，LangChain 的 `.pipe()` 是代码编排。本质都是把 Prompt、模型、解析、业务节点串成预定义链路。它们解决的是"稳定流水线"，不是"自主探索"。若要 Agent，还需要循环决策、工具选择、状态记忆等机制。

## 结语

第四十二天关于 Workflow 的学习，不是再写一条 `.pipe()`，而是把 v045 里已经出现过的"工作流"，正式抬到了架构概念层，并和 Agent 做了干净切割。

```text
Workflow
  预定义轨道
  节点固定
  条件驱动
  适合流程化、重复性任务
  技术栈：规则 / 可视化编排 / 流程引擎

Agent
  开放空间
  感知 → 决策 → 执行
  路径运行时生成
  适合动态、复杂、目标可能漂移的任务
  技术栈：推理 / 记忆 / 工具调用

双层能力
  Workflow = 骨架（稳定、可控）
  Agent    = 大脑（灵活、智能）
```

面试里如果只能带走一句话，就带走笔记里的这句：

> **Workflow 是确定的执行，Agent 是不确定的探索。**
