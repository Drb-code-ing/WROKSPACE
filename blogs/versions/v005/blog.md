# 从 Git 到版本思维：一个 AI Native 开发者的基本功补全

## 引言

回顾这个博客系列，我走过的路是这样的：

- **v001** 聊了 OPC（一人公司）的概念——借助 AI，一个人可以身兼七个角色。
- **v002** 聊了 Prompt 设计和 LLM 原理——怎么写精确的指令让 AI 输出高质量代码。
- **v003** 聊了 AI Agent 的实战——用 Claude Code 从零到一搭建完整项目。
- **v004** 聊了工作流进化——从 VS Code 插件到 CLI，用 /plan 和 CLAUDE.md 让 AI 融入日常开发。

一路走来，我越来越依赖 AI 帮我写代码。但有一个问题开始浮现：**我对代码的理解，是不是越来越"薄"了？**

AI 帮我生成了很多东西——落地页、鼓点模拟器、工具脚本——但底层的东西呢？版本控制、命令行、服务器、数据库……这些传统开发者的基本功，我一个都没正经学过。

所以 v005 的主题很不一样：**我主动回归基础，开始学 Git。**

这不是一篇"Git 教程"，而是一个 AI Native 开发者为什么要补基本功、以及怎么补的思考。

## 一、为什么要学 Git？

先坦白一件事：在学 Git 之前，我的"版本管理"完全靠 AI Agent 完成。

Claude Code 有 `/init` 命令，能自动分析项目并生成 CLAUDE.md。它帮我管理了"AI 对项目的理解版本"，但它不管"代码本身的版本"。实际上，Git 仓库只是我让 AI 生成代码时自动初始化出来的——我对它的理解停留在"点一下提交按钮"的水平。

但有一天，我遇到了一个很尴尬的场景：

我在做一个项目，改了一堆代码，但新方案没跑通。我想回到之前能跑的状态，但我不记得改了什么。底层文件用不了一键还原。那一刻我意识到：**我的项目没有"存档"。**

做游戏需要存档，写代码同样需要。而 Git 就是这个"存档系统"。

我们常说的"AI Native 开发者不用学基础"，我觉得这话只说对了一半。AI 确实可以帮你跳过大段的入门门槛，让你快速做出东西来。但**基本功解决的不是"能不能做"的问题，而是"安不安全、可不可持续"的问题。**

版本管理就是最典型的一个——你不会 Git，代码也能跑；但你随时可能丢了它。

## 二、三个核心概念：仓库、状态、快照

Git 的笔记里写了三件最基本的事：

### 1. git init：从"文件夹"到"仓库"

```bash
git init
```

这行命令把一个普通文件夹变成一个 Git 仓库。背后发生了什么？生成了一个 `.git` 隐藏目录，里面存着这个项目的完整版本历史。

笔记里有一句话我印象很深：**"文件 : 文件版本(快照) === 1 : n"**——一个文件可以有无数个版本的快照。

这对我来说是一个思维转变：以前我把代码文件看作"正在编辑的东西"，改了就是覆盖了。但现在我知道，每一次提交都是一个可回溯的时间点，代码不是一条直线，而是一棵可以有分支的树。

### 2. git status：时刻知道自己在哪里

```bash
git status
```

笔记里特别标注了：**"做任何 git 操作前，先 git status"。**

这是一个习惯，更是一种意识——**确认当前状态再行动。**

这让我联想到 v004 里说的 `/plan` 模式：先对齐再执行。`git status` 和 `/plan` 本质上做的是同一件事：**在行动之前，先搞清楚自己在哪里、要干什么。**

### 3. git add + git commit：两次确认，一次存档

```bash
git add 文件名
git commit -m "描述"
```

这个两步走的操作设计得很妙：

- `git add` 把文件放入**暂存区**——"我决定要存这些文件"
- `git commit` 真正创建版本快照——"我确认，存！"

两次确认，一次存档。这不是技术限制，而是一个**防误操作的设计**——给你两次机会想清楚再提交。

这对于习惯了"AI 帮我搞定一切"的我来说，是一个很微妙的学习：**控制流程中的每一步，都值得停下来确认一下。** 这和 Prompt 设计中反复审视 prompt 质量、和在 /plan 模式下确认计划，本质上是同一套思维。

## 三、分布式与协作：一人公司的版本管理

Git 的核心理念是**分布式版本控制**。对我来说，理解这个最好的方式是类比：

> 没有 Git 的时候，项目就像你桌面上一个叫"最终版"的文件夹，里面塞满了"最终版_v1"、"最终版_v2"、"真的最终版_v3"……
>
> 有了 Git 之后，你再也不需要这种命名了。每一次提交都是一个命名的版本，你随时可以坐时间机器回到过去。

但 Git 不只是一个"时光机"，它还是一个"协作平台"。

- **本地仓库**：你电脑上的 `.git`，你的私人存档
- **远程仓库**：GitHub/Gitee 上的中央仓库，团队的共享存档
- **push**：把你的本地版本推送到远程

在 OPC（一人公司）的语境下，远程仓库的意义不太一样——**它不只是协作工具，更是备份和发布机制。**

我一个人写代码，不需要和别人协作，但我仍然需要：
1. 备份我的代码（硬盘会坏，电脑会丢）
2. 在不同的设备上继续工作（工作站和笔记本）
3. 把我的项目"发布"出去（让别人看到、CI/CD 自动部署）

Git + GitHub 一套下来，以上全解决了。

所以我的感悟是：**一人公司不等于单机开发。** 相反，因为只有一个人，你更需要可靠的基础设施来支撑——而 Git 就是代码基础设施的第一块砖。

## 四、Git 与 AI Agent：两种"版本管理"

学完 Git 之后，我发现了一个有意思的对比：

| 维度 | CLAUDE.md（AI 版本管理） | Git（代码版本管理） |
|------|-------------------------|-------------------|
| 管什么 | AI 对项目的理解上下文 | 代码本身的历史 |
| 谁读 | AI 和开发者 | 开发者和团队 |
| 时间线 | 当前理解快照 | 完整版本历史 |
| 更新方式 | `/init` 重新生成 | `commit` + `push` |
| 回滚 | 不适用 | `git checkout` / `revert` |

两者是互补的。`CLAUDE.md` 帮助 AI 理解"项目现在是什么样的"，Git 记录"项目是怎么变成这样的"。

当 AI Agent 越来越强，它能接管更多编码工作，但**版本管理的决策仍然是人的事**——什么时候提交、提交什么、要不要回退、怎么处理冲突，这些都需要你对项目有整体理解。

这和我在 v002 里说的"领域知识是护城河"一脉相承：**AI 可以帮你写代码，但理解代码在项目中的位置和历史，仍然是你的责任。**

## 五、配置与开始：建立自己的 Git 工作流

学完基础之后，我做了两件事来把 Git 融入我的开发流：

### 1. 配置全局身份

```bash
git config --global user.name "drb"
git config --global user.email "[email]"
```

这是一次性设置，但意义不小——**每一次提交都带着你的名字。** 这在 OPC 场景下可能没那么关键，但它建立了一种"所有权意识"：这些代码是我的，我为其负责。

### 2. 建立"写代码 → 提交"的节奏

我现在的开发模式是：

1. 让 AI Agent 生成或修改代码
2. review 改动，确认没问题
3. `git add` 暂存
4. `git commit` 提交
5. `git push` 推送备份

这套流程看起来是纯手动操作，但我觉得在现阶段是对的——**每次提交都是一个有意识的决策。** 未来也许有 AI 自动提交的工具，但现在，亲手提交代码让我对项目保持掌控感。

## 结语：AI Native ≠ 不学基础

这篇博客和前面四篇很不一样。没有炫酷的 AI 工具，没有高级的工作流，只是最基础的 Git 操作。但对我来说，它是整个系列里很重要的一篇。

因为这个系列的主题一直是"一个人 + AI 能做什么"，但忽略了另一个问题：**一个人 + AI，能持续做多久？**

答案是：**看你的基本功有多扎实。**

AI 帮你写代码、搭架构、做测试——但如果你不会版本控制，你的代码随时可能丢失；如果你不会命令行，你的工作流被绑定在 GUI 上；如果你不懂数据库，你的应用永远是个玩具。

学 Git 是补基础的第一步。接下来还有命令行、数据库、网络……这条路很长，但 AI 让它可以走得更快。

因为正如我在 v001 里说的，AI 可以让你身兼七个角色，但前提是——**你真的愿意去学这七个角色**的基本功。
