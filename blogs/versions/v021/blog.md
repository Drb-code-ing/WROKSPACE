# 栈、队列与链表：一个 AI Native 开发者的线性数据结构进阶

## 引言

v019 学了数组——连续内存、索引访问、高阶函数。那是数据结构的"第一块积木"。

v020 学了 JS 执行机制——单线程、Event Loop、Promise。那是运行时层面的基本功。

今天回到数据结构，把剩下的线性结构补齐：**栈、队列、链表**。这三种结构都可以看作数组的"变体"——要么是操作受限的数组，要么是存储方式不同的数组。

理解它们的本质区别，才能在实际开发中选对工具。

## 一、线性数据结构全景

先梳理整个线性数据结构的版图：

```
线性数据结构
├── 数组（Array）
│   └── 连续存储，索引访问 O(1)
├── 链表（Linked List）
│   └── 非连续存储，节点通过指针连接
├── 栈（Stack）
│   └── 操作受限的数组，只能在一端操作
└── 队列（Queue）
    └── 操作受限的数组，一端入另一端出
```

**核心认知：** 栈和队列，本质上就是**操作受限的数组**——底层用数组实现，只是限制了操作方法。而链表是**存储方式不同**——从连续内存变成了离散节点。

（非线性数据结构——树和图——那是后话。）

## 二、灵活增删的数组：push、unshift、splice

v019 学过 push/pop/shift/unshift，今天从**内存视角**重新审视：

### push：尾部添加，可能有扩容开销

```javascript
const arr = [1, 2]
arr.push(3)  // [1, 2, 3]，返回新长度 3
```

push 往尾部加——大多数时候 O(1)。但如果 `arr.length >= capacity`（内部容量满了），JS 引擎需要**重新分配一块更大的连续内存**，把旧数据搬过去。这是隐藏的 O(n) 开销。链表没有这个问题。

### unshift：头部添加，必须移动所有元素

```javascript
const arr = [2, 3]
arr.unshift(1)  // [1, 2, 3]，返回新长度 3
```

从内存视角看：头部插入元素 1，原本的 2 和 3 都要**往后挪一个位置**。数组长度 n 越大，挪的元素越多——O(n)。

### splice：删 + 增的组合拳

```javascript
const arr = [1, 2]
console.log(arr.splice(1, 0, 3))  // []（从索引1开始，删0个，插入3）
console.log(arr)                   // [1, 3, 2]
```

`splice(start_index, delete_count, ...added)` —— 在指定位置，先删再增。底层相当于 `slice + replace`。

### 关键认知：数组增删都不是纯函数

| 方法 | 位置 | 操作 | 时间复杂度 | 纯函数？ |
|------|------|------|-----------|----------|
| `push` | 尾部 | 添加 | O(1)* | ❌ |
| `pop` | 尾部 | 删除 | O(1) | ❌ |
| `unshift` | 头部 | 添加 | O(n) | ❌ |
| `shift` | 头部 | 删除 | O(n) | ❌ |
| `splice` | 任意 | 删+增 | O(n) | ❌ |

\* push 扩容时退化为 O(n)

**纯函数**：不修改原数据，同样的输入永远得到同样的输出。map、filter 是纯函数；push、pop、splice 都直接改原数组，不是纯函数。

## 三、栈 Stack：后进先出的"冰棍箱子"

### 生活类比

```
      ┌─────────┐
      │  巧乐兹   │  ← 最后放进去的
      ├─────────┤
      │  冰工厂   │
      ├─────────┤
      │  可爱多   │
      ├─────────┤
      │ 东北大板  │  ← 最先放进去的
      └─────────┘
   只能从顶部拿！
```

小卖部的冰棍箱子——老板总是把新到的货放在最上面，你买的时候拿到的永远是最新放进去的那根。这就是**后进先出（LIFO, Last In First Out）**。

### 代码实现

栈就是**只用 push 和 pop 的数组**：

```javascript
const stack = []           // 空栈

// 入栈 push
stack.push("东北大板")
stack.push("可爱多")
stack.push("冰工厂")
stack.push("巧乐兹")

// 查看栈顶元素 peek
const top = stack[stack.length - 1]  // "巧乐兹"

// 出栈 pop —— 后进先出
while (stack.length) {
  console.log(stack.pop())
}
// 输出：巧乐兹 → 冰工厂 → 可爱多 → 东北大板

console.log(stack)  // []
```

栈的三个核心操作：
- `push` —— 入栈（只能在栈顶）
- `pop` —— 出栈（只能在栈顶）
- `peek` —— 查看栈顶元素（`stack[stack.length - 1]`，不删除）

**栈 = 操作受限的数组，只能在尾部操作。**

### 栈的实际应用

- **浏览器后退按钮** —— 每访问一个页面就 push，点后退就 pop
- **函数调用栈** —— 每调用一个函数就 push 到调用栈，return 就 pop
- **括号匹配** —— 左括号 push，右括号 pop 并检查是否匹配
- **撤销/重做** —— 操作历史 push，Ctrl+Z 就是 pop

## 四、队列 Queue：先进先出的"排队"

### 生活类比

```
  出队 ← ┌────┬────┬────┬────┐ ← 入队
  shift  │ 1  │ 2  │ 3  │ 4  │  push
         └────┴────┴────┴────┘
         队头              队尾
```

食堂排队打饭——先来的先打到饭，后来的在后面排着。这就是**先进先出（FIFO, First In First Out）**。

### 代码实现

队列就是**push + shift 的组合**：

```javascript
const queue = []

// 入队 push（队尾进）
queue.push("东北大板")
queue.push("可爱多")
queue.push("冰工厂")
queue.push("巧乐兹")

// 出队 shift（队头出）—— 先进先出
while (queue.length) {
  console.log(queue.shift())
}
// 输出：东北大板 → 可爱多 → 冰工厂 → 巧乐兹

console.log(queue)  // []
```

队列的两个核心操作：
- `push` —— 入队（队尾进）
- `shift` —— 出队（队头出）

**队列 = 操作受限的数组，队尾进队头出。**

注意：用数组模拟队列有一个性能问题——`shift()` 是 O(n)，因为删除头部后所有元素都要前移。生产环境中会用**循环队列**或**链表实现队列**来优化。

### 队列的实际应用

- **任务队列** —— JS 的 Event Loop 宏任务队列就是队列
- **消息队列** —— RabbitMQ、Kafka 的核心数据结构
- **BFS 广度优先搜索** —— 树的层序遍历
- **打印机任务** —— 先提交的先打印

## 五、链表 Linked List：离散存储的"火车"

### 数组 vs 链表：两种存储哲学

```
数组（连续存储）：
┌───┬───┬───┬───┐
│ 1 │ 2 │ 3 │ 4 │  一块连续内存，索引直接访问
└───┴───┴───┴───┘

链表（离散存储）：
┌───┬───┐    ┌───┬───┐    ┌───┬───┐    ┌───┬───┐
│ 1 │ ●─┼───→│ 2 │ ●─┼───→│ 3 │ ●─┼───→│ 4 │ ∅ │
└───┴───┘    └───┴───┘    └───┴───┘    └───┴───┘
  head                                    tail
```

**数组：** 连续内存，像一整排连号的储物柜。知道第一个柜子的位置，加上偏移量就能直接找到任意一个柜子——O(1)。

**链表：** 离散内存，像一列火车。每节车厢（节点）装着数据 + 指向下一节车厢的钩子（next 指针）。要找到第 3 节车厢，必须从车头开始一节一节走过去——O(n)。

### 节点结构

链表的数据单位叫**节点（Node）**，每个节点包含：
- `val` —— 存数据
- `next` —— 指向下一个节点的引用（指针）

```javascript
function ListNode(val) {
  this.val = val
  this.next = null
}

const node = new ListNode(1)
node.next = new ListNode(2)

// node 的结构：
// {
//   val: 1,
//   next: {
//     val: 2,
//     next: null
//   }
// }
```

**关键概念：**
- **head** —— 链表的第一个节点。访问链表任何一个元素，都必须从 head 开始，逐个访问 next，直到找到目标节点
- **tail** —— 链表的最后一个节点，它的 `next` 指向 `null`，标志着链表结束
- 节点和节点的分布是**离散的、不连续的**——不像数组那样一块连续内存

### 共同点

链表和数组：
- 都是**有序的列表（list）**
- 都是**线性结构**——有且仅有一个前驱节点，有且仅有一个后继节点
- 区别：数组靠索引访问，链表靠 next 指针串联

## 六、链表的增删：指针的魔法

链表的增删不需要像数组那样移动大量元素——只需要**改变指针指向**。

### 添加节点

```
添加前：
  [A] ──→ [C]

添加 B 到 A 和 C 之间：
  1. 找到目标位置的前驱节点 A
  2. B.next = A.next    （让 B 指向 C）
  3. A.next = B          （让 A 指向 B）

添加后：
  [A] ──→ [B] ──→ [C]
```

**本质是对 next 指针操作：**
1. 找到目标节点的前驱节点
2. 新节点的 next 指向目标节点
3. 前驱节点的 next 指向新节点

⚠️ **注意顺序！** 如果先把前驱节点的 next 指向新节点，就会"坐过站"——丢失对目标节点的引用。

### 删除节点

```
删除前：
  [A] ──→ [B] ──→ [C]

删除 B：
  1. 找到 B 的前驱节点 A
  2. A.next = B.next    （让 A 直接指向 C）
  3. B.next = null       （断开 B 与链表的联系）

删除后：
  [A] ──→ [C]    [B] 孤立
```

**本质也是对 next 指针操作：**
1. 找到目标节点的前驱节点
2. 前驱节点的 next 指向目标节点的后继节点
3. 目标节点的 next 置为 null

### 时间复杂度对比

| 操作 | 数组 | 链表 | 原因 |
|------|------|------|------|
| **访问（按索引）** | O(1) | O(n) | 数组直接偏移计算；链表必须从头遍历 |
| **增删（头部）** | O(n) | O(1) | 数组需要移动所有后续元素 |
| **增删（尾部）** | O(1)* | O(1) | 都不需要移动元素 |
| **增删（中间）** | O(n) | O(1)** | 数组要移动；链表只改指针 |

\* 数组 push 扩容时 O(n)
\** 前提是已经定位到目标位置——链表定位本身需要 O(n) 遍历

**核心权衡：**
- 数组：遍历快（按索引 O(1)），增删慢（移动元素 O(n)）
- 链表：遍历慢（从 head 逐个找 O(n)），增删快（改指针 O(1)）

### 数据规模决定选型

```
数据规模
  ├── 小 → 数组（开箱即用，cache 友好）
  └── 大 → 链表（动态扩容，频繁增删时优势明显）
```

- 数组扩容只有初始化时开销大，其他时候没有
- 链表每次新增都申请内存，开销平均但分散
- 数组的优势：遍历、按索引取元素
- 链表的优势：增删（找到位置后改指针即可）

## 七、JS 数组的"双重人格"

一个容易被忽略的细节：**JS 数组未必是真正的数组**。

```javascript
const arr = [1, 2, 3, 4]              // 纯数组——连续内存
const arr2 = ['haha', 1, { a: 1 }]    // 不那么"数组"了
console.log(arr2[2])                   // { a: 1 }，仍可正常访问
```

JS 引擎（V8）的优化策略：

| 数组类型 | 条件 | 底层存储 |
|----------|------|----------|
| **纯数组** | 每一项类型一致 | 连续内存，真正的数组 |
| **非纯数组** | 类型不一致 | HashTable 分配内存，失去数组特征 |

**当每一项类型一致时**，JS 引擎会优化为纯数组——连续内存，索引偏移访问，速度快。

**当类型不一致时**，连续存储没有意义（类型不同，每项大小不同），底层退化到 **HashTable** 来分配内存空间。此时 `arr[2]` 仍然可以访问，但底层是用哈希表计算索引，而不是简单的内存偏移。

> 这是 JS 引擎层面的优化细节，日常开发不需要过度关注——但知道它的存在，能帮你理解为什么"保持数组元素类型一致"是一个好的实践。

## 八、sort 的暗坑：默认按 ASCII 码排序

```javascript
let arr = [10, 2, 5]

// ❌ 错误——默认按字符串（ASCII码）排序
arr.sort()        // [10, 2, 5]（"10" < "2" 因为 '1' 的 ASCII 码 < '2'）

// ✅ 正确——传比较函数
arr.sort((a, b) => a - b)  // [2, 5, 10]
```

**`sort()` 默认把元素转成字符串，按 ASCII 码比较。** 数字排序一定要传比较函数：
- `a - b` → 升序
- `b - a` → 降序

这也是面试高频踩坑点。

## 结语

今天从数组出发，把线性数据结构的版图基本补齐了：

1. **线性数据结构全景** —— 数组、栈、队列、链表，都是线性的（一个前驱一个后继）
2. **数组增删再审视** —— push 扩容、unshift 移动元素、splice 删增组合，都不是纯函数，时间复杂度 O(n)
3. **栈 Stack** —— 操作受限的数组，push/pop/peek，LIFO 后进先出。浏览器后退、函数调用栈
4. **队列 Queue** —— push/shift，FIFO 先进先出。任务队列、BFS、消息队列
5. **链表 Linked List** —— 离散存储，节点 + next 指针串联。遍历 O(n)，增删改指针 O(1)
6. **链表增删** —— 找到前驱节点 → 改 next 指针指向。别"坐过站"
7. **JS 数组双重人格** —— 类型一致 = 连续内存（真数组），类型不一致 = HashTable（伪数组）
8. **sort 暗坑** —— 默认 ASCII 码排序，数字必须传比较函数

**数组是第一块积木，栈和队列是它的"受限版本"，链表是它的"离散版本"。四种结构各有适用场景，选对工具比写出代码更重要。**

数据结构的地基打好了，下一步该上难度了——非线性结构（树和图）即将到来。
