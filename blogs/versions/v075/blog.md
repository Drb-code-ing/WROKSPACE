# 微信公众号 Markdown 渲染组件：需求文档的验收清单、juice 内联样式的复制链路，与渐进式任务拆分

微信公众号编辑器对外部 HTML 的样式支持极其苛刻——**所有样式必须以内联 `style` 属性存在**，CSS 文件、`<style>` 标签统统不认。所以"做一个通用 Markdown 预览组件 + 一键复制到公众号"这件事，真正的难点从来不是把 Markdown 渲染出来，而是**复制到剪贴板的那一刻，如何把主题 CSS 变成每个元素身上的内联样式**。第六十四天的笔记把这样一个 NPM 组件项目（md-wx）完整走了一遍 SDD 流程：从需求文档 `proposal.md`，到技术架构 `design.md`，到玻璃拟态的高保真交互原型 `ui-design.html`，再到任务拆分 `tasks.md`。这篇文章按这条链路拆开讲：需求文档怎么把"要什么"变成可验收的清单、`juice` 怎么打通"复制到公众号"的内联样式链路、原型长什么样、任务又怎么渐进式推进。

---

## 一、需求文档：把"要什么"变成可验收的清单

`proposal.md` 开头一句话点明定位：**一个通用的 Markdown 预览组件，针对微信公众号文章的样式与排版进行优化，以 NPM 包形式发布**。组件接收外部提供的 Markdown 文本，实时展示排版结果，并支持把预览内容复制为可直接粘贴到公众号编辑器的富文本。

产品目标写了四条，全部围绕"通用、可集成"展开：

1. 降低其他项目接入公众号 Markdown 预览能力的成本；
2. 为 Markdown 内容提供稳定、清晰且适合公众号阅读的排版效果；
3. 让终端用户可以切换主题和预览设备，并将结果一键复制到公众号编辑器；
4. 允许组件使用方控制内置设置区域的显示，并按自身产品界面重新组织设置入口。

紧接着是**成功标准**——需求文档里最容易被跳过、却最值钱的一节。它把目标翻译成五条可验证的话：

- 外部 Markdown 变化后，预览及时同步，无需手动刷新；
- 五个预设主题均可正常使用，切换后内容与滚动位置不丢失、不重置；
- 手机和桌面视图均能完整展示文章，默认进入手机视图；
- 复制结果粘贴到公众号编辑器后，主要结构和视觉样式保留，无需重新基础排版；
- 内置设置区域可显示或隐藏；隐藏后，使用方仍可在组件外部提供相同的设置操作。

真正让这份需求文档"可执行"的，是它的**边界**。文档专门用一节写"内容与样式边界"：组件只负责展示外部传入的 Markdown，不负责创建、编辑、保存、管理源内容；图片只做展示，上传、存储、地址转换、公众号素材管理都不在范围内。更有一整章"本期不包含"，一口气划掉八条——不做 Markdown 编辑器、不做账号与云端草稿、不做文件导入、不做图片托管与素材库对接、不做直接发布、不做自定义主题编辑器、不强求保留微信不支持的样式、不做微信以外平台的专项适配。

**把"不做什么"写清楚，是需求文档最值钱的部分。** 否则 AI（或任何开发者）会顺着"markdown 组件"一路加出编辑器、云同步和发布后台，范围无限膨胀。边界先于功能，是这份 proposal 的第一课。

## 二、双层用户：组件使用方与终端用户

通用组件的需求文档有一个和普通产品不一样的设计点——**用户有两层**。`proposal.md` 把"用户与使用场景"拆成了：

- **组件使用方**：安装并集成 NPM 包的开发者或产品团队。诉求是向组件传入 Markdown 并展示预览、决定是否使用自带设置区、自行安排设置按钮的位置与顺序、把组件融入现有页面风格。
- **终端用户**：通过已集成产品查看和调整排版的内容创作者。诉求是实时看排版效果、快速比较和切换主题、在手机与桌面效果之间切换、把满意的结果复制到公众号。

配套的"典型使用流程"五步，正好串起两层用户：使用方在业务页面展示预览组件并提供 Markdown → 终端用户修改 Markdown 并看到实时预览 → 切换主题/视图 → 确认排版后执行复制 → 粘贴到公众号继续编辑或发布。

第 4.8 节"设置能力导出与自定义排版"把这个设计落成了具体规则，它是组件 API 的核心：**组件不强制使用内置顶部设置区，而是把主题切换、视图切换、复制这些能力暴露出去，让使用方自己摆按钮、排顺序、定横竖**。规则包括：外部设置操作的状态必须与预览组件保持一致（当前主题、当前视图、复制可用状态与结果反馈）；同一页面存在多个预览组件时，各自的设置与状态不得相互干扰；内置与外部两种展示方式不要求同时展示，若同时展示两处状态必须一致。

这就是"通用组件"区别于"自带页面"的分水岭：**能力内聚在组件里，UI 外放给使用方**。

## 三、技术选型：react-markdown 安全渲染 + juice 内联样式

`design.md` 的技术选型是一张"每个选择都带理由"的表：

| 关注点 | 选型 | 理由 |
| --- | --- | --- |
| 框架 | React 18+ | 庞大的社区与生态、组件化开发模式、Hooks 管理状态与副作用 |
| 构建 | Vite | 极速冷启动与 HMR；基于 Rollup 输出高度优化的生产代码 |
| 样式 | CSS Modules + PostCSS | 局部作用域避免全局污染；PostCSS 支持最新 CSS 特性并自动加浏览器前缀 |
| Markdown 解析 | `react-markdown` + `remark-gfm` | 流行的 Markdown 转 React 组件库，安全性高、可定制强；`remark-gfm` 支持表格、删除线等 GFM 语法 |
| 代码高亮 | `react-syntax-highlighter` | 支持多种语言与丰富主题（如 `github-dark`），满足需求中的代码块要求 |
| 样式内联化 | `juice` | 把 CSS 规则转换为 HTML 内联样式，是"复制到公众号"功能的核心 |

其中 `react-markdown` 的选择暗含一个安全考量：它把 Markdown 解析成 React 组件树而非直接拼 HTML 字符串，天然规避了 `dangerouslySetInnerHTML` 注入 XSS 的问题——这对一个"接收任意外部 Markdown"的通用组件是硬要求。

目录结构按高内聚低耦合设计：`components/`（Previewer、SettingsPanel、CodeBlock 三个可复用组件）、`styles/themes/`（主题 CSS Modules）、`hooks/`、`utils/`、`constants/`。编码规范用 Prettier 统一格式、ESLint + `eslint-plugin-react` 保质量、组件 PascalCase、函数/变量 camelCase。

## 四、核心难点：公众号只认内联 style，juice 的复制链路

公众号编辑器对外部 HTML 的样式支持有严格限制，核心要求一句话：**所有样式必须以内联 `style` 属性的形式存在**。这是 `design.md` 明确写出的约束，也是整个项目最独特的技术难点。

`design.md` 给出了六步复制流程：

1. **用户点击"复制"**：触发 `handleCopy` 函数；
2. **获取渲染后 HTML**：通过 `ref` 获取预览区域 `div` 的 `innerHTML`；
3. **获取当前主题 CSS**：根据用户选择的主题，动态加载对应主题的 CSS 文件内容（字符串形式）；
4. **调用 `juice` 进行转换**：把 HTML 字符串和主题 CSS 字符串作为参数传进去，`juice` 解析 CSS，把所有匹配的样式规则应用为对应 HTML 元素的 `style` 属性；
5. **处理代码块高亮**：`react-syntax-highlighter` 默认生成的 `<span>` 自带 `style`，这部分微信可直接识别，无需额外处理；
6. **写入剪贴板**：用 `navigator.clipboard.writeText` 把处理后的 HTML 字符串复制到用户剪贴板。

`juice` 干的活，本质是**"CSS 选择器 → 元素匹配 → 内联注入"**：它把样式表里每条规则的选择器在 HTML 上匹配，命中就把声明的样式合并进该元素的 `style`。一个最直观的例子——CSS 里的

```css
.title { color: blue; }
```

经过 `juice` 后变成

```html
<h1 class="title" style="color: blue;">…</h1>
```

主题颜色、字体、边距、代码高亮，全部从"一份主题 CSS"变成"每个元素身上的内联属性"，粘贴到公众号编辑器后就能做到"所见即所得"。这就是这份需求文档第 4.5 节"复制到微信公众号"的验收基准：不要求与组件预览像素级一致，但**不得出现结构错乱、不得必须重新做基础排版**。

## 五、玻璃拟态高保真交互原型：把界面共识固化成 HTML

README 里讲到一个方法：需求文档、技术文档确定后，利用 AI 快速构建一个**可交互的视觉原型**（产品经理 MVP 产品，用于演示）——让"产品界面和交互是什么样的"有一个看得见摸得着的东西，设计师和程序员基于它对齐审美、性能、开发流程，后续做二次开发。

`ui-design.html` 就是这个高保真交互原型，一份 718 行的纯 HTML/CSS/JS。它实现了一套完整的**玻璃拟态（Glassmorphism）设计语言**：半透明白玻璃工具栏（`backdrop-filter: blur(24px) saturate(145%)` + rgba 半透明白 + 内高光边框 + 大阴影）、`min-height: 100svh` 的居中舞台、`cubic-bezier` 缓动的设备框宽度过渡动画。交互上它把需求里最核心的几个功能都做出来了：

- **固定顶部工具栏**：主题选择下拉、手机/桌面视图切换组、复制按钮，配悬停 tooltip；
- **5 个主题色板**：minimal（白/绿）、purple（紫）、wechat（微信绿）、tech（科技蓝）、retro（复古橙），每个都是选中状态有明确勾选反馈的下拉菜单；
- **手机/桌面视图**：手机设备框宽度 `min(430px, calc(100vw - 32px))`，切换时宽度和圆角带过渡动画；
- **完整交互反馈**：`.control:hover` 背景变深、`:active` 缩放 `.96`、`:focus-visible` 高亮焦点环、tooltip 渐显——鼠标和键盘都可用。

原型里还照顾了可访问性：交互元素支持 Tab 导航、焦点环明确、功能不只靠颜色表达。**原型的价值是让"第一次创造"可见**——文档是文字，原型是画面，两者加在一起才构成对产品界面和交互的完整共识。

## 六、任务拆分：渐进式开发，每阶段都有可见效果和验收标准

需求和技术都定了，`tasks.md` 把项目拆成可推进的任务。拆分原则四条：

1. **渐进式开发**：从基础功能到高级特性，每个阶段都有可见成果；
2. **模块化设计**：按组件和功能模块拆分，降低耦合度；
3. **优先级导向**：核心功能优先，增强功能其次；
4. **可测试性**：每个阶段都能独立测试和验证。

任务的颗粒度到"每阶段有预期效果 + 每任务有可勾选清单 + 有验收标准"。看前三个阶段的骨架：

- **阶段一 · 项目基础架构搭建**：任务 1.1 项目初始化和配置（Vite + React、ESLint + Prettier、`vite.config.js` 同时配开发模式和库模式、CSS Modules + PostCSS、标准目录结构）；任务 1.2 基础样式系统（global.css、玻璃拟态基础样式、5 个主题的 CSS Modules 文件、响应式断点、动画过渡类）。
- **阶段二 · 核心预览功能**：任务 2.1 Markdown 渲染引擎（集成 `react-markdown` + `remark-gfm`、创建 Previewer 核心组件、支持基础语法 + GFM 扩展、实时渲染）；任务 2.2 预览容器组件（PreviewContainer、预览头部、白色圆角内容区、玻璃拟态容器效果、响应式适配）。
- **阶段三 · 主题系统**：任务 3.1 主题管理系统（`useTheme` 自定义 Hook、主题 Context 状态管理、主题常量配置、切换逻辑、样式动态加载）；任务 3.2 设置面板组件（SettingsPanel、ThemeSelector、粘性定位 + 玻璃拟态、下拉菜单交互、悬停点击动画）。

每个任务的验收标准都写得很具体——比如任务 1.1 的验收是"项目能启动开发服务器、代码格式化和检查工具正常工作、目录结构符合架构设计规范"；任务 2.1 是"能正确渲染各种 Markdown 语法、内容变化实时更新、GFM 扩展正常工作"。**这种"任务可勾选、完成可验证"的写法，正是让 AI 一次只做一件可验收的事**，每一步推进都能人工验收，而不是攒到最后一起翻车。

## 七、AI 辅助需求：头脑风暴、tavily 实时调研与项目规则

README 里还沉淀了一套"怎么驱动 AI 做需求"的方法，和上面的文档产出是配套的：

**需求文档怎么做。** 第一步是头脑风暴——用 Skill 让 AI 吃不同维度（核心功能、用户界面、可配置性等）分析并提出需求建议；需求清楚后再进入编写。产品原型用蓝狐、figma、Google Stitch 这类工具（配 MCP）做，AI coding 生成一个可以交互、看到界面的 MVP。

**技术架构怎么调研。** 提到 `tavily`——专为大模型与 AI Agent 打造的搜索 API，可输出结构化网页检索内容，用来给大模型补充实时网络信息、**缓解幻觉问题**。拿不准的技术选项，让 AI 去搜、去验证，而不是凭记忆硬编。

**任务拆分像带新员工。** 不能直接抛给 AI 一个宏大任务然后指望它完美交付——两个原因：一是**上下文限制**，处理过程会遗忘早期的关键细节；二是**细节处理能力下降**，一次性处理的内容越多，AI 对每个细节的关注度越低。所以要把复杂项目拆成清晰、具体、可执行的小任务，先启动任务划分，再审查与迭代。

**项目规则约束 AI 行为。** 用四条规则让 AI 像团队成员一样守规矩而不是自由发挥：任务执行边界（何时开始何时停止）、代码风格（生成代码的统一性和可读性）、技术栈遵循（使用指定的语言和框架）、沟通方式（规定 AI 如何响应和提问）。

这一整套下来，需求文档（proposal）、技术架构（design）、原型（ui-design.html）、任务拆分（tasks）四件套闭环，AI 从"一个飘忽的目标"变成"有边界、有顺序、可验收的工程"。

## 面试问答

**问：为什么微信公众号编辑器对 CSS 支持这么苛刻？项目怎么解决？**

> 公众号编辑器对外部 HTML 的样式支持有严格限制，核心要求是所有样式必须以内联 `style` 属性形式存在，CSS 文件和 `<style>` 标签不会被保留。解决方式是 `juice` 库：把渲染后的 HTML 和当前主题 CSS 字符串一起传给 `juice`，它会解析 CSS、把每条规则的选择器在元素上匹配，命中就把声明合并进该元素的 `style` 属性，实现"所见即所得"的复制。

**问：`react-markdown` 相比 `dangerouslySetInnerHTML` 有什么安全优势？**

> `react-markdown` 把 Markdown 解析成 React 组件树而不是拼接 HTML 字符串，天然规避了直接注入 HTML 带来的 XSS 风险；`dangerouslySetInnerHTML` 会把任意 HTML 原样插进 DOM，配合不可信的 Markdown 输入很容易被注入脚本。对一个接收任意外部 Markdown 的通用组件，这是硬性要求。

**问：需求文档为什么要专门写"本期不包含"？**

> 因为不划边界，需求会无限膨胀——顺着"markdown 组件"很容易一路加出编辑器、云同步、发布后台、图片托管。把不做什么写清楚，范围先于功能，AI 或开发者才不会自由发挥，验收也有了明确依据。

**问："设置能力导出"解决什么问题？**

> 它解决"通用组件如何融入不同宿主产品"的问题：组件把主题切换、视图切换、复制等能力暴露出去，让使用方自己组织按钮位置、顺序、横竖排列，而不是被内置设置区绑死。配套规则是外部操作状态必须与预览组件保持一致、多实例互不干扰。

**问：通用组件为什么要把用户分成"使用方"和"终端用户"两层？**

> 因为通用组件卖给的是集成它的开发者（使用方），而真正用起来的是产品里的内容创作者（终端用户）。需求必须同时满足两层：使用方要能传 Markdown、控制设置区、自定义布局；终端用户要实时预览、切主题、切设备、复制到公众号。只有需求文档先分清这两层，产品目标才不会错位。

**问：`tasks.md` 的任务拆分有什么原则？**

> 四条：渐进式开发（从基础到高级，每阶段有可见成果）、模块化设计（按组件/模块拆分降低耦合）、优先级导向（核心功能优先）、可测试性（每阶段能独立验证）。落地形态是每阶段有"预期效果"、每任务有可勾选清单和"验收标准"，让 AI 一次只做一件可验收的事。

**问：`tavily` 在大模型 / AI Agent 里起什么作用？**

> 它是专为大模型与 AI Agent 打造的搜索 API，输出结构化网页检索内容，给大模型补充实时网络信息，核心作用是缓解幻觉——拿不准的技术选型让 AI 去实时检索验证，而不是凭记忆硬编。

## 结语：一个 NPM 组件从"要什么"到"怎么做"的完整链路

第六十四天这套材料，本质是用 SDD 的方式把一个 NPM 组件项目完整规划了一遍：

```text
proposal.md     要什么：定位、目标、成功标准、边界（本期不包含）
design.md       怎么做：技术选型、目录结构、juice 内联样式复制链路
ui-design.html  长什么样：玻璃拟态高保真交互原型
tasks.md        按什么顺序：阶段一基础 → 阶段二核心预览 → 阶段三主题系统
───────────────────────────── 第一次创造（心智创造）
      ↓ 需求/设计/任务驱动
代码             按 tasks 渐进式实现（第二次创造）
```
