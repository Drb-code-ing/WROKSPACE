# Next.js 全栈框架：CSR 与 SSR 的本质差异、SEO 的三层做法，与 App Router 的文件即路由

前端写到一定阶段，会撞上一个绕不开的问题：**同一段 React 组件，放进 SPA 和放进 Next.js，爬虫看到的是两个世界。** SPA 的 HTML 里只有一个 `#root` 空壳和一行 `<script>`，搜索引擎爬进来什么内容都抓不到；Next.js 却能把 `jsx + 数据` 在服务器上编译成一段实实在在的 HTML。这个分水岭，就是第五十七天笔记从头捋到尾的主题——CSR 和 SSR，以及它背后的 SEO。

一句话概括这一天：**"组件到底在哪里渲染"，是理解 Next.js 一切能力的钥匙。**

---

## 一、Next.js 是谁：React 的全栈框架

先厘清三个名字，笔记开头就把它们摆在一起：

- **Next** 是 React 的全栈框架；
- **Nuxt** 是 Vue 的全栈框架；
- **Nest** 是后端框架（纯服务端，别和前两个混了）。

Next 的定位是"全栈"：既能写页面（前端），也能写 API（后端）。它背靠 Vercel，SEO 做得非常好，所以很多 AI 产品直接拿 Next.js 做官网——因为官网的命根子就是"被搜索引擎收录、被爬虫读懂"。

创建项目一句话：

```bash
npx create-next-app@latest
```

选默认配置，会得到一套组合：`react` / `react-dom`（界面）、`typescript`（类型）、`tailwindcss`（样式）、`eslint`（代码风格）。这套默认栈就是 Next 给 React 开发者准备的"开箱即用"。

---

## 二、SPA：体验好，但天生不 SEO

为什么要有 Next？得先看 SPA 的账本。笔记把 SPA 的好处和短板各列了一栏。

**SPA 的好处**——体验好：

- 组件在前端挂载，用 `useEffect` 去异步请求数据，页面**不需要刷新**；
- 前端路由让页面切换又快又顺，体验直逼原生 App。

**SPA 的短板**——不为 SEO 而生：

- 它抄的是原生 App 的体验。移动端超级 App 里约 80% 的页面都是 SPA，原生壳（20%）加 WebView 组件来兜底，前端一套 HTML 只写一次，不用写两套；
- 但 SPA 根本不是给浏览器搜索引擎（百度、谷歌、必应）准备的。PC 时代浏览是流量入口、SEO 是命；而 SPA 的 HTML 里只有 `#root` 空壳，**爬虫抓不到任何内容**。

这就是笔记里那句关键对照：

```text
#root (SPA)  ->  seo (react jsx -> html) (next.js)
```

SPA 交付的是一个 `#root` 空节点，Next.js 交付的是"jsx 编译后的 html"。SEO 的差距，从这一步就注定了。

---

## 三、CSR 与 SSR：组件到底在哪里渲染

SEO 的根本，笔记用一句话点破：**组件到底在哪里渲染。**

- **CSR（Client Side Rendering，客户端渲染）**：组件在用户的浏览器里渲染，对应 SPA；
- **SSR（Server Side Rendering，服务器端渲染）**：组件在服务器上渲染，对应 Next.js。

回到 CSR 的完整链路，笔记把它拆成两端：

```text
Server 前端项目所在的服务器
  请求 /todos
  ↓ 返回 index.html（只有 #root + <script src="main.js">）
Client 用户的浏览器
  执行 main.js → App.jsx → Todos.jsx
  ↓ 组件在 client 端挂载、运行
```

爬虫是通过 URL 来爬的。它爬到 `/todos` 时，服务器只给它一个 `index.html`，里面是 `#root` 和 `script` 两个节点——**内容还没渲染出来，爬虫就走了。** 等用户在浏览器里跑完 JS，页面才"活"过来，但这已经和搜索引擎没关系了。

---

## 四、从前后端分离到全栈：`/todos` 返回 JSON 还是 HTML

同样是 `/todos` 这个路由，两种架构返回的东西完全不同。笔记用 Java 全栈做对照讲清了这件事。

**前后端分离**：`/todos` 是 API，返回的是数据——

```text
/todos  api  ->  todos json 数组
```

浏览器拿到 JSON，再交给 React 在前端拼页面。爬虫爬到 `/todos`，只看到一串 JSON 数组（甚至一个空壳），没有可读内容。

**全栈项目**：`/todos` 返回的是**React 组件编译过后的 HTML**——

```text
jsx + todos(数据) = 服务端 UI html   （SSR）
```

关键在于"服务器端不是 DOM，是字符串的格式化"。React 组件只要**不做事件监听、不用 `useEffect`**，它本质上就是"组件函数 + 数据"，完全可以在服务器上把 jsx 和 todos 数据编译成一段 HTML 字符串返回。爬虫爬到 `/todos`，拿到的是已经带内容的完整页面。

这就是 SSR 的核心：**把"渲染"这件原本发生在浏览器的事，提前到服务器上做。**

---

## 五、App Router：约定大于配置，文件即路由

Next.js 的语法理念是"**约定大于一切**"，App Router 是这套理念的集中体现：

- **不需要手动建路由表**，文件本身就是路由，天然支持嵌套路由；
- `page.tsx` 就是页面；
- `layout.tsx` 是布局文件（nav 等共用的部分）；
- Next.js 给 React 开发者的是开箱即用的利器。

渲染规则，笔记写得很清楚。以 `/about` 为例：

```text
/about  ->  后端路由
  先到 layout.tsx（布局文件）
  再到 about/page.tsx（完成组件编译 tsx -> html）
```

访问一个路径，Next 先找到对应的 `layout.tsx` 搭好骨架，再把 `page.tsx` 编译成 HTML 塞进去。**一个文件对应一条路由，路径结构就是目录结构。**

## 六、Demo 源码：根布局、服务端组件与嵌套布局

demo 里 `app/layout.tsx` 是整站的根布局，最能说明"layout + metadata + 嵌套"三件事：

```tsx
// app/layout.tsx
export const metadata: Metadata = {
  title: "Create Next App",
  description: "Generated by create next app",
};

export default function RootLayout({ children }: LayoutProps<"/">) {
  return (
    <html lang="en">
      <body>
        <nav>
          <ul>
            <li><Link href="/">首页</Link></li>
            <li><Link href="/about">关于</Link></li>
            <li><Link href="/dashboard">后台</Link></li>
          </ul>
        </nav>
        {children}
      </body>
    </html>
  );
}
```

这里能读出三层：

1. **`export const metadata`**——这就是 SEO 第一层的落点：`title` 和 `description` 会被渲染进页面的 `<head>`，直接决定爬虫怎么认识你；
2. **`<nav>` + `{children}`**——导航是整站共用的，写在根 `layout` 里；`{children}` 就是当前路由的 `page` 内容；
3. **`<Link>`**——Next 的客户端导航，替代 `<a>`，切换时只更新变化的部分。

再看 `app/page.tsx`，它是最纯粹的"服务端组件"：

```tsx
// app/page.tsx
// 服务器端组件
// 在服务器端 react node 的方式运行
// jsx -> html
export default function Home() {
  return (
    <h1>Hello World</h1>
  )
}
```

没有 `useState`、没有 `useEffect`，就是一个返回 jsx 的函数。这样的组件**能在服务器上直接编译成 HTML 字符串**——这就是 SSR 的地基。

嵌套路由靠"目录套目录 + 各自的 layout"实现。`app/dashboard/layout.tsx` 是 dashboard 这一层的布局：

```tsx
// app/dashboard/layout.tsx
import Link from "next/link";

export default function DashboardLayout({ children }: { children: React.ReactNode }) {
  return (
    <div>
      {children}
      <nav>Nav
        <Link href="/dashboard/settings">设置</Link>
      </nav>
    </div>
  )
}
```

于是路由结构长这样：

```text
app/
  layout.tsx              # 根布局（整站导航）
  page.tsx                # /          首页
  about/page.tsx          # /about     关于
  dashboard/
    layout.tsx            # /dashboard 这一层共用的布局
    page.tsx              # /dashboard 后台
    settings/page.tsx     # /dashboard/settings 设置
```

访问 `/dashboard/settings` 时，Next 会**逐层套布局**：根 `layout.tsx` 包 `dashboard/layout.tsx`，再包 `settings/page.tsx`。这就是"嵌套路由"——目录结构即路由结构，布局逐层叠加。

对照的 `spa-demo/src/App.jsx` 则是最典型的 CSR：一个 `useState(0)` 的计数器，点击按钮 `setCount` 更新数字。这段逻辑只能在浏览器里跑，因为服务器上没有"点击"这回事——**同一份组件，在 SPA 里是 CSR，在 Next.js 里（无状态时）是 SSR，差别就在这。**

## 七、SEO 的三层做法

笔记最后把 SEO 的落地归纳成三层，从浅到深：

**第一层：告诉别人你是谁。** 用 `title` 说明"这是做什么的"、`description` 说明"有什么价值"、`keywords` 给出关键词：

```html
<title>这是一个标题</title>
<meta name="description" content="这是一个描述" />
<meta name="keywords" content="这是一个关键词" />
```

在 Next 里，这一层对应 `layout.tsx` 里的 `export const metadata`。

**第二层：做内容。** 用户来，是因为有他们想要的内容。标题描述只是门面，真正留住人、让爬虫持续收录的是内容本身。

**第三层：SSR 服务器端渲染。** 像 `/post/:id` 这种"一个页面可能有千万篇"的动态内容，如果靠 CSR，爬虫对每篇都只能爬到空壳；而 SSR 让整站成千上万页都被搜索引擎收录并加权。**第三层是 SEO 的胜负手，也是 Next.js 相对纯 SPA 的核心价值。**

顺带一提，笔记还点到了 GEO（Generative Engine Optimization，生成式引擎优化）：当用户入口变成豆包这类 AI，生成答案时能带上你的内容和购买链接，就成了一种新的"被看见"。SEO 的边界正在从搜索引擎向生成式引擎延伸。

## 八、面试问答

**问：Next、Nuxt、Nest 分别是什么？**

> Next 是 React 的全栈框架，Nuxt 是 Vue 的全栈框架，Nest 是后端框架。Next 既能写页面（前端）也能写 API（后端），背靠 Vercel，SEO 做得好，很多 AI 产品用它做官网。

**问：CSR 和 SSR 的本质区别是什么？**

> 本质是"组件在哪里渲染"。CSR（客户端渲染）组件在用户浏览器里渲染，对应 SPA，服务器只返回 `#root` + `<script>` 的空壳 HTML；SSR（服务器端渲染）组件在服务器上渲染，对应 Next.js，服务器返回 jsx + 数据编译后的 HTML。SSR 让爬虫能直接抓到带内容的页面，是 SEO 的根本。

**问：为什么 SPA 的 SEO 很差？**

> SPA 的 `index.html` 里只有 `#root` 空节点和 `<script src="main.js">`，真正的内容要等浏览器执行 JS 挂载后才出现。爬虫通过 URL 爬取时只拿到空壳，抓不到任何可读内容，所以 SPA 天生不 SEO。

**问：同样是 `/todos` 路由，前后端分离和全栈项目分别返回什么？**

> 前后端分离时 `/todos` 是 API，返回 `todos` 的 JSON 数组，前端拿数据自己拼页面；全栈项目里 `/todos` 返回 React 组件编译过后的 HTML（`jsx + todos 数据 = 服务端 UI html`），爬虫拿到的是带内容的完整页面。

**问：Next.js App Router 的"约定大于配置"体现在哪？**

> 不需要手动建路由表，文件本身就是路由：`page.tsx` 是页面，`layout.tsx` 是布局文件，目录结构即路由结构，天然支持嵌套路由。访问 `/about` 时先到根 `layout.tsx` 搭骨架，再编译 `about/page.tsx` 塞进去；访问 `/dashboard/settings` 则逐层套 `layout.tsx` → `dashboard/layout.tsx` → `settings/page.tsx`。

**问：什么样的 React 组件能做 SSR？**

> 不做事件监听、不用 `useEffect` 的组件，本质是"组件函数 + 数据"，可以在服务器上用 react/node 的方式运行，把 jsx 编译成 HTML 字符串。带交互状态（如 `useState` 计数器）的组件只能在浏览器里跑，属于 CSR。

**问：SEO 的三层做法是什么？**

> 第一层用 `title`/`description`/`keywords` 告诉别人你是谁；第二层做内容，给用户来的理由；第三层用 SSR 服务器端渲染，让整站动态内容（如 `/post/:id` 的千万篇）都被搜索引擎收录并加权。第三层是 SEO 的胜负手。

---

## 结语：从"组件在哪里渲染"出发

这一天没写复杂算法，而是把 Next.js 的入门地基打实了——理解 Next.js 的所有能力，都从"组件在哪里渲染"这一问出发：

```text
CSR     组件在浏览器渲染     SPA         #root 空壳，不 SEO
SSR     组件在服务器渲染     Next.js     jsx+数据 -> html，SEO
App Router   文件即路由      page.tsx 页面 / layout.tsx 布局，嵌套叠加
SEO     三层做法            metadata -> 内容 -> SSR
```

动手前，拿这份清单自检：

- [ ] 能否说清 CSR 和 SSR 的本质区别是"组件在哪里渲染"？
- [ ] 能否解释为什么 SPA 的 `#root` 空壳导致 SEO 差？
- [ ] 能否区分"前后端分离返回 JSON"与"全栈返回 HTML"两种 `/todos`？
- [ ] 能否说出 App Router 里 `page.tsx` 和 `layout.tsx` 各自职责？
- [ ] 访问 `/dashboard/settings` 时，布局是如何逐层套起来的？
- [ ] 什么样的组件能做 SSR，什么样的只能在浏览器跑？
- [ ] SEO 三层做法分别对应什么，为什么第三层（SSR）是胜负手？

Next.js 不是"又一个框架"，它用 SSR 补上了 SPA 在 SEO 上的短板，再用"文件即路由"把全栈开发的门槛压到最低。把今天的地基打牢，后面的数据获取、服务端组件、动态渲染才有处落脚。
