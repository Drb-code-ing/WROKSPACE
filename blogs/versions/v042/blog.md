# 从 Prompt 到可复用能力：Agent Skills 的工程本质、SKILL.md 协议与面试通关指南

## 引言

v033 给 Agent 补全了六要素公式：

```text
Agent = LLM + Memory + Tool + RAG + MCP + Skills
```

后面几篇把其中几块拆得很细：

| 版本 | 补齐的组件 | 解决的问题 |
|------|-----------|-----------|
| v036 / v037 | MCP + Tool | Agent 如何跨进程、跨语言调用外部能力 |
| v038 / v040 / v041 | RAG | Agent 如何检索私有知识、如何把文档加工成可检索知识块 |
| v039 | 交互层（流式） | 回答如何边生成边呈现 |
| **v042（本篇）** | **Skills** | **如何把重复的专业流程固化成可触发、可复用、可评测、可演进的能力包** |

注意边界：第三十八天仓库里还有「流式输出」和「RAG」相关提交，但**本文只更新 Skills**。不把同日其他主题硬塞进来——Skills 值得单独成篇，而且值得写透。

第三十八天的 skill 初步笔记里，有一句很值钱的判断：

> **前有 MCP，后有 Skills。**

MCP 解决“Agent 能调用什么外部工具”；Skills 解决“Agent 在具体岗位上怎么按专业标准干活”。一个给手脚，一个给手艺。

```text
MCP / Tool  →  能做什么动作（读文件、搜网页、调 API）
Skills      →  按什么专业流程做（会议纪要、前端设计、日报整理）
RAG         →  知道什么私有知识
Memory      →  记得谁、记得上次做到哪
```

本文基于 `ai/skills` 学习笔记与本地 `.agents/skills` 实践（会议纪要、AI 日报、skill-creator），把 Skills 从“听说过这个词”推进到：

1. **面试能讲透**——定义、边界、机制、失败模式；
2. **落地能封装**——从场景到 `SKILL.md` 到评测；
3. **上线能治理**——版本、权限、冲突、安全、团队共享。

## 一、何为 Skill：不是提示词文件，是能力蒸馏

### 1.1 一句话定义

**Skill（技能）是把专业人士的处理方式，蒸馏进一个文件夹，再用 `SKILL.md` 标准化表达出来的可复用能力包。**

它不是：

- 又一段每次手动粘贴的 Prompt；
- 又一个 Function Calling 工具定义；
- 又一份 README 说明文档；
- 又一个“自定义 GPT”聊天角色卡的简单换皮。

它是：

- **可被 Agent 自动发现并触发的工作流说明**；
- **把“你怎么做这件事”固化成“Agent 默认就会这么做”**；
- **在 token 经济下，用最小上下文成本换取专业输出质量**；
- **可版本化、可评测、可在团队间迁移的能力资产**。

### 1.2 笔记里的三个关键词

第三十八天笔记把 Skill 压成了三个彼此咬合的词：

| 关键词 | 含义 | 工程含义 |
|--------|------|---------|
| **技能** | 专业岗位的处理方式 | 不是泛泛“帮我写”，而是“按会议秘书标准产出纪要” |
| **OPC / 超级个体** | 一个人 + AI 完成一个小团队的工作 | 每个 Skill 相当于一个虚拟岗位员工 |
| **LLM tokens 经济** | 上下文有限且昂贵 | 好 Skill 少解释、少重试、少跑偏，直接省 token |

核心公式可以写成：

```text
智能个体 = 通用 LLM 智能 + 高技能（Skills）+ 记忆（Memory）+ 工具（Tools/MCP）+ 知识（RAG）
```

只有智能没有技能：你得到一个“什么都懂一点、什么都做不专业”的聊天机器人。  
只有技能没有智能：你得到一堆死板脚本，遇边缘情况就崩。  
两者合在一起，才是 OPC 语境下的“问出专业问题、干专业事情”的超级个体。

### 1.3 一堆虚拟数字人，而不是一个万能对话框

笔记里的想象很直观：

```text
PPT Skill        → 专业 PPT 设计师
前台 Skill       → 公司前台话术与流程
前端 Skill       → front design 规范与交付标准
数据分析 Skill   → 指标口径、图表与结论结构
会议纪要 Skill   → 会议小秘书
AI 日报 Skill    → 行业信息官
        │
        ▼
全部进入同一个 Agent Host
```

你不是在“训练一个更大的模型”，而是在**给同一个大脑装配不同岗位技能**。这和公司招人很像：模型是通用人才，Skill 是岗位 SOP + 专业判断标准。

### 1.4 为什么叫“蒸馏”，不叫“保存”

“保存 Prompt”只是把文本归档。  
“蒸馏能力”意味着你完成了四次抽象：

```text
1. 从一次成功对话中抽出可复用步骤
2. 从个人习惯中抽出可教给别人的标准
3. 从模糊偏好中抽出可验收的输出契约
4. 从“我觉得差不多”中抽出可评测的断言
```

所以 Skill 的质量标准不是“写得很长”，而是：

> **换一个会话、换一个相似任务、换一个执行 Agent，结果是否仍然专业且稳定。**

> **面试金句：Skill 是能力的产品化封装，不是 Prompt 的文件化保存。**

## 二、用 AI 的两个阶段，以及更长的三阶段史

### 2.1 第一批人：永远从第 0 句开始

笔记里把 2026 年前后用 AI 的人分成两批。

第一批人每次打开对话框，第一句总是在解释：

```text
我是谁？
我在做什么项目？
我们公司的风格是什么？
这次任务的约束有哪些？
输出必须是什么格式？
```

他们依赖的是：

- message 对话列表；
- 临时粘贴的长 Prompt；
- 运气一般的记忆窗口。

问题很明显：

1. **重复解释成本高**——同样的背景每天讲三遍；
2. **质量不稳定**——今天模型听懂了，明天换会话又漂移；
3. **无法沉淀组织能力**——高手的流程停在个人聊天记录里，团队无法复用；
4. **无法回归**——改了一句提示词，不知道会破坏哪些旧场景。

这不是“在用 AI 工作”，更像“每天重新培训一个实习生”。

### 2.2 第二批人：Skill + Memory，打开就能干活

第二批人从 2026 年的 openclaw / hermes / Claude Skills 路线开始，工作方式变了：

```text
打开 Agent
  → 它已经知道你是谁（Memory / 用户画像）
  → 它已经加载你的工作技能（Skills）
  → 你直接说“把这份转写做成纪要”
  → 它按岗位标准执行，而不是先问你“纪要长什么样”
```

差别不在模型智商，而在**工作流是否被系统化封装**。

| 维度 | 第一批（对话驱动） | 第二批（Skill 驱动） |
|------|-------------------|---------------------|
| 启动成本 | 每次重新解释 | 打开即用 |
| 质量来源 | 当场 Prompt 水平 | 沉淀后的技能标准 |
| 复用性 | 个人会话内 | 团队 / 项目 / 多 Agent 共享 |
| 演进方式 | 改聊天习惯 | 改 SKILL.md + 评测 |
| token 成本 | 高（重复上下文） | 低（按需加载技能） |
| 组织资产 | 几乎没有 | Skills 目录就是能力资产库 |

### 2.3 AI 使用的三个阶段

笔记还把更宏观的 AI 使用史分成三阶段，用来定位 Skills 的位置：

```text
阶段 1：把 AI 当搜索引擎
  提问 → 得到答案 → 关掉
  本质：查字典，不是协作

阶段 2：研究提示词（Prompt Engineering）
  学会写角色、约束、示例、输出格式
  本质：每次手动编程模型行为

阶段 3：Skills / Agent 工作流
  把高频专业流程固化成可触发能力
  本质：把提示词工程升级为能力工程
```

**Prompt Engineering 没有过时，它被吸收进了 Skill 工程。**  
Skill 的正文，本质上就是“写得好、测过、可复用的专业 Prompt + 工作流 + 资源”。

还可以补一刀更工程化的理解：

```text
Prompt Engineering   = 单次请求的行为编程
Context Engineering  = 给模型装什么上下文
Skills Engineering   = 把稳定工作流产品化，并接入触发与评测
```

> **关键认知：从“会写 Prompt”到“会封装 Skill”，是从个人技巧到组织能力的跃迁。**

## 三、Skill 在 Agent 六要素中的位置

### 3.1 再看六要素，但这次只拆 Skills

v033 说过：Skills 解决的是 LLM“不会做复杂任务”的短板。这里把它和其他组件严格对照，避免面试时概念串台。

| 组件 | 解决什么 | 典型形态 | 和 Skill 的关系 |
|------|---------|---------|----------------|
| **LLM** | 推理、规划、生成 | 模型本身 | Skill 指导 LLM 如何推理与产出 |
| **Memory** | 跨会话记住用户与历史 | 数据库 / 摘要 / 画像 | Skill 可读取 Memory，但不等于 Memory |
| **Tool** | 执行原子动作 | 函数、CLI、API | Skill 会编排多个 Tool |
| **MCP** | 标准化跨进程工具协议 | MCP Server | Skill 可规定何时用哪个 MCP 工具 |
| **RAG** | 检索私有知识 | 向量库 + Retriever | Skill 可规定检索策略与引用规范 |
| **Skills** | 固化专业复杂流程 | `SKILL.md` + 资源目录 | 能力层 / 岗位层 |

一句话区分：

```text
Tool  = 螺丝刀
MCP   = 统一的工具插座标准
RAG   = 说明书资料库
Memory= 工牌与工作日志
Skill = 老师傅教你“什么时候用哪把螺丝刀、按什么顺序装、验收标准是什么”
```

### 3.2 易混概念对照矩阵

这是面试高频送命题，建议直接背结构。

| 概念 | 核心问题 | 生命周期 | 触发方式 | 是否执行动作 |
|------|---------|---------|---------|-------------|
| 临时 Prompt | 这一次怎么说 | 单次 | 用户手写 | 否（只是指令） |
| System Prompt | 你是谁、全局规则是什么 | 会话/应用级 | 始终生效 | 否 |
| Tool | 能不能做这个原子动作 | 长期 | 模型 function call | 是 |
| MCP | 工具如何标准化接入 | 长期 | 连接 Server 后可用 | 是（经协议） |
| RAG | 私有知识在哪、怎么找 | 长期 | 检索链路 | 否（取知识） |
| Subagent | 是否拆给另一个执行体 | 任务级 | 主 Agent 委派 | 可 |
| Custom GPT / 角色卡 | 某个聊天机器人的固定人设 | 应用级 | 进入该 Bot | 视实现 |
| **Skill** | **这类专业任务默认怎么做完** | **长期资产** | **description 匹配后加载** | **编排动作与知识** |

### 3.3 Skill ≠ Prompt，≠ System Prompt，≠ Tool

#### Skill vs 临时 Prompt

| | 临时 Prompt | Skill |
|--|------------|-------|
| 生命周期 | 一次对话 | 项目 / 团队长期资产 |
| 触发方式 | 用户手写或粘贴 | Agent 根据 description 自动匹配 |
| 结构 | 自由文本 | YAML + Markdown + 可选资源 |
| 演进 | 靠人记 | 可版本化、可评测、可回归 |

#### Skill vs System Prompt

System Prompt 更像“人格与全局规则”：你是谁、安全边界、默认语气。  
Skill 更像“岗位技能包”：遇到某类任务时加载的专项 SOP。

一个 Agent 通常：

- **只有一份**全局 system / 身份设定；
- **可以有很多个** Skills，按任务触发加载。

#### Skill vs Tool

Tool 回答“能不能做这个动作”。  
Skill 回答“这件事该按什么专业流程做完”。

例如“生成会议纪要”：

- Tool 可能是：读文件、写文件、搜索日历；
- Skill 规定：先通读、去口语、抽主题、列行动项、不确定写待确认、按固定模板输出。

没有 Skill，模型也会“尽量总结”；有了 Skill，输出才稳定地像“会议小秘书”，而不是“随便写个摘要的大学生”。

#### Skill vs Subagent

Subagent 是**执行单元拆分**（另起一个上下文/角色去干活）。  
Skill 是**能力说明加载**（在当前或子执行体中注入岗位 SOP）。

常见组合：

```text
主 Agent 识别“这是会议纪要任务”
  → 加载 meeting-minutes Skill
  → 必要时再委派 subagent 处理超长转写
```

Skill 解决“会不会做”；Subagent 解决“谁来做、上下文是否隔离”。

### 3.4 Skill 解决的是“复杂任务的稳定性”

复杂任务的特征通常是：

1. 多步骤；
2. 有行业/岗位规范；
3. 输出结构固定；
4. 边界情况多（缺字段、冲突信息、口语噪声）；
5. 重复发生，值得沉淀。

单次问答搞不定这些；临时 Prompt 能搞定一次，但搞不定第一百次。Skill 的价值就在第一百次仍然稳定。

## 四、Skill 的构成：文件夹即能力单元

### 4.1 最小形态

一个 Skill 首先是一个文件夹：

```text
meeting-minutes/
└── SKILL.md          # 必需：元数据 + 工作流说明
```

进阶形态：

```text
meeting-minutes/
├── SKILL.md                 # 必需
├── scripts/                 # 可选：确定性脚本
├── references/              # 可选：按需加载的长文档
├── assets/                  # 可选：模板、样式、示例文件
└── evals/                   # 可选：评测集
```

第三十八天笔记的概括非常准：

> **文件夹蒸馏员工的能力；`SKILL.md` 把专业人士的处理方式表达出来；把每次都得写的 Prompt 固化下来。**

### 4.2 为什么是文件夹，而不是单文件 Prompt

因为专业能力很少只靠一段文字：

| 资源类型 | 作用 | 例子 |
|---------|------|------|
| `SKILL.md` | 触发条件 + 主工作流 | 何时用、怎么做、输出模板 |
| `references/` | 长规范按需读取 | 品牌手册、API 规范、法规摘要 |
| `scripts/` | 确定性步骤交给代码 | 格式校验、HTML 生成、数据清洗 |
| `assets/` | 输出素材 | PPT 母版、日报 CSS、图标 |
| `evals/` | 防止改坏 | 典型输入与期望输出 |

文件夹让 Skill 具备了**软件模块**的味道：接口（description）、实现（body）、依赖资源、测试。

### 4.3 本地实践地图

本仓库第三十八天相关的 Skills 实践可以这样理解：

```text
ai/skills/                         # 学习笔记与场景素材
├── readme.md                      # Skills 0 基础概念
└── hys/
    ├── readme.md                  # 会议室 + 日报场景、skill-creator 思路
    └── meeting/meeting_content.txt# 真实口语转写样例

.agents/skills/                    # 可被 Agent 加载的技能实现
├── meeting-minutes/SKILL.md       # 会议纪要技能
├── tian-ai-daily/SKILL.md         # AI 日报技能
└── skill-creator/SKILL.md         # 创建/改进技能的元技能
```

学习路径也清晰：

```text
概念笔记（ai/skills）
    → 场景定义（会议 / 日报）
    → 落地 SKILL.md（.agents/skills）
    → 用 skill-creator 标准化创建与迭代
```

### 4.4 目录设计的工程建议

1. **一个 Skill 一个清晰职责**，不要“万能办公 skill”；
2. **name 用 kebab-case**，稳定如包名；
3. **references 按域名拆分**（aws.md / gcp.md），正文只写选择逻辑；
4. **脚本放 scripts/**，避免每个会话让模型重写同一段生成代码；
5. **样例输入可进 assets/ 或 evals/**，方便回归。

## 五、SKILL.md 协议深挖

### 5.1 基础头部：YAML Frontmatter

笔记写到：`SKILL.md` 用 YAML 头部隔开元数据，至少包含：

```yaml
---
name: "meeting-minutes"
description: "Generates structured meeting minutes from a transcript. Invoke when the user provides meeting text and asks to organize, summarize, or produce meeting minutes."
---
```

| 字段 | 职责 | 写作要点 |
|------|------|---------|
| `name` | 技能标识 | 短、稳定、可检索；像包名，不像标题党 |
| `description` | **触发器** | 写清“做什么 + 什么场景该用”；这是主触发机制 |

可选字段在生态中还会出现 `compatibility` 等，但初学先把 `name` 和 `description` 写对，收益最大。

### 5.2 description 是第一生产力

很多人对 Skill 的误解是：正文写得越长越好。  
真正决定“会不会被用上”的，往往是 **description**。

原因：Agent 通常先看各 Skill 的元数据，再决定加载谁的正文。description 写得含糊，就会：

- **漏触发（undertrigger）**：明明该用会议纪要 skill，却靠通用能力随便总结；
- **误触发（overtrigger）**：用户只是随口提了“会议”，却加载了不相关 skill。

好的 description 同时回答两件事：

1. **What**：这个 skill 产出什么；
2. **When**：用户怎样表达时应该调用。

对比：

```text
# 弱
description: 帮助处理会议相关内容。

# 强
description: Generates structured meeting minutes from a transcript.
Invoke when the user provides meeting text and asks to organize,
summarize, or produce meeting minutes.
```

`tian-ai-daily` 的写法更进一步，直接把触发短语写进 description：

```yaml
description: "Generates a daily AI news digest in Chinese with a visual HTML page.
Invoke when user asks for AI news, daily AI briefing, or says '甜甜AI日报' / 'tian-ai-daily'."
```

> **面试要点：description 不是简介文案，而是路由规则。写 description 像写网关匹配条件。**

### 5.3 正文该写什么

一个高质量 `SKILL.md` 正文通常包含：

1. **目标**：这个技能最终交付什么；
2. **触发场景补充**：正文可举例，但“何时用”的主信息仍应落在 description；
3. **工作流程**：分步骤，祈使句，可执行；
4. **边界与反例**：什么不该做、不确定时怎么办；
5. **输出模板**：固定结构，降低自由发挥；
6. **示例**：输入 → 输出，校准模型预期；
7. **失败处理**：工具挂了、信息不足、结果不够时怎么办；
8. **资源指针**：何时去读 `references/` 或跑 `scripts/`。

本地会议纪要 skill 的骨架就是标准答案：

```text
# 会议纪要生成
## 触发场景
## 工作流程
  1. 通读与理解
  2. 清理无关口语
  3. 提取结构化信息
  4. 处理不确定信息
  5. 输出原则
## 固定输出模板
## 行动项判定规则
## 示例
```

注意它的工程味道：

- 不是“请尽量总结一下会议”；
- 而是“先通读再输出”“口语怎么清”“不确定写 `—` 或待确认”“什么叫行动项、什么只是讨论”。

这就是**专业人士处理方式的蒸馏**。

### 5.4 输出模板为什么重要

没有模板，模型每次结构都可能变：

```text
今天这次会……
大家觉得……
最后决定……
```

有模板，交付物才可被下游系统消费：

```markdown
# 会议纪要
## 一、会议基本信息
## 二、会议目标
## 三、会议内容
## 四、行动项
## 五、风险与待确认事项
```

对 OPC 来说，模板不只是“好看”，而是：

- 方便复制到飞书 / Notion / 邮件；
- 方便二次 Agent 读取行动项并催办；
- 方便做评测（字段是否齐全、行动项是否可执行）。

### 5.5 失败处理写进 Skill，而不是临场发挥

`tian-ai-daily` 在这一点上很成熟：

- 搜索全失败：明确告知，不输出空日报；
- 单源失败：跳过并标注；
- 资讯不足 5 条：如实减少，不强行凑旧闻。

把失败路径写进 Skill，等于给模型装上**降级策略**。生产系统最怕的不是不会成功，而是失败时一本正经地瞎编成功。

## 六、渐进式披露：Skills 的 token 经济学

### 6.1 三级加载

skill-creator 强调的核心机制是 **Progressive Disclosure（渐进式披露）**：

```text
Level 1: Metadata（name + description）
         始终可见，约 ~100 words
         作用：决定是否触发

Level 2: SKILL.md body
         触发后进入上下文，理想 <500 行
         作用：告诉 Agent 怎么做

Level 3: Bundled resources
         需要时再读，理论上可很大
         作用：细则、脚本、资产、长参考
```

这直接回应了笔记里的 “llm tokens 经济”。

如果把所有岗位手册一股脑塞进 system prompt：

- 上下文瞬间膨胀；
- 无关技能互相干扰；
- 成本高、延迟高、注意力被噪声稀释。

Skills 的加载策略是：**先知道有哪些技能，用到再展开，细则按需再读。**

### 6.2 为什么这比“超长 System Prompt”更工程

| 方案 | 优点 | 缺点 |
|------|------|------|
| 全塞 System Prompt | 实现简单 | token 贵、冲突多、难维护 |
| 用户每次手贴 Prompt | 灵活 | 不可复用、质量看心情 |
| Skills 渐进加载 | 省 token、可模块化、可演进 | 需要设计 description 与目录结构 |

可以把它理解成软件里的：

```text
接口声明（description）
  → 打开实现文件（SKILL.md）
    → import 子模块（references/scripts）
```

而不是把整个 monorepo 编译进每一次请求。

### 6.3 写 Skill 时的 token 友好原则

1. **description 短而准**，承担路由；
2. **正文写主路径**，别把百科全书塞进 body；
3. **长规范放 references/**，并在正文写明“何时读取”；
4. **可脚本化的确定性步骤放 scripts/**，别让模型每次“重新发明”格式校验；
5. **控制 SKILL.md 体量**，接近 500 行就分层；
6. **删掉不拉分的句子**——skill-creator 明确建议：keep the prompt lean。

### 6.4 一个成本直觉账

假设你有 20 个岗位技能，每个正文 800 tokens，references 另算：

| 策略 | 每次请求大概额外成本 |
|------|---------------------|
| 全量塞进 system | 20 × 800 = 16000 tokens 起 |
| 只塞 metadata | 20 × 60 ≈ 1200 tokens |
| 触发 1 个 skill 后再加载正文 | 1200 + 800 = 2000 tokens 量级 |

还没算误触发带来的返工 token。  
**Skills 体系首先是上下文编译器，其次才是文案集合。**

> **面试金句：好的 Skill 体系，本质是上下文的按需编译，而不是上下文的无脑堆叠。**

## 七、触发工程：undertrigger 与 overtrigger

### 7.1 触发是 Skills 的“网关层”

很多团队正文写得很漂亮，上线后却感觉“skill 没生效”。根因常常不是模型笨，而是：

1. description 没有覆盖用户真实说法；
2. description 太宽，和其他 skill 抢触发；
3. 用户请求同时命中多个 skill，缺少优先级/组合策略。

### 7.2 undertrigger：该用不用

典型表现：

- 用户说“把会议录音整理成待办”，没有命中 `meeting-minutes`；
- 用户说“今天 AI 圈有啥大事”，没有命中日报 skill；
- Agent 用通用总结能力“凑合做了”，质量明显掉档。

修复方向：

- 在 description 中补充同义词与口语说法；
- 加入“Invoke when ...”句式；
- 覆盖中英双语触发词（如“甜甜AI日报” / `tian-ai-daily`）；
- 用 20 条 trigger eval（该触发/不该触发）做回归。

### 7.3 overtrigger：不该用却用了

典型表现：

- 用户只是问“敏捷会议一般多长”，却加载会议纪要 skill 开始要模板；
- 用户说“帮我看看新闻网站怎么做”，却触发 AI 日报 skill。

修复方向：

- description 写清**输入形态**（transcript / 近 24h AI 资讯）；
- 写清**用户意图动词**（organize / summarize / produce minutes）；
- 避免空泛词独占描述（“帮助处理一切办公事务”）。

### 7.4 触发评测最小集

skill-creator 建议为 description 建 should-trigger / should-not-trigger 集合。会议纪要可以长这样：

| query | should_trigger |
|------|----------------|
| “把下面这段会议转写整理成纪要” | true |
| “从录音稿里提取行动项和负责人” | true |
| “帮我总结这次评审会的结论” | true |
| “standup meeting 的最佳实践是什么？” | false |
| “如何提高会议效率？” | false |
| “把这段代码里的 meeting 变量重命名” | false |

> **面试加分点：你不只会写 skill，还会测 trigger precision / recall。**

## 八、写作模式：可执行、可解释、可泛化

### 8.1 用祈使句写流程，而不是写散文

弱：

```text
你可以考虑先大概看一下内容，然后尽量提炼重点……
```

强：

```text
1. 完整阅读文字稿
2. 清理不影响结论的口语
3. 按主题归类讨论与决策
4. 仅在存在明确执行意图时创建行动项
```

Skill 是给模型的操作手册，不是给领导的汇报稿。

### 8.2 解释 why，少写空洞的 ALWAYS / NEVER

skill-creator 有一条很高级的原则：

> 与其到处大写 ALWAYS/NEVER，不如解释为什么这样做。今天的模型有 theory of mind，理解动机后往往比死记硬性规则更稳。

例如：

```text
# 弱
永远不要编造负责人。

# 强
文字稿没有明确给出的事实不得猜测或补全。
把猜测写成决议，会让下游错误分配任务并破坏信任。
信息不确定时使用“待确认”或 “—”。
```

### 8.3 防过拟合：为“一万次调用”而写

你和用户可能只在 3 个样例上迭代，但 Skill 未来可能被调用成千上万次。  
因此：

- 不要把某个样例的特殊字段写死成唯一路径；
- 发现多个测试都在重写同一脚本时，把脚本固化进 `scripts/`；
- 优先抽象“判定规则”，而不是堆“如果用户这样说就那样做”的窄分支。

### 8.4 示例怎么写才有用

好示例具备：

1. 真实噪声（口语、缺字段、冲突信息）；
2. 明确期望结构；
3. 展示边界处理（待确认，而不是脑补）。

会议纪要 skill 的示例就做对了：输入很短、很口语，输出却完整落到模板字段，并保留“支付接口排期待确认”这类风险。

### 8.5 语言约定也可以写进 Skill

`tian-ai-daily` 明确约定：

- 与用户对话：中文；
- 摘要与页面文案：中文；
- frontmatter 的 name/description：英文为主，保证匹配稳定。

这是很实用的工程细节：**对模型的路由层与对用户的交付层，可以使用不同语言策略。**

## 九、实战一：会议纪要 Skill

### 9.1 场景：班味、重复、必须自动化

`ai/skills/hys/readme.md` 把场景写得很有生活感：

- 开不完的会；
- 会后总有人要整理纪要；
- 纪要的价值其实很固定：主题是什么、解决什么问题、谁负责、截止日期是什么；
- 王老板发言、程序员要排期、设计师和测试插话——信息密度低、噪声高。

完整链路是：

```text
AI 硬件录音
  → 语音转文本
  → 会议转写稿
  → Skill 自动化生成纪要
  → 行动项可跟踪
```

这不是“让 AI 帮忙写一段话”，而是**把会议秘书岗位 SOP 产品化**。

### 9.2 真实输入长什么样

`meeting_content.txt` 是典型 ASR 转写：口语、抢话、重复、不完整句子。

```text
发言人1  00:22
今天咱们四个人过来，碰个头……小部门好久没团建了……

发言人2  00:51
这里边我觉得有必要团建。

发言人3  00:53
是得玩玩是吧？对市场工作压力太大了。

发言人1  01:00
……出去团建，那肯定是公司花钱……我跟领导去申请去。
大家说既然说出去团建，那大家是想出去怎么玩？
```

如果没有 Skill，模型容易输出：

- 流水账复述；
- 把玩笑写成决议；
- 漏掉负责人与时间；
- 结构每次都不一样。

### 9.3 Skill 如何把噪声变成可执行资产

`meeting-minutes` 的关键设计点：

#### （1）先理解，再输出

> 完整阅读文字稿，先理解会议背景、目标、议题、结论与待办之间的关系，再输出纪要。不要按原始发言顺序机械拼接。

这是专业秘书和录音机的区别。

#### （2）清口语，但保留分歧

删除“嗯 / 那个 / 就是”，但**不得删除关键异议、风险、条件、数字、责任人**。  
简洁不能以失真为代价。

#### （3）不确定就显式标记

- 没出现的事实不编造；
- 空字段用 `—`；
- 责任人或时间不清写“待确认”；
- 冲突表述保留冲突，不擅自选边。

这一点在生产里极重要：AI 纪要最危险的不是不够漂亮，而是**把猜测写成决议**。

#### （4）行动项有判定规则

只有明确执行意图才进行动项表，例如：

- “小王下周三前把方案发出来”；
- “产品组负责补充预算测算”。

“可以考虑 / 也许 / 我觉得”不能自动变 TODO。

### 9.4 把团建会转写“技能化”后的目标形态

对上面的团建讨论，一个合格 Skill 输出应接近：

```markdown
# 会议纪要

## 一、会议基本信息
| 项目 | 内容 |
| 会议时间 | — |
| 参会人员 | 发言人1-4（姓名待确认） |

## 二、会议目标
- 讨论是否组织部门团建及如何组织

## 三、会议内容
### 主题 1：是否团建
- 结论：有必要组织团建，需劳逸结合
### 主题 2：费用
- 结论：公司报销；由发言人1向领导申请

## 四、行动项
| 行动项 | 负责人 | 截止时间 |
| 向领导申请团建预算 | 发言人1 | 待确认 |
| 收集团建玩法意向 | 待确认 | 待确认 |
```

注意：即使原文很“水”，Skill 也要产出**可跟进对象**，而不是散文复述。

### 9.5 信息压缩管道视角

```text
高噪声口语流
  → 去停顿/寒暄/口误
  → 主题聚类
  → 决策与待确认分离
  → 行动项结构化
  → 固定模板交付
```

对面试官来说，你要能讲清：  
**Skill 在这里做的不是“摘要”，而是“业务对象抽取 + 质量门禁 + 固定 schema 输出”。**

## 十、实战二：AI 日报 Skill

### 10.1 场景：信息过载下的重复学习劳动

笔记场景二：

> 每天被海量 AI 信息淹没，想了解行业动态，却没时间一个网站一个网站去刷。

这也是典型“重复但必须做”的工作：

- 多源检索；
- 过滤水文与重复；
- 压缩成可消费摘要；
- 最好还有统一视觉交付。

### 10.2 `tian-ai-daily` 的工作流设计

这个 skill 把“信息官”的一天拆成了可执行步骤：

```text
1. 近 24 小时多源检索（TechCrunch / The Verge / HN / Reddit…）
2. 智能过滤（主题相关、信息密度、去重、去水文）
3. 中文精华摘要（50-100 字，先发生什么，再为什么重要）
4. 关键词标签（2-4 个，避免空泛标签）
5. 单文件可视化 HTML 输出
6. 按规定顺序交付：前言 → HTML → 使用说明 → 来源清单
```

它展示了 Skill 的四种能力叠加：

| 能力 | 体现 |
|------|------|
| 流程编排 | 搜 → 滤 → 写 → 标 → 排版 |
| 质量标准 | 字数、标签、时效、去重规则 |
| 交付形态 | 不是聊天回复，而是可打开的 HTML 页面 |
| 降级策略 | 源失败、数量不足、全失败时的处理 |

### 10.3 为什么这比“帮我看看今天 AI 新闻”更强

用户随口一说，通用 Agent 也可能搜几条。  
但 Skill 预先规定了：

- 时间窗（近 24 小时）；
- 来源策略；
- 入选条数（5–8）；
- 摘要写法；
- 标签体系；
- 视觉与响应式规范；
- 输出顺序与失败处理。

于是结果从“有时候还行”变成“每天可预期”。

### 10.4 两个实战 Skill 的对照

| 维度 | 会议纪要 | AI 日报 |
|------|---------|--------|
| 输入 | 用户提供转写 | Agent 主动检索 |
| 核心难点 | 噪声与事实边界 | 时效、去重、信息密度 |
| 工具依赖 | 读文件为主 | WebSearch / WebFetch |
| 输出 | Markdown 模板 | HTML 页面 + 来源清单 |
| 质量门禁 | 不编造、待确认 | 不凑旧闻、不空报 |
| OPC 岗位 | 会议秘书 | 行业情报官 |

> **OPC 视角：Skill 把个人兴趣流程升级成可每日复用的岗位流水线。**

## 十一、从 0 到 1：手把手封装一个 Skill

下面用“会议纪要”走一遍最小闭环，面试时也能当设计题答。

### 11.1 Step 0：确认这是 Skill 题，不是 Tool 题

- 需要稳定流程与输出契约？是  
- 主要痛点是“不专业/不稳定”而不是“没 API”？是  
→ 做 Skill

### 11.2 Step 1：捕获意图

回答四问：

1. 让 Agent 能做什么？→ 从转写生成结构化纪要  
2. 何时触发？→ 用户提供会议文本并要求整理/总结/出纪要  
3. 输出是什么？→ 固定 Markdown 模板  
4. 如何验收？→ 字段完整、行动项可执行、不编造

### 11.3 Step 2：先写 description，再写正文

先把路由写对，再写工艺。很多失败项目顺序反了。

### 11.4 Step 3：正文只保留主路径

通读 → 去噪 → 抽结构 → 处理不确定 → 套模板 → 校验行动项。

### 11.5 Step 4：补反例与失败路径

- 没有负责人怎么办  
- 只有抱怨没有决议怎么办  
- 转写中途截断怎么办  

### 11.6 Step 5：用 2～3 个真实样例试跑

至少覆盖：

1. 正常短会；
2. 缺字段会；
3. 有冲突信息的会。

### 11.7 Step 6：把反复出现的硬逻辑规则化

例如“行动项判定规则”一旦在多个样例中被重复口头强调，就应升格为正文固定条款。

### 11.8 Step 7：需要时再加 scripts / references

如果每次都要做同一段 HTML 骨架校验、同一套公司会议字段映射，再脚本化/参考文档化。不要一上来过度设计。

## 十二、skill-creator：用 Skill 创建 Skill，以及完整评测体系

### 12.1 元技能的意义

当“封装 skill”本身变成高频动作时，Anthropic 路线给出了 `skill-creator`：  
**一个专门用来创建、修改、评测、优化 skill 的 skill。**

这非常符合笔记判断：

> 当我们频繁重复的时候，就应该封装；skill-creator 标准化、简化 skill 的封装，让你随时创建自己的 skill。

闭环是：

```text
捕获意图
  → 访谈边界与输入输出
  → 写 SKILL.md 草稿
  → 设计测试用例
  → with-skill / baseline 对比评测
  → 人工/自动 grading
  → 根据反馈改写
  → 优化 description 触发率
  → 扩大测试集
  → 迭代直到稳定
```

### 12.2 创建 Skill 的标准问题单

在动手写文件前，先回答：

1. 这个 skill 要让 Agent 能完成什么？
2. 用户怎样说时应该触发？
3. 期望输出格式是什么？
4. 有哪些边界情况？
5. 输出是客观可验收，还是主观风格型？
6. 是否需要脚本、模板、参考文档？
7. 与现有 skills 是否职责重叠？

### 12.3 评测分层

| 层级 | 测什么 | 手段 |
|------|--------|------|
| 触发层 | 该不该加载此 skill | should_trigger 集合 |
| 过程层 | 是否按工作流执行 | transcript 检查 |
| 结果层 | 输出是否达标 | assertions / 人工审阅 |
| 成本层 | token / 耗时是否可接受 | timing.json |
| 回归层 | 改动是否破坏旧用例 | 迭代 benchmark |

### 12.4 好的 assertion 长什么样

客观 skill（会议纪要、数据抽取）适合硬断言：

```text
- 包含“行动项”表格
- 未出现文字稿中不存在的负责人姓名
- 不确定时间标记为“待确认”
- 输出包含会议目标小节
```

主观 skill（文风、设计审美）不要硬凑布尔断言，保留人工评审。

### 12.5 with-skill vs baseline

这是 skill-creator 最有工程味道的部分：

- 新建 skill：和 **without_skill** 比；
- 改进 skill：和 **旧版本 skill** 比；
- 进阶：盲评（不告诉评判者哪个是新版本）。

你要证明的不是“我写了文档”，而是：

> **有 skill 比没 skill 更好；新 skill 比旧 skill 更好；且没有明显过拟合。**

### 12.6 从评测反推 Skill 改进

常见信号与动作：

| 信号 | 可能原因 | 动作 |
|------|---------|------|
| 有无 skill 都过 | 断言太弱 | 换更能区分的用例 |
| 只对样例 A 好 | 过拟合 | 抽象规则，增加多样例 |
| token 暴涨 | 正文太胖/工具空转 | lean 化，脚本化重复步骤 |
| 触发不稳 | description 差 | 单独做 trigger 优化 |
| 高方差 | 规则含糊 | 补边界与示例 |

### 12.7 description 优化是单独一层

即使正文很好，description 写弱也会 undertrigger。  
因此 skill-creator 把 description 优化视为独立步骤：让触发更“主动”一点，但不要变成乱触发。

经验规则：

- 写清任务动词与对象；
- 覆盖同义说法（“纪要 / 整理会议 / 总结待办”）；
- 写出典型用户原话；
- 避免空泛到无所不包；
- 用 20 条真实 query 做触发回归。

## 十三、Skill 组合、冲突与 Agent Host 运行时

### 13.1 单 Skill 足够吗

很多真实任务需要组合：

```text
“听完这周评审会，生成纪要，并把行动项同步到项目看板，再发一封纪要邮件”
```

可能涉及：

- `meeting-minutes` Skill（结构化）
- 项目管理 MCP/Tool（写看板）
- 邮件 Tool（发送）
- 可选 `corp-writing` Skill（邮件语气）

Skill 负责“专业做法”，Tool 负责“执行触点”，Host 负责“编排与权限”。

### 13.2 冲突类型

| 冲突 | 例子 | 处理 |
|------|------|------|
| 触发冲突 | 两个 skill 都匹配“总结” | 收紧 description，增加更具体意图词 |
| 规范冲突 | A 要求极简，B 要求详尽 | 拆场景，或在 Host 层定义优先级 |
| 工具冲突 | 两个 skill 要求不同搜索策略 | 在正文声明适用边界 |
| 语言冲突 | 中英输出约定不一致 | 统一组织级默认，再允许 skill 覆盖 |

### 13.3 运行时的推荐心智模型

```text
用户请求
  → Host 扫描 skills metadata
  → 选择 0..N 个 skills 加载正文
  → 结合 system / memory / tools / rag
  → 执行
  → 产出
  →（可选）写入评测与日志
```

面试时可强调：

> Skills 不是替代 Agent 架构，而是 Agent 架构里的**可插拔能力层**。

### 13.4 与多 Agent 的关系

- **单 Agent + 多 Skills**：适合 OPC 与本地助手，简单高效；
- **多 Agent + 各带 Skills**：适合组织级分工（研究 Agent、写作 Agent、评审 Agent）；
- **Supervisor**：按任务把请求路由到“拥有对应 skills 的专家 Agent”。

第三十八天笔记说的“一堆 Agent 虚拟数字人来到 Agent Host”，指的就是这种编制思维。

## 十四、生产治理：版本、权限、安全、团队共享

### 14.1 Skills 是代码资产，不是聊天偏好

请把 Skills 当软件管理：

| 治理项 | 建议 |
|--------|------|
| 版本 | Git 管理，`SKILL.md` 变更可 diff |
| Code Review | description/正文/脚本都要审 |
| 测试 | evals + 触发集 + 关键样例 |
| 发布 | 个人 skills / 项目 skills / 组织 skills 分层 |
| 回滚 | 坏版本可快速回退 |
| 观测 | 记录触发率、失败率、人工改写率 |

### 14.2 分层放置

```text
用户级 skills     → 个人习惯与私有流程
项目级 skills     → 当前仓库的业务 SOP
组织级 skills     → 公司规范、合规、品牌、安全
```

项目级优先于用户级、组织级提供底线约束——具体优先级取决于 Host 实现，但分层思想要有。

### 14.3 安全：无惊喜原则

skill-creator 提到一条不可妥协的原则：**Principle of Lack of Surprise（无惊喜原则）**。

Skill 不应：

- 夹带恶意脚本；
- 偷偷外传数据；
- 以“角色扮演”为名绕过权限；
- 做 description 承诺之外的高风险动作。

生产上还要补：

1. **最小权限**：skill 需要哪些 tools 就开哪些；
2. **敏感数据提示**：纪要中的人事/财务信息如何处理；
3. **人工确认点**：发送邮件、改生产配置前暂停；
4. **审计日志**：谁触发了什么 skill、产出了什么。

### 14.4 团队共享的正确姿势

- 用仓库共享，而不是微信传文件；
- 每个 skill 有维护者（owner）；
- 变更附带 eval 结果；
- 淘汰长期不触发、或总被人工大改的 skill（说明它没创造价值）。

### 14.5 质量指标（可上线看板）

| 指标 | 含义 |
|------|------|
| Trigger Precision | 触发中真正该用的比例 |
| Trigger Recall | 该用时成功触发的比例 |
| Edit Distance / 人工改写率 | 输出还要改多少 |
| Assertion Pass Rate | 自动验收通过率 |
| p50/p95 Latency | 耗时 |
| Tokens / Task | 成本 |
| Reuse Count | 复用次数（是否真资产） |

## 十五、何时封装、决策树与反模式大全

### 15.1 值得封装的信号

| 信号 | 解释 |
|------|------|
| **高频重复** | 一周超过两次的同类任务 |
| **有专业标准** | 输出有行业/岗位规范 |
| **结构稳定** | 字段、章节、验收项可模板化 |
| **易跑偏** | 通用模型常漏字段或乱发挥 |
| **可复用主体多** | 团队共享，或多个 Agent 共用 |
| **可评测** | 能用样例判断好坏 |
| **失败代价高** | 一旦胡编会造成业务事故 |

### 15.2 不该过早封装的情况

| 情况 | 更合适的做法 |
|------|-------------|
| 一次性探索问题 | 直接对话 |
| 还在摸索最佳流程 | 先跑 3～5 次，再蒸馏 |
| 只是单次 API 调用 | 做 Tool / MCP 即可 |
| 核心是检索私有知识 | 先做 RAG，再在 Skill 里规定如何引用 |
| 流程天天大变 | 先固化稳定部分，别一上来写巨石 skill |
| 纯审美且无共识 | 先做人审样本，再决定是否 skill 化 |

### 15.3 决策树

```text
这个任务会重复吗？
  ├─ 否 → 临时 Prompt
  └─ 是
      需要外部动作吗？
        ├─ 是 → 先有 Tool/MCP
        └─ 否/已有工具
            需要私有知识吗？
              ├─ 是 → 配 RAG
              └─ 否/已有
                  是否存在稳定专业流程与输出契约？
                    ├─ 是 → 封装 Skill
                    └─ 否 → 继续试跑，沉淀后再封装
```

### 15.4 反模式大全

| 反模式 | 表现 | 后果 | 修复 |
|--------|------|------|------|
| Prompt 搬家 | 把聊天记录原样粘进 SKILL.md | 又臭又长，不可执行 | 重写成步骤与模板 |
| 万能 Skill | 一个 skill 包办所有办公 | 冲突多、难维护 | 按岗位拆分 |
| 只写 what 不写 when | description 像广告语 | 触发失败 | 补 Invoke when |
| 只写 when 不写 how | 能触发但不会做 | 输出不稳 | 补工作流与示例 |
| 无失败路径 | 工具挂了仍硬生成 | 胡编 | 写降级策略 |
| 无评测 | 凭感觉迭代 | 越改越坏 | 建 evals |
| 过拟合三样例 | 只对 demo 有效 | 线上翻车 | 多样化测试 |
| 与 Tool 抢活 | 用自然语言替代本该脚本化的步骤 | 成本高、不稳定 | 能代码就代码 |
| 秘密 Skill | 个人目录私藏关键流程 | 组织无法复用 | 项目/组织级共享 |
| 有惊喜 Skill | 做超范围动作 | 安全事故 | 无惊喜原则 + 权限 |

### 15.5 OPC 公司的 Skills 编制思路

如果把 OPC 当成一人公司，Skills 就是编制表：

```text
CEO Agent Host
├── 会议秘书 Skill
├── 行业情报 Skill
├── 前端设计 Skill
├── 数据分析 Skill
├── 周报 / 月报 Skill
├── 品牌写作 Skill
└── skill-creator（HR / 培训岗：生产其他 skill）
```

你招聘的不是更多聊天窗口，而是**可版本化的岗位能力**。

## 十六、面试题库与答题框架

### A. 基础概念

#### 16.1 什么是 Agent Skill？和 Prompt 有什么区别？

> Skill 是把某类专业任务的处理流程、质量标准与输出契约封装成可被 Agent 自动触发的能力包，通常以包含 `SKILL.md` 的文件夹形式存在。Prompt 是一次请求里的指令文本；Skill 是可复用、可版本化、可评测的能力模块。Prompt 解决“这一次怎么说”，Skill 解决“这一类事默认怎么做”。

#### 16.2 Skill 和 Tool / MCP 有什么区别？

> Tool/MCP 提供原子能力；Skill 提供如何组合这些能力完成岗位级任务的 SOP。没有 Tool，Skill 可能“会说不会做”；没有 Skill，Tool 可能“能做但不专业、不稳定”。

#### 16.3 Skill 和 RAG 的关系？

> RAG 解决“知道什么”，Skill 解决“怎么做”。二者常配合：Skill 规定何时检索、如何引用、不足时如何降级；RAG 提供私有知识内容。

#### 16.4 Skill 和 System Prompt 怎么分工？

> System Prompt 管全局身份与底线规则；Skill 管专项任务工艺。全局稳定、专项可插拔。

#### 16.5 Skill 和 Subagent 有什么不同？

> Subagent 是执行体/上下文隔离问题；Skill 是能力说明书加载问题。可以“带某个 skill 的 subagent”。

### B. 机制深挖

#### 16.6 为什么 description 这么重要？

> 渐进式披露下，元数据先于正文被看见。description 是路由层，决定 skill 是否进入上下文。写不好就 undertrigger 或 overtrigger。

#### 16.7 什么是 Progressive Disclosure？

> 三级加载：metadata 常驻、body 触发后加载、resources 按需加载。目标是在有限上下文中装配专业能力，同时控制 token 与干扰。

#### 16.8 如何设计一个会议纪要 Skill？

> 先定义交付 schema；再定义去噪规则；再定义不确定性策略；再定义行动项判定；最后给正反例与失败路径。核心是结构化、可执行、可追责，而不是“写得通顺”。

#### 16.9 如何优化 skill 触发率？

> 收集真实用户说法 → 构造 should/should-not 集合 → 改 description → 回归触发评测 → 再观察线上 trigger precision/recall。

#### 16.10 skill-creator 解决什么问题？

> 把写 skill 从手工作坊变成标准工程：意图捕获、起草、eval、baseline 对比、反馈迭代、description 优化。它本身也是 skill，说明能力可以层级化生产。

### C. 场景与设计题

#### 16.11 给“前端落地页生成”设计一个 Skill 大纲

答题要点：

- description：何时做 landing page、包含哪些页面区块  
- 流程：信息架构 → 文案层级 → 组件结构 → 响应式 → 无障碍 → 交付文件  
- 模板：分区输出（Hero/痛点/方案/社会证明/CTA）  
- 边界：无品牌素材时的占位策略  
- evals：3 个不同行业提示词

#### 16.12 线上发现 skill 输出经常被用户大改，怎么排查

1. 看是否触发了正确 skill  
2. 看正文规则是否过时  
3. 看样例是否覆盖新业务  
4. 看是否该脚本化的步骤仍靠模型自由发挥  
5. 把高频人工修改沉淀回 SKILL.md  
6. 补回归，防修 A 坏 B

#### 16.13 如何衡量 Skills 体系是否值回票价

> 看复用次数、人工改写率、任务时长、token 成本、错误事故率、新成员上手时间。若一个 skill 长期无人触发或总被大改，应重构或下线。

#### 16.14 Skills 如何服务 OPC / 超级个体？

> OPC 的瓶颈不是模型是否聪明，而是个人无法同时具备所有岗位经验。Skills 把设计、秘书、分析、情报等专业流程编码进 Agent Host，让一个人调度多个虚拟专业能力。

#### 16.15 落地 Skills 时最常见的失败模式？

| 失败模式 | 表现 | 修复 |
|---------|------|------|
| description 含糊 | 该触发不触发 | 补场景短语与任务边界 |
| 正文像散文 | 模型自由发挥 | 改成步骤 + 模板 + 反例 |
| 什么都塞进一个 skill | 又胖又慢 | 拆分技能，按需加载 |
| 只写不做评测 | 越改越坏 | 建 evals，对比 baseline |
| 把猜测当事实 | 会议纪要写错责任人 | 强制待确认策略 |
| 与 Tool 边界不清 | skill 里空谈无法执行动作 | 先补工具，再写编排 |
| 无治理 | 个人技能无法组织复用 | Git + owner + review |

### D. 一分钟口述版（终面备用）

> Skill 是 Agent 的岗位能力包。Tool 让它能动手，RAG 让它有知识，Memory 让它记得你，Skill 让它按专业流程稳定把事做完。`SKILL.md` 的 description 负责路由，正文负责工艺，references/scripts 负责细则与确定性，evals 负责回归。好的 Skills 体系是上下文的按需编译器，也是 OPC 把个人经验变成可复制资产的关键基础设施。

## 十七、上线检查清单与 FDE 技能树更新

### 17.1 Skill 上线前 20 项检查

**定位**

- [ ] 职责单一，能用一句话说清  
- [ ] 与现有 skills 无严重重叠  
- [ ] 明确这是 Skill 而不是 Tool/RAG 能单独解决的问题  

**路由**

- [ ] `name` 稳定且语义清晰  
- [ ] `description` 含 what + when  
- [ ] 有 should-trigger / should-not-trigger 样例  

**正文**

- [ ] 工作流可执行（步骤化）  
- [ ] 有输出模板或 schema  
- [ ] 有不确定性/失败处理  
- [ ] 有至少一个真实示例  
- [ ] 解释了关键规则背后的 why  

**资源**

- [ ] 长文档进 references，而非全塞 body  
- [ ] 重复确定性逻辑进 scripts  
- [ ] 资源在正文中有“何时读取/调用”的指引  

**评测与治理**

- [ ] 至少 2～3 个 eval prompts  
- [ ] 客观输出有 assertions  
- [ ] 与 baseline 对比过  
- [ ] Git 可追踪，有维护者  
- [ ] 权限与无惊喜原则已审查  

### 17.2 第三十八天后的能力树更新

```text
AI Native 开发者 / FDE 能力栈（更新）

  概念层：Agent = LLM + Memory + Tool + RAG + MCP + Skills
  机制层：Loop = gen() + check() + stop()
  基础层：Token + Embedding
  框架层：LangChain + LangGraph
  工具层：MCP Server / Resource / 多 Server 协作
  知识层：RAG 检索 + 文档切分入库
  交互层：流式输出
  能力层：Skills Engineering
            ├─ SKILL.md 协议
            ├─ Progressive Disclosure
            ├─ 触发工程
            ├─ skill-creator 评测闭环
            └─ 生产治理与安全
  后端层：把 Agent 部署成产品
```

一句话：

> **会调模型 ≠ 会做 Agent；会做 Agent ≠ 会经营 Skills 资产。**

## 结语

第三十八天 skill 初步，看起来只是几份笔记和一个会议室场景，但它补上了 Agent 能力版图里长期缺席的一块：

```text
v033 提出：Agent 需要 Skills
v036/v037 解决：Agent 如何调用工具（MCP/Tool）
v038/v040/v041 解决：Agent 如何获得知识（RAG）
v039 解决：回答如何流式呈现
v042 解决：Agent 如何按专业标准稳定完成复杂工作（Skills）
```

把学习笔记压成可记住的七句话：

1. **Skill 是能力蒸馏**，不是 Prompt 备份。  
2. **文件夹 + `SKILL.md`** 是最小工程单元。  
3. **description 负责路由，正文负责工艺，资源负责细则。**  
4. **渐进式披露**让专业能力与 token 成本可兼得。  
5. **触发工程**和正文质量同样重要。  
6. **skill-creator + evals** 让技能可生产、可回归、可进化。  
7. **治理与安全**决定 Skills 是组织资产还是个人玩具。

从用 AI 的阶段看：

```text
查字典（搜索）
  → 写提示词（Prompt Engineering）
  → 封装技能（Skills Engineering）
  → 经营能力资产（Trigger / Eval / Governance）
```

第一批人每天重新解释“我是谁、要做什么”；  
第二批人把解释沉淀成 Skills，把记忆交给 Memory，把动作交给 Tools/MCP，把知识交给 RAG——然后直接开工。

**Agent 的大脑可以共用，岗位技能必须封装。**  
**封装之后还要评测，评测之后还要治理。**

这就是 Skills 的工程本质，也是 OPC 真正能从概念走向日常作业的关键一跳。

下一次当你发现自己在重复粘贴同一段“请按如下格式……”时，别再只是保存聊天记录——把它做成一个 Skill，再给它几条 eval。  
那一刻，你才是在“训练”你的 AI 团队，而不只是在“聊天”。
