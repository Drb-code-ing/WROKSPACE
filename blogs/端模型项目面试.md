### （一）架构类

**1. 为什么用 Web Worker**

一句话：浏览器里的多线程机制，让重计算跑在独立线程，不阻塞主线程。

展开：主线程就是渲染线程，它既要算 UI 又要响应交互。模型的加载（下载几十上百 MB 权重）和推理（WebGPU 上跑 token 循环）都是重活，如果放主线程，页面会卡死——点按钮没反应、滚动掉帧。把重活丢给 Worker 后，主线程只负责发指令、收结果、渲染，两边通过 `postMessage` 通信。

创建方式：

```js
worker.current = new Worker(new URL("./worker.js", import.meta.url), {
  type: "module",
});
```

`new URL(..., import.meta.url)` 是 Vite 的写法，让打包工具正确解析 worker 路径；`type: "module"` 让 worker 里能用 ESM 的 `import`。

追问准备：Worker 有几种？这里用 Dedicated Worker（专用线程，一对一）。还有 Shared Worker（多页面共享）、Service Worker（网络代理、离线缓存）。

**2. postMessage 为什么是结构化克隆**

一句话：postMessage 传的是数据副本，不是共享内存。

展开：结构化克隆（structured clone）会把消息对象深拷贝一份传过去，两边改自己的副本互不影响。它不是函数调用那种「等返回值」，而是发一条消息过去、对方处理完再发一条回来，是异步的、消息驱动的。

边界：结构化克隆能拷大多数对象，但函数、DOM 节点、部分类型（如 `Map` 早期不支持）不能。传大对象有拷贝成本，但这个项目里消息都很小，无所谓。真正要共享内存得用 `SharedArrayBuffer`，这里用不上。

**3. 消息协议是一套状态机**

一句话：主线程和 Worker 靠 `status` 字段分派消息。

展开：主线程发 `check / load / generate / interrupt / reset` 五种指令；Worker 回 `loading / initiate / progress / done / ready / start / update / complete / error` 九种状态。主线程在 message 事件里 `switch (e.data.status)` 分派。

为什么用状态而不是回调：因为跨线程没有共享调用栈，只能靠消息 + 约定的状态字段来协调。这套协议就是两个线程之间的「约定」。

### （二）模型加载类

**4. 单例模式：模型只加载一次**

一句话：用单例保证 tokenizer 和 model 全局只有一份，只加载一次。

展开：

```js
class TextGenerationPipeline {
  static model_id = "onnx-community/DeepSeek-R1-Distill-Qwen-1.5B-ONNX";

  static async getInstance(progress_callback = null) {
    this.tokenizer ??= AutoTokenizer.from_pretrained(this.model_id, { progress_callback });
    this.model ??= AutoModelForCausalLM.from_pretrained(this.model_id, {
      dtype: "q4f16",
      device: "webgpu",
      progress_callback,
    });
    return Promise.all([this.tokenizer, this.model]);
  }
}
```

三个点要讲：

- `static`：`tokenizer` 和 `model` 挂在**类**上，不挂在实例上，所以不用 `new`，所有调用方共享同一份。
- `??=`：空值合并赋值。左边是 `null` / `undefined` 才赋值，否则复用。首次调用 `this.tokenizer` 是 undefined，触发加载；之后发现已有值，直接复用。
- 存的是 Promise 不是结果：`from_pretrained` 返回 Promise，所以 `??=` 存的是 Promise 本身。这样并发调用 `getInstance` 时，两个调用拿到的是同一个 Promise，不会重复下载。

类比：单例就是「懒加载 + 缓存」。模型下载昂贵，必须只做一次。设计模式里 23 种之一，解决全局状态和资源浪费。

追问：`??=` 和 `||=` 区别——`??=` 只在 null/undefined 时赋值，`||=` 在 falsy（0、空串、false）时也赋值。这里必须用 `??=`，精确判断「还没初始化」。

**5. 量化 q4f16：模型怎么塞进浏览器**

一句话：把权重从 16 位浮点量化到 4 位，体积缩到约四分之一。

展开：1.5B 参数，fp16 每参数 2 字节，光权重约 3GB，浏览器扛不住。量化到 4 比特，每参数约 0.5 字节，权重降到约 0.75GB，下载快、内存占用小。

代价是精度损失：4 比特只能表示 16 个值，和 fp16 差很多。但推理场景可接受——模型泛化能力够强，量化后输出和原版差别不大。这是「用精度换可行性」，端侧模型能落地的关键一步。

追问：量化方式有对称/非对称、per-tensor/per-channel；`q4f16` 是混合精度，权重 4 比特、部分计算保持 fp16，兼顾体积和精度。

**6. device: "webgpu" 为什么快**

一句话：让推理走 GPU 而不是 CPU。

展开：CPU 跑 1.5B 模型的 token 循环非常慢，因为矩阵运算是高度并行的，CPU 串行算效率低。GPU 有成百上千个核心，天然适合矩阵并行，WebGPU 把算子放到 GPU 上跑，速度提升一个量级。

追问：WebGPU 和 WebGL 区别——WebGL 是图形渲染 API，做通用计算是「借道」，有各种限制；WebGPU 是新一代标准，原生支持 compute shader（通用计算），对 ML 推理这类并行计算支持更好、更贴近底层。这个项目用 WebGPU 做推理加速。

**7. 下载进度怎么流到 UI**

一句话：progress_callback 从 Worker 转发到主线程，按文件去重更新。

展开：

```js
const [tokenizer, model] = await TextGenerationPipeline.getInstance((x) => {
  self.postMessage(x);
});
```

`from_pretrained` 下载模型文件时周期性调用回调，回调里带进度信息。Worker 直接 `postMessage` 回主线程。主线程收到三种消息：`initiate`（文件开始下载，push 进列表）、`progress`（进度更新，按 file 找到并合并）、`done`（下载完成，从列表移除）。进度列表用不可变更新，后面前端部分讲。

**8. 预热：为什么先跑一次假输入**

一句话：提前编译 WebGPU shader，避免首次推理卡顿。

展开：WebGPU 推理有前置成本——把模型计算图编译成 shader（着色器）、构建算子图、分配缓冲，这个过程可能要几秒。如果等用户第一次提问才做，用户会明显感觉到「发了消息卡好久才出第一个字」。所以加载阶段用假输入 `"a"` 跑一次 `max_new_tokens: 1`，把一次性成本提前付掉。等用户真正提问时，shader 已编译好，直接进 token 循环。这就是为什么加载完会显示「Compiling shaders and warming up model...」。

### （三）生成类

**9. chat template：把对话转成模型认识的格式**

一句话：把 messages 数组转成模型训练时见到的字符串格式。

展开：用户在 UI 里的消息是数组 `[{ role: "user", content: "你好" }]`，但模型不理解 `role` 字段，它训练时看到的是带特殊标记的字符串（ChatML 格式）：

```
<|im_start|>user
你好<|im_end|>
<|im_start|>assistant
```

`apply_chat_template` 执行 tokenizer 配置里定义的模板，完成这个转换：

```js
const inputs = tokenizer.apply_chat_template(messages, {
  add_generation_prompt: true,
  return_dict: true,
});
```

- `add_generation_prompt: true`：末尾追加 `<|im_start|>assistant\n`，告诉模型「轮到你了，开始回答」。不加的话模型不知道从哪开始生成。
- `return_dict: true`：返回字典，含 `input_ids`（token id 序列）和 `attention_mask`（注意力掩码）。

**10. attention_mask 是什么**

一句话：标记序列里哪些是真实 token、哪些是 padding，让模型忽略填充。

展开：序列长度固定时，不足的部分用 padding 补齐。`attention_mask` 是同样长度的 0/1 序列，1 表示真实 token，0 表示 padding。模型算注意力时对 0 的位置不关注。单条消息 padding 不多，但这是标准输入字段，`generate` 需要它。

**11. token 和分词**

一句话：模型处理的不是字，是 token（词元）的 id。

展开：文本要先分词，切成一个个 token，再映射成数字 id，模型才能运算。`tokenizer.encode("...")` 把字符串转成 token id 数组。token 不一定是完整单词，可能是子词（subword），中文可能一个字或几个字一个 token。这就是为什么模型有「词汇表」，未知词会被拆成更小的子词。

**12. 思考和回答的分界**

一句话：R1 是推理模型，先思考、再回答，用 `<think></think>` 分界。

展开：DeepSeek-R1 蒸馏模型训练时被要求「先推理再给答案」，思考过程用 `<think></think>` 包起来。代码里把这两个特殊标记的 token id 提前算出来：

```js
const [START_THINKING_TOKEN_ID, END_THINKING_TOKEN_ID] = tokenizer.encode(
  "<think></think>",
  { add_special_tokens: false },
);
```

维护一个 `state`，默认 `"thinking"`，每生成一个 token 就检查是不是 `END_THINKING_TOKEN_ID`，是就切成 `"answering"`。这个 state 随每次更新发回主线程，前端靠它区分「思考」和「答案」。

**13. TextStreamer：流式输出怎么实现**

一句话：TextStreamer 在生成循环内部一边生成一边触发回调。

展开：这是全项目技术含量最高的一点。`await model.generate(...)` 是异步的，看似要等所有 token 生成完，但实际是流式的，关键在于 TextStreamer：

```js
const streamer = new TextStreamer(tokenizer, {
  skip_prompt: true,
  skip_special_tokens: true,
  callback_function,        // 每攒一段文本触发
  token_callback_function,  // 每生成一个 token 触发
});
```

它有两个回调，粒度不同：

- `token_callback_function(tokens)`：每生成一个 token 触发，参数是 token id 数组，做细粒度的事——统计 token 数、算 TPS、检测思考结束标记。
- `callback_function(text)`：每攒出一小段可读文本触发，参数是解码后的文本，把内容 `postMessage` 回主线程显示。

为什么两个回调？如果每个 token 都 postMessage 一次，消息太频繁、性能浪费。所以显示用文本粒度（攒够一段再发），统计用 token 粒度（精确计数）。

`skip_prompt: true` 不重复输出输入的 prompt；`skip_special_tokens: true` 解码时跳过 `<think>` 等特殊 token。

**关键理解**：`await model.generate` 本质是内部循环——每步生成一个 token → 触发 token 回调 → 攒成文本触发 text 回调 → 检查停止条件 → 决定是否继续。循环跑完 Promise 才 resolve。所以「流式输出」和「await 等结果」不矛盾：回调负责「过程」，await 负责「结束」。

**14. TPS 怎么算**

一句话：已生成 token 数 ÷ 已耗时，衡量生成速度。

展开：

```js
const token_callback_function = (tokens) => {
  startTime ??= performance.now();
  if (numTokens++ > 0) {
    tps = (numTokens / (performance.now() - startTime)) * 1000;
  }
};
```

`performance.now()` 返回高精度毫秒时间戳。`startTime ??= performance.now()` 记录第一个 token 的时间。tps = 已生成 token 数 ÷ 已耗时（秒）。第一个 token 不参与计算（`numTokens++ > 0` 才更新），因为第一个 token 之前包含 prompt 预处理时间，用它算的 TPS 不准，从第二个开始才是纯生成速度。

**15. generate 的参数**

一句话：控制生成行为的采样和长度参数。

展开：

```js
const { past_key_values, sequences } = await model.generate({
  ...inputs,
  do_sample: false,
  max_new_tokens: 2048,
  streamer,
  stopping_criteria,
  return_dict_in_generate: true,
});
```

- `do_sample: false`：贪心解码，每步选概率最高的 token，输出确定。`do_sample: true` 会按概率分布采样，输出随机。代码里还留了 `temperature`、`top_k` 采样参数但都关了。
- `max_new_tokens: 2048`：最多生成 2048 个新 token，防无限生成。
- `streamer`：流式输出器。
- `stopping_criteria`：停止条件，实现手动中断。
- `return_dict_in_generate: true`：让返回值是对象（含 sequences、past_key_values），而不是直接返回 token 序列。和前面 `apply_chat_template` 的 `return_dict` 是两回事——那个控制模板函数返回格式，这个控制 generate 返回格式。

**16. KV Cache 是什么，为什么注释掉**

一句话：缓存历史 token 的 key/value，加速多轮对话，但这里因后端不稳定故意关掉。

展开：生成 token 时每层都要做注意力计算，其中有大量对「历史 token」的 key/value 计算。多轮对话时，下一轮的前缀（历史消息）和上一轮重叠，如果缓存了上一轮的 key/value，下一轮就不用从头算，能省大量算力。

但代码里复用逻辑是注释掉的：

```js
// past_key_values: past_key_values_cache,
```

原因是 WebGPU 后端在张量生命周期、中断状态、多轮输入对齐上还不够稳定，贸然复用容易出错。所以先缓存 `past_key_values_cache = past_key_values`，复用逻辑关掉，等后端稳定再开。注释掉的代码不一定是有 bug，有时在记录「还没准备好的决策」——这也是个能体现工程判断的点。

**17. 中断：用户点停止**

一句话：用 InterruptableStoppingCriteria 打断生成。

展开：

```js
const stopping_criteria = new InterruptableStoppingCriteria();
```

它内部有个 `interrupted` 标志，生成循环每生成一个 token 前检查，置 true 就停。用户点「停止」发 `{ type: "interrupt" }`，Worker 调 `stopping_criteria.interrupt()` 置 true。下次生成前先 `reset()` 清标志，否则残留上次中断状态，导致下一次一开始就停。

**18. 解码：decoded 为什么没用上**

一句话：流式已经把文本送完了，complete 里的完整结果反而不需要。

展开：生成结束 `batch_decode` 把完整 token 序列解码成文本，随 `complete` 消息发回。但主线程的 `complete` 分支只用它做了 `setIsRunning(false)`，没用 `e.data.output`。因为流式阶段已经通过 `update` 消息把文本逐段拼好了，`complete` 回来时文本已显示完。所以 decoded 目前是「发了但没消费」的状态，不是 bug。

### （四）前端类

**19. 不可变更新**

一句话：不直接改原 state，返回新对象，React 靠引用变化判断重渲染。

展开：

```js
setProgressItems((prev) =>
  prev.map((item) => {
    if (item.file === e.data.file) {
      return { ...item, ...e.data };
    }
    return item;
  }),
);
```

`map` 出新数组、`{ ...item, ...e.data }` 出新对象。React 比较新旧 state 的引用，引用变了才重渲染；直接改原数组，引用没变，React 察觉不到，不会更新 UI。这是 React 的核心习惯。

**20. answerIndex：思考/答案的分界**

一句话：在 thinking→answering 切换瞬间记录文本长度，前端据此切分。

展开：

```js
if (data.answerIndex === undefined && state === "answering") {
  data.answerIndex = last.content.length;
}
```

当 worker 的 state 从 thinking 切到 answering 那一刻，把当前文本长度记下来。前端用 `content.slice(0, answerIndex)` 拿思考部分，`content.slice(answerIndex)` 拿答案部分。`data.answerIndex === undefined` 保证只在第一次切换时记录，之后不覆盖。

**21. 安全渲染：模型输出不可信**

一句话：模型输出是 untrusted 内容，必须清洗后再注入页面。

展开：模型返回 Markdown 纯文本，渲染前三步处理：

1. `marked` 把 Markdown 转 HTML
2. `DOMPurify` 清洗 HTML，去掉 `<script>`、`onclick` 等危险内容
3. `MathJax` 渲染数学公式

```js
const result = DOMPurify.sanitize(marked.parse(text, { async: false, breaks: true }));
```

模型输出本质是「不可信的外部输入」，直接 `dangerouslySetInnerHTML` 注入等于打开 XSS 大门，DOMPurify 是那道闸门。

还有个细节：`marked` 解析时会吞掉公式定界符（`\(`、`\[`）前的单个反斜杠，导致 MathJax 识别不了，所以 marked 之前先转义一次，`\(` 变 `\\(`。

**22. 为什么不直接返回 HTML**

一句话：模型吐纯文本更可控，Markdown 做中间格式。

展开：模型本质输出文本，直接吐 HTML 不可控也不安全。Markdown 是约定俗成的轻量格式，浏览器里再转 HTML，更通用、更可控。

**23. 自动滚动：只在用户没上翻时跟随**

一句话：用距离底部的距离判断该不该自动滚。

展开：

```js
if (element.scrollHeight - element.scrollTop - element.clientHeight < STICKY_SCROLL_THRESHOLD) {
  element.scrollTop = element.scrollHeight;
}
```

`scrollHeight` 内容总高度，`scrollTop` 已滚上去的高度，`clientHeight` 可视区高度，三者相减是「距离底部还有多远」。只有本来就靠近底部（小于阈值 120px）才自动滚到底，否则用户上翻历史时会被硬拽回底部，体验差。

**24. formatBytes：字节格式化**

一句话：把字节转成可读单位。

展开：

```js
function formatBytes(size) {
  const i = size == 0 ? 0 : Math.floor(Math.log(size) / Math.log(1024));
  return +(size / Math.pow(1024, i)).toFixed(2) * 1 +
    ["B", "kB", "MB", "GB", "TB"][i];
}
```

`Math.log(size) / Math.log(1024)` 是换底公式算 `log_1024(size)`，向下取整得到落在 B/kB/MB/GB 哪个量级。`size / 1024^i` 得到对应单位数值，`toFixed(2)` 保留两位小数，`+... * 1` 把字符串转回数字，最后取单位后缀。

**25. useRef vs useState**

一句话：useState 变化触发重渲染，useRef 不触发，且引用稳定。

展开：worker 引用不需要触发重渲染，只需要一个稳定的句柄随时 `.postMessage`，所以用 `useRef<Worker | null>(null)`。useRef 返回的对象在组件整个生命周期是同一个。

追问：为什么用 `Worker | null` 而不是 `null`？因为 `useRef(null)` 会让 TS 推断 current 是 `null`，调 `postMessage` 报类型错误，`Worker | null` 把「可能为 null」明确告诉 TS。

**26. useEffect 的依赖数组**

一句话：依赖数组控制 effect 何时重新执行。

展开：触发生成的 effect：

```js
useEffect(() => {
  if (messages.filter((x) => x.role === "user").length === 0) return;
  if (messages.at(-1).role === "assistant") return;
  worker.current.postMessage({ type: "generate", data: messages });
}, [messages, isRunning]);
```

它要在用户发新消息时触发，所以依赖 messages。两个 return 是保护：还没有用户消息不触发；最后一条已是 assistant（正在生成中）不重复触发。依赖数组写漏或写多都会导致 bug——漏了该重跑的不重跑，多了不该重跑的乱跑。

**27. 组件拆分**

一句话：把独立、可复用的部分抽成组件。

展开：进度条 `Progress`、聊天渲染 `Chat`、图标 `ArrowRightIcon` / `StopIcon` 各自抽成组件。组件是「搭积木」，把 HTML/CSS/JS 封装成一个功能单元。父组件给 props，子组件负责展示，不能直接改 props，要报告父组件改。state 是组件自有状态，props 是父传子的数据。

## 六、面试官可能问的问题

下面这些是精选的高频追问，答案都基于第五节，这里给「回答策略 + 关键点」，深挖就回到对应点展开。

**Q1：为什么用 Web Worker？** → 重计算不能放主线程（渲染线程），会卡死 UI。详见第 1 点。深挖：postMessage 结构化克隆、Dedicated/Shared/Service Worker。

**Q2：postMessage 是异步的吗？数据怎么传？** → 异步，传结构化克隆的副本，不是共享内存、不是引用。详见第 2 点。

**Q3：单例模式是什么？为什么用？** → 保证模型只加载一次，懒加载 + 缓存，实现是 static + ??=。详见第 4 点。深挖：??= vs ||=。

**Q4：量化 q4f16 是什么？** → 权重 4 比特量化，体积约四分之一，精度换可行性。详见第 5 点。深挖：对称/非对称、per-tensor/per-channel、混合精度。

**Q5：WebGPU 和 WebGL 区别？** → WebGL 是图形 API「借道」算通用计算，WebGPU 原生支持 compute shader，对 ML 推理更好。详见第 6 点。

**Q6：流式输出怎么实现？** → TextStreamer 在生成循环内边生成边回调。详见第 13 点。深挖：为什么两个回调。

**Q7：await 不是等所有 token 吗，怎么还流式？** → generate 是内部循环，每步生成一个 token 触发回调，循环完才 resolve。回调管过程，await 管结束。详见第 13 点关键理解。

**Q8：KV Cache 是什么？为什么注释掉？** → 缓存历史 key/value 加速多轮；WebGPU 后端不稳定故意关。详见第 16 点。

**Q9：attention_mask 干嘛的？** → 标记真实 token vs padding，让模型忽略填充。详见第 10 点。

**Q10：apply_chat_template 是什么？** → 把 messages 转成 ChatML 训练格式，add_generation_prompt 补助手开头。详见第 9 点。

**Q11：token 和分词是什么？** → 模型处理的是 token id，文本要先分词映射成数字。详见第 11 点。

**Q12：怎么区分思考过程和答案？** → R1 用 `<think></think>` 分界，检测 END 标记切 state，前端用 answerIndex 切分。详见第 12、20 点。

**Q13：模型输出怎么安全渲染？** → marked 转 HTML + DOMPurify 清洗防 XSS + MathJax 渲染公式。详见第 21 点。

**Q14：为什么不直接返回 HTML？** → 模型吐文本更可控，Markdown 做中间格式。详见第 22 点。

**Q15：React 怎么更新 state？为什么不直接改数组？** → 不可变更新，返回新对象，React 靠引用变化判断重渲染。详见第 19 点。

**Q16：useRef 和 useState 区别？** → useState 触发重渲染，useRef 不触发且引用稳定。worker 用 useRef。详见第 25 点。

**Q17：useEffect 依赖数组怎么用的？** → 控制 effect 何时重跑，写漏写多都有 bug。详见第 26 点。

**Q18：这个项目最大难点是什么？** → 两个：理解流式与 await 不矛盾；KV Cache 复用不稳定最后决定注释掉。前者是理解问题，后者是工程取舍。

**Q19：端侧模型 vs 调 API？** → 端侧优势隐私、成本、离线；劣势能力上限、部署门槛。适合隐私敏感、任务固定的场景。

**Q20：你怎么学这个项目的？** → 没教程照抄，顺着数据流读源码，把每个不懂的点记下来查清楚，最后能从头到尾说清「一个输入怎么变成一次输出」。

**Q21：为什么选 React + TypeScript？** → AI 时代前端首选，类型安全、大型项目好维护。工程化用 ESLint 约束代码风格，Tailwind 原子类不用写 CSS。
