# 端模型项目理解

这个项目做的事情一句话能说清：把一个 1.5B 参数的 DeepSeek-R1 蒸馏模型，通过 WebGPU 在浏览器本地跑起来，做文本生成。不联网、不上传任何数据。

但它值得讲的东西远不止这一句。我按数据流的方向把它拆开：用户输入一个字 → 主线程收到 → 丢给 Worker → 模型加载/生成 → 生成的 token 流式回传 → 主线程渲染成对话。理解这条链路，就理解了这个项目。

## 一、两个线程的分工

项目里只有两个关键文件：`App.tsx`（主线程，管 UI）和 `worker.js`（Worker 线程，管模型）。为什么要拆成两个线程，这是理解整个项目的起点。

模型的加载和推理都是重活。加载要下载几十上百 MB 的权重文件；推理要在 WebGPU 上跑 token 循环。这两件事如果放在主线程，页面会整个卡死——因为主线程就是渲染线程，它被阻塞了，用户点什么都没反应。

所以把重活丢给 Web Worker。Worker 在独立的线程里跑，不影响主线程渲染。两边通过 `postMessage` 通信。这里有个容易误解的点：`postMessage` 不是共享内存，它是把数据**结构化克隆**一份传过去。所以它不是函数调用那种「等返回值」，而是发一条消息过去，Worker 处理完再发一条回来。主线程在 `App.tsx` 里用 `addEventListener("message", ...)` 接收，用 `switch (e.data.status)` 分派。

Worker 是这样创建的：

```js
worker.current = new Worker(new URL("./worker.js", import.meta.url), {
  type: "module",
});
```

`new URL("./worker.js", import.meta.url)` 是 Vite 的写法，让打包工具能正确解析 worker 文件的路径。`type: "module"` 让 worker 里能直接用 ESM 的 `import`。

`worker.current` 用 `useRef` 存，而不是 `useState`。原因有两个：worker 引用本身不需要触发组件重渲染，而且我们需要一个在多次渲染之间保持稳定、可以随时 `.postMessage` 的句柄。`useRef` 返回的对象在组件整个生命周期里是同一个。

消息协议其实是一套简单的状态机，主线程和 Worker 各维护一部分状态。主线程发 `check / load / generate / interrupt / reset`，Worker 回 `loading / initiate / progress / done / ready / start / update / complete / error`。后面每一节都会涉及这些消息。

## 二、加载：从「能跑吗」到「热起来了」

### WebGPU 检测，做了两层

`App.tsx` 顶部有一行：

```js
const IS_WEBGPU_AVAILABLE = !!navigator.gpu;
```

这决定整个页面是显示正常的界面，还是显示「WebGPU is not supported」。`navigator.gpu` 是浏览器暴露的 GPU 接口，不支持时是 `undefined`，`!!` 强制转成布尔。

但这一层检测不够。Worker 里还有个 `check()`：

```js
const adapter = await navigator.gpu.requestAdapter();
if (!adapter) {
  throw new Error("WebGPU is not supported (no adapter found)");
}
```

`navigator.gpu` 存在，不代表真的能申请到适配器。有的浏览器暴露了这个对象，但驱动或硬件不支持，`requestAdapter()` 会返回 `null`。所以两层检测各管各的：第一层是快速的路由判断（UI 要不要直接显示「不支持」），第二层是真正的能力验证（真的去要一个 adapter，要不到就报 error 回来）。

### 单例：模型只加载一次

```js
class TextGenerationPipeline {
  static model_id = "onnx-community/DeepSeek-R1-Distill-Qwen-1.5B-ONNX";

  static async getInstance(progress_callback = null) {
    this.tokenizer ??= AutoTokenizer.from_pretrained(this.model_id, { progress_callback });
    this.model ??= AutoModelForCausalLM.from_pretrained(this.model_id, {
      dtype: "q4f16",
      device: "webgpu",
      progress_callback,
    });
    return Promise.all([this.tokenizer, this.model]);
  }
}
```

这个类的核心是 `static` 加 `??=`。

`static` 意味着 `tokenizer` 和 `model` 是挂在**类**上，而不是实例上。所以不需要 `new TextGenerationPipeline()`，直接 `TextGenerationPipeline.getInstance()` 就能用，而且所有调用方共享同一份 `tokenizer` 和 `model`。

`??=` 是「逻辑空赋值」。`this.tokenizer ??= xxx` 等价于 `this.tokenizer === null || this.tokenizer === undefined ? this.tokenizer = xxx : this.tokenizer`。也就是说，第一次调用时 `this.tokenizer` 是 `undefined`，触发加载；之后每次调用发现已经有值了，直接复用，不再加载。

这就是单例模式的落地形式：**懒加载 + 缓存**。模型只下载一次、只初始化一次，之后反复用。

`Promise.all` 是因为 tokenizer 和 model 是两个独立的异步任务，可以并行下载，等两个都 resolve 了再一起返回。`from_pretrained` 返回的是 Promise，所以 `??=` 赋值后存的是 Promise 本身，不是结果——这也保证了并发调用 `getInstance` 时，两个调用拿到的是同一个 Promise，不会重复下载。

### 量化：1.5B 模型凭什么能进浏览器

`from_pretrained` 里两个配置是关键：

```js
dtype: "q4f16",   // 权重 4 比特量化
device: "webgpu", // 推理走 WebGPU
```

一个 1.5B 参数的模型，如果按 fp16 存，每个参数 2 字节，光权重就是 3GB 左右，浏览器根本扛不住。`q4f16` 把权重**量化**到 4 比特——每个参数从 16 位压到 4 位，体积直接缩到原来的四分之一左右，下载快、内存占用也小。

量化的代价是精度损失。4 比特能表示的值只有 16 个，和 fp16 的精度差很多。但对推理来说，这种损失是可接受的——模型的泛化能力够强，权重量化后的输出和原版差别不大。这就是「用精度换可行性」，端侧模型能落地的关键一步。

`device: "webgpu"` 则是告诉推理引擎用 WebGPU 而不是 CPU 去算。CPU 跑 1.5B 模型的 token 循环会非常慢，WebGPU 把矩阵运算放到 GPU 上并行，速度能提升一个量级。

底层这些能力是 Transformers.js 和 ONNX Runtime Web 提供的。模型本身是 ONNX 格式，`from_pretrained` 会去 HuggingFace 下载对应的 ONNX 权重，然后用 WebGPU 后端加载。

### 下载进度是怎么流到 UI 的

`load()` 里把 `progress_callback` 传给 `getInstance`：

```js
const [tokenizer, model] = await TextGenerationPipeline.getInstance((x) => {
  self.postMessage(x);
});
```

`from_pretrained` 下载模型文件时，会周期性调用这个回调，`x` 里带下载进度信息。Worker 直接把它 `postMessage` 回主线程。主线程收到的是三种消息：

- `initiate`：某个文件开始下载（主线程把它 push 进进度列表）
- `progress`：某个文件下载进度更新（主线程找到对应文件，合并新进度）
- `done`：某个文件下载完成（主线程把它从列表里移除）

主线程更新进度列表用的是不可变更新，这个后面讲前端时细说。

### 预热：为什么要先跑一次假输入

`load()` 的最后一步：

```js
self.postMessage({ status: "loading", data: "Compiling shaders and warming up model..." });

const inputs = tokenizer("a");
await model.generate({ ...inputs, max_new_tokens: 1 });
self.postMessage({ status: "ready" });
```

WebGPU 推理有个前置成本：把模型的计算图**编译成 shader**（着色器），构建算子图、分配缓冲。这个过程很慢，可能要几秒甚至更久。如果等用户第一次提问时才做，用户会明显感觉到「我发了消息，卡了好久才出第一个字」。

所以加载阶段用假输入 `"a"` 跑一次 `max_new_tokens: 1` 的生成，把 shader 编译、算子构建这些一次性成本提前付掉。等用户真正提问时，这些已经准备好了，直接进入 token 循环。这就是「预热」，也是为什么加载完会显示一个「Compiling shaders」的提示。

## 三、生成：从 messages 数组到流式 token

### chat template：把对话转成模型认识的格式

用户在 UI 里的消息，在代码里是这样一个数组：

```js
[{ role: "user", content: "你好" }]
```

但模型训练时看到的是**带特殊标记的字符串**，比如 ChatML 格式：

```
<|im_start|>user
你好<|im_end|>
<|im_start|>assistant
```

模型不理解「role」这个字段，它只认识 token。所以需要一个东西把 `messages` 数组翻译成它训练时见到的格式。这个东西就是 chat template——它其实是 tokenizer 配置文件里一段模板，定义了「对话怎么拼成字符串」。

`apply_chat_template` 就是执行这个模板：

```js
const inputs = tokenizer.apply_chat_template(messages, {
  add_generation_prompt: true,
  return_dict: true,
});
```

`add_generation_prompt: true` 的作用是在末尾追加 `<|im_start|>assistant\n`，相当于告诉模型「轮到你了，开始回答」。如果不加这个，模型不知道要从哪开始生成。

`return_dict: true` 让返回值是个字典，包含：

```js
{
  input_ids: tensor([151649, 151650, ...]),  // token id 序列
  attention_mask: tensor([1, 1, 1, ...]),      // 注意力掩码
}
```

`input_ids` 是文本分词后每个 token 的 id。`attention_mask` 是同样长度的 0/1 序列，标记哪些位置是真实 token（1）、哪些是 padding 填充（0）。模型算注意力时，对 mask 为 0 的位置不关注。单条消息 padding 通常不多，但这个字段是标准输入，`generate` 需要它。

### 思考与回答的分界

DeepSeek-R1 是推理模型，它的输出结构是「先思考、再回答」。思考过程用 `<think></think>` 包起来，结束后的内容才是正式答案。

代码里把这两个特殊标记的 token id 提前算出来：

```js
const [START_THINKING_TOKEN_ID, END_THINKING_TOKEN_ID] = tokenizer.encode(
  "<think></think>",
  { add_special_tokens: false },
);
```

`tokenizer.encode` 把字符串转成 token id 数组。`"<think></think>"` 编码后正好是两个 token（一个开始、一个结束），解构出来就是这两个 id。`add_special_tokens: false` 表示不要自动加 `<s>`、`</s>` 这类额外的特殊 token，只编码这个字符串本身。

然后维护一个 `state`：

```js
let state = "thinking"; // thinking | answering
```

每生成一个 token 就检查是不是 `END_THINKING_TOKEN_ID`，是就把 `state` 切成 `"answering"`。这个 `state` 会随着每次更新一起发回主线程，前端靠它区分「思考过程」和「最终答案」。

### TextStreamer：流式输出的机制

`await model.generate(...)` 是异步的，那为什么还能边生成边显示？关键在于 `TextStreamer`：

```js
const streamer = new TextStreamer(tokenizer, {
  skip_prompt: true,
  skip_special_tokens: true,
  callback_function,
  token_callback_function,
});
```

`TextStreamer` 不是「等所有 token 生成完再输出」，而是**在生成循环内部，一边生成一边触发回调**。它有两个回调，粒度不同：

- `token_callback_function(tokens)`：每生成一个 token 触发一次，参数是刚生成的 token id 数组。用来做细粒度的事：统计 token 数、算 TPS、检测思考结束标记。
- `callback_function(text)`：每攒出一小段可读文本触发一次，参数是解码后的文本。用来把内容发回主线程显示。

为什么要两个回调？如果每个 token 都 `postMessage` 一次，消息太频繁，性能浪费。所以显示用文本粒度（攒够一段再发），统计用 token 粒度（精确计数）。`skip_prompt: true` 是不重复输出输入的 prompt，`skip_special_tokens: true` 是解码时跳过 `<think>` 这类特殊 token。

`await model.generate` 本质上是一个内部循环：每一步生成一个 token → 触发 token 回调 → 攒成文本触发 text 回调 → 检查停止条件 → 决定是否继续。这个循环跑完，Promise 才 resolve。所以「流式输出」和「await 等结果」不矛盾：回调负责「过程」，await 负责「结束」。

### TPS：每秒生成多少 token

`token_callback_function` 里算 TPS：

```js
const token_callback_function = (tokens) => {
  startTime ??= performance.now();
  if (numTokens++ > 0) {
    tps = (numTokens / (performance.now() - startTime)) * 1000;
  }
};
```

`performance.now()` 返回高精度时间戳，单位毫秒。`startTime ??= performance.now()` 记录第一个 token 的时间。`tps` 的计算是「已生成 token 数 ÷ 已耗时（秒）」。

第一个 token 不参与 TPS 计算（`numTokens++ > 0` 才更新），因为第一个 token 之前包含了 prompt 的预处理时间，用它算出来的 TPS 不准。从第二个 token 开始，才是纯生成速度。

### 生成参数

`model.generate` 的完整调用：

```js
const { past_key_values, sequences } = await model.generate({
  ...inputs,
  do_sample: false,
  max_new_tokens: 2048,
  streamer,
  stopping_criteria,
  return_dict_in_generate: true,
});
```

- `do_sample: false`：贪心解码，每步选概率最高的 token，输出确定。反过来 `do_sample: true` 会按概率分布采样，输出更随机。这里注释里还留了 `temperature`、`top_k` 等采样参数，但都关了。
- `max_new_tokens: 2048`：最多生成 2048 个新 token，防止无限生成。
- `streamer`：上面说的流式输出器。
- `stopping_criteria`：停止条件，用来实现用户手动中断。
- `return_dict_in_generate: true`：让返回值是个对象（含 `sequences`、`past_key_values` 等字段），而不是直接返回 token 序列。这跟前面 `apply_chat_template` 的 `return_dict` 是两回事——那个是控制模板函数的返回格式，这个是控制 `generate` 的返回格式。

### 返回值的解构

```js
const { past_key_values, sequences } = await model.generate(...);
```

- `sequences`：完整生成的 token 序列（包括输入的 prompt 部分），形状是 `[batch_size, seq_len]` 的二维张量。要显示成文本，得 `batch_decode`。
- `past_key_values`：KV Cache，这一轮生成过程中每一层注意力算出来的 key/value 缓存。

KV Cache 是多轮对话加速的关键。生成 token 时，每一层都要做注意力计算，而注意力计算里有大量对「历史 token」的 key/value 计算。这些计算结果在多轮对话里是可以复用的——下一轮对话的前缀（历史消息）和上一轮是重叠的，如果缓存了上一轮的 key/value，下一轮就不用从头算。

但代码里这行是注释掉的：

```js
// past_key_values: past_key_values_cache,
```

原因是 WebGPU 后端在张量生命周期、中断状态、多轮输入对齐这些方面还不够稳定，贸然复用 KV Cache 容易出问题。所以先缓存了 `past_key_values_cache = past_key_values`，但复用逻辑先关掉，等后端稳定了再打开。注释掉的代码不一定是有 bug，有时是在记录一个「还没准备好的决策」。

### 解码：为什么 complete 里 decoded 没用上

生成结束后：

```js
past_key_values_cache = past_key_values;

const decoded = tokenizer.batch_decode(sequences, {
  skip_special_tokens: true,
});

self.postMessage({
  status: "complete",
  output: decoded,
});
```

`batch_decode` 把二维的 token 序列解码成文本（`batch` 指它处理的是 `[batch, seq]` 形状，一次解一批）。`skip_special_tokens: true` 去掉特殊 token。

但注意：主线程的 `complete` 处理分支里，**没有用 `e.data.output`**，只做了 `setIsRunning(false)`。

这不是 bug，是因为流式输出阶段已经通过 `update` 消息把完整文本发过去了。`decoded` 是「完整结果」，但主线程在 `update` 阶段就把文本逐段拼好了，等 `complete` 回来时，文本已经显示完了，不需要再用这个完整结果。所以 `decoded` 目前是「发了但没消费」的状态。

### 中断：用户点停止

`max_new_tokens: 2048` 意味着生成可能很长，必须能让用户打断。用的是 `InterruptableStoppingCriteria`：

```js
const stopping_criteria = new InterruptableStoppingCriteria();
```

它内部有个 `interrupted` 标志。生成循环每生成一个 token 前会检查这个标志，如果被置为 true，就停止生成。用户点「停止」时，主线程发 `{ type: "interrupt" }`，Worker 调用 `stopping_criteria.interrupt()` 把这个标志置 true。

下一次生成前，要先 `stopping_criteria.reset()` 把这个标志清掉，否则会残留上次的中断状态，导致下一次一开始就停。

## 四、前端：消息和状态怎么流转

### App.tsx 的状态设计

`App.tsx` 里状态不少，但每个职责单一：

```js
const [status, setStatus] = useState(null);          // null / loading / ready
const [error, setError] = useState(null);
const [loadingMessage, setLoadingMessage] = useState("");
const [progressItems, setProgressItems] = useState([]);
const [isRunning, setIsRunning] = useState(false);
const [input, setInput] = useState("");
const [messages, setMessages] = useState([]);
const [tps, setTps] = useState(null);
const [numTokens, setNumTokens] = useState(null);
```

`status` 是一个三态状态机，驱动页面显示三个不同界面：

- `null`：还没加载，显示欢迎页和「Load model」按钮
- `loading`：显示下载进度条
- `ready`：显示聊天界面

`messages` 的每个元素是 `{ role, content, answerIndex }`。`role` 是 `user` 或 `assistant`，`content` 是文本内容，`answerIndex` 是「思考过程」和「最终答案」的分界位置（可选）。

### 消息处理：一个 switch 分派所有 worker 回信

主线程在 worker 的 `message` 事件里用一个 `switch` 处理所有回信。挑几个关键的分支讲。

**`update` 分支**，流式输出时把新文本追加到 assistant 消息：

```js
setMessages((prev) => {
  const cloned = [...prev];
  const last = cloned.at(-1);
  const data = {
    ...last,
    content: last.content + output,
  };
  if (data.answerIndex === undefined && state === "answering") {
    data.answerIndex = last.content.length;
  }
  cloned[cloned.length - 1] = data;
  return cloned;
});
```

这里 `cloned = [...prev]` 浅拷贝数组，然后只改最后一条消息，返回新数组。这是 React 的不可变更新原则：不直接改原 state，而是返回新对象，React 靠引用变化判断要不要重渲染。

`answerIndex` 的记录逻辑很关键：当 worker 的 `state` 从 `thinking` 切到 `answering` 的那一刻，把**当前文本长度**记下来。这样前端就能用 `content.slice(0, answerIndex)` 拿思考部分，`content.slice(answerIndex)` 拿答案部分。注意 `data.answerIndex === undefined` 的判断，保证只在第一次切换时记录，之后不再覆盖。

**`start` 分支**，生成开始时追加一条空的 assistant 消息：

```js
setMessages((prev) => [...prev, { role: "assistant", content: "" }]);
```

这条空消息是后续 `update` 追加文本的「目标」。没有它，`update` 里的 `last` 就是用户消息，会把生成内容拼到用户消息上。

### 触发生成的 effect

```js
useEffect(() => {
  if (messages.filter((x) => x.role === "user").length === 0) return;
  if (messages.at(-1).role === "assistant") return;
  worker.current.postMessage({ type: "generate", data: messages });
}, [messages, isRunning]);
```

这个 effect 的职责是「当用户发了一条新消息时，触发一次生成」。两个 return 是保护：

1. 还没有用户消息（比如初始空状态），不触发。
2. 最后一条已经是 assistant 消息，说明正在生成中（`start` 刚追加了空 assistant 消息），不再触发新的生成。

这样能避免重复触发。`onEnter` 里追加用户消息后，这个 effect 会因为 `messages` 变化而执行，把完整 `messages` 发给 worker 生成。

### 自动滚动：只在用户没上翻时跟随

流式输出时内容不断变长，聊天区要自动滚到底。但用户如果手动往上翻历史，就不能硬拽回底部。处理方式：

```js
if (element.scrollHeight - element.scrollTop - element.clientHeight < STICKY_SCROLL_THRESHOLD) {
  element.scrollTop = element.scrollHeight;
}
```

`scrollHeight` 是内容总高度，`scrollTop` 是已经滚上去的高度，`clientHeight` 是可视区高度。三者相减得到「距离底部还有多远」。只有当用户本来就靠近底部（小于阈值 120px）时，才把 `scrollTop` 设到 `scrollHeight`（滚到底）。这样「跟随滚动」和「用户主动上翻」就不冲突。

### 输入框自适应高度

```js
useEffect(() => {
  if (!textareaRef.current) return;
  const target = textareaRef.current;
  target.style.height = "auto";
  const newHeight = Math.min(Math.max(target.scrollHeight, 24), 200);
  target.style.height = `${newHeight}px`;
}, [input]);
```

每次 `input` 变化时，先 `height = "auto"` 重置，再读 `scrollHeight`（内容实际高度），取 `max(24, min(scrollHeight, 200))`——最小 24px，最大 200px。先重置再测量是关键，否则 `scrollHeight` 读到的是上一次设的高度，会越算越高。

### Chat.tsx：思考折叠 + 安全渲染

`Chat.tsx` 负责把 `messages` 渲染成对话气泡。核心是两个点。

**思考过程的折叠。** 靠 `answerIndex` 把 assistant 消息的文本切成两段：

```js
const thinking = hasAnswer ? content.slice(0, answerIndex) : content;
const answer = hasAnswer ? content.slice(answerIndex) : "";
```

生成过程中，`answerIndex` 还没出现，整段内容都归入 `thinking`，顶部显示「Thinking...」（带跳动动画）。一旦检测到思考结束标记、`answerIndex` 出现，`answer` 有内容了，顶部就变成「View reasoning.」，点开能看完整思考过程，下方直接显示最终答案。

**模型输出是 untrusted 内容，要安全渲染。** 模型返回的是 Markdown 纯文本，前端渲染前要做三步处理：

1. `marked` 把 Markdown 转成 HTML
2. `DOMPurify` 清洗 HTML，防止模型输出里混入 `<script>`、`onclick` 之类的危险内容
3. `MathJax` 渲染数学公式

```js
const result = DOMPurify.sanitize(marked.parse(text, { async: false, breaks: true }));
```

这一步是必须的——模型输出本质上是「不可信的外部输入」，直接 `dangerouslySetInnerHTML` 注入页面等于把 XSS 的大门打开。`DOMPurify` 就是那道闸门。

还有个细节：`marked` 解析 Markdown 时会吞掉数学公式定界符（`\(`、`\[` 等）前面的单个反斜杠，导致 MathJax 识别不了。所以在 `marked` 之前要先转义一次，把 `\(` 变成 `\\(`。这是那种「不真跑一遍不会发现」的坑。

这里也回答了「为什么不直接返回 HTML」的问题：模型输出本质是文本，让它直接吐 HTML 不可控也不安全；用 Markdown 这种约定俗成的轻量格式作为中间层，在浏览器里再转成 HTML，更通用、更可控。

### Progress.tsx：进度条和字节格式化

`Progress.tsx` 很小，但 `formatBytes` 值得一说：

```js
function formatBytes(size) {
  const i = size == 0 ? 0 : Math.floor(Math.log(size) / Math.log(1024));
  return +(size / Math.pow(1024, i)).toFixed(2) * 1 +
    ["B", "kB", "MB", "GB", "TB"][i];
}
```

它在把字节数转成「人能读的单位」。`Math.log(size) / Math.log(1024)` 是用换底公式算 `log_1024(size)`，向下取整得到「落在 B/kB/MB/GB 哪个量级」。然后 `size / 1024^i` 得到对应单位的数值，`toFixed(2)` 保留两位小数。`+... * 1` 把字符串转回数字（因为 `toFixed` 返回字符串）。最后的 `["B","kB","MB","GB","TB"][i]` 取单位后缀。

这几行代码信息密度很高，是我读源码时喜欢停下来琢磨的那种小函数。

## 五、串起来看

把上面这些细节连回最开始那条数据流，整个项目的图景就完整了：

用户敲下回车 → 主线程 `onEnter` 追加一条 user 消息 → `messages` 变化触发生成 effect → 主线程把 `messages` 发给 Worker → Worker 用单例拿到的 tokenizer 走 `apply_chat_template`，把对话转成模型认识的 token 序列 → `model.generate` 在 WebGPU 上一个 token 一个 token 生成 → `TextStreamer` 每攒一段文本就 `update` 回主线程 → 主线程把文本追加到 assistant 消息，同时记录 `answerIndex` 分界 → 生成结束发 `complete`，`isRunning` 复位 → `Chat.tsx` 把思考过程和答案分开渲染，Markdown 转 HTML、清洗、渲染公式。

链条上每个环节都有一件事要处理：线程怎么分工、模型怎么只加载一次、权重怎么量化、对话怎么转格式、token 怎么流式回传、思考怎么和答案分界、文本怎么安全地变成页面。单看每一段都很小，连起来才是一个能跑的东西。

这就是我对这个项目的理解。不是背一堆「WebGPU」「量化」「流式」的名词，而是能从头到尾说出一个输入是怎么变成一次输出的。
